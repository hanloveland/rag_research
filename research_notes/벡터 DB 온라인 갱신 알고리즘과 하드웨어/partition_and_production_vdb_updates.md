# Partition/cluster-based ANN indexes and production vector DBs: online updates and index freshness (2020–2026)

Scope note: this file covers (a) research systems for updatable partition-based / disk-based vector indexes (SPFresh/LIRE, Ada-IVF, DeDrift, LSM-VEC, UBIS, IP-DiskANN and related graph-update work where it frames the comparison), and (b) the update architectures of Milvus, Qdrant, Weaviate, Vespa, pgvector, Elasticsearch/Lucene, Pinecone, Redis, LanceDB and Chroma, plus benchmarks and embedding-drift/migration work. Everything marked "vendor doc/blog" is a vendor claim; arXiv/venue items are research results (peer-review status noted where known). Numbers were taken from the primary pages fetched; where a page could not be read, that is recorded in Gaps.

## KQ1. SPFresh (SOSP 2023): how LIRE works, what it reports vs. DiskANN/FreshDiskANN, and what hardware it relies on

### Takeaway
SPFresh is an in-place-update extension of SPANN (centroid graph in memory + posting lists on SSD). Its LIRE protocol appends inserts to the nearest posting, tombstones deletes, and keeps partitions balanced by splitting over-long postings and reassigning only boundary vectors in nearby postings; a background "Local Rebuilder" does this off the foreground path. Against a FreshDiskANN-style DiskANN baseline at 100M scale it reports ~2.41× lower P99.9 latency, ~5.3× less memory and stable recall; it depends on an SPDK user-space NVMe block controller for in-place posting appends.

### Cited Findings
- Title/venue/authors: "SPFresh: Incremental In-Place Update for Billion-Scale Vector Search", Yuming Xu, Hengyu Liang, Jin Li, Shuotao Xu, Qi Chen, Qianxi Zhang, Cheng Li, Ziyue Yang, Fan Yang, Yuqing Yang, Peng Cheng, Mao Yang; SOSP '23 (Koblenz, Oct 23–26, 2023); arXiv:2410.14452 posted 18 Oct 2024 — [arXiv abstract](https://arxiv.org/abs/2410.14452); [Microsoft Research listing](https://www.microsoft.com/en-us/research/publication/spfresh-incremental-in-place-update-for-billion-scale-vector-search/)
- Motivation (abstract): existing systems "keep a secondary index for updates and periodically rebuild the main index", which causes "high fluctuations of search latency and accuracy" and is resource-intensive; SPFresh claims it needs "only 1% of DRAM and less than 10% cores needed at the peak" vs. the state of the art for a billion-scale disk index at 1% daily update rate — [arXiv abstract](https://arxiv.org/abs/2410.14452)
- Base index: LIRE sits on SPANN; vectors are stored in on-disk postings (partitions) and an in-memory SPTAG graph over posting centroids routes queries — [arXiv HTML v1](https://arxiv.org/html/2410.14452v1)
- NPA invariant ("nearest partition assignment"): "each vector should be put into the nearest posting so that it can be well represented by the posting centroid" — [arXiv HTML v1](https://arxiv.org/html/2410.14452v1)
- Insert/delete mechanics: inserts append to the nearest posting; deletes are tombstones in a version map (filtered from results, physically removed later) — [arXiv HTML v1](https://arxiv.org/html/2410.14452v1)
- Split: when a posting exceeds a length limit it is split evenly into two; this can break NPA for vectors in the split posting and in neighboring postings, triggering reassignment. Merge: when a posting falls below a lower threshold it is merged into its nearest neighbor; only vectors of the removed posting need reassignment, and those reassignments never trigger splits of the merged posting — [arXiv HTML v1](https://arxiv.org/html/2410.14452v1)
- Reassign pruning (two necessary conditions under Euclidean distance): (1) a vector in the split posting is a candidate only if its old centroid is closer than both new centroids; (2) a vector in a neighboring posting is a candidate only if one of the new centroids is closer than its own centroid. Only the nearest postings around the split are scanned (default reassign range 64); each candidate gets an NPA check before moving — [arXiv HTML v1](https://arxiv.org/html/2410.14452v1)
- Termination argument: each split adds one centroid and centroid count is bounded by vector count, so split/reassign cascades terminate — [arXiv HTML v1](https://arxiv.org/html/2410.14452v1)
- Background work: a Local Rebuilder runs split/merge/reassign on background threads; splits first garbage-collect deleted vectors, then cluster the posting. Versioning uses one byte per vector in memory (7-bit reassign version + 1-bit deletion); stale replicas are dropped at search time and collected later. Foreground:background thread ratio reported as 2:1 — [arXiv HTML v1](https://arxiv.org/html/2410.14452v1)
- Concurrency: posting-level write locks make append/split/merge atomic; reassignment uses CAS on version numbers; reported lock contention < 1% and "posting-missing" aborts < 0.001% of insertions — [arXiv HTML v1](https://arxiv.org/html/2410.14452v1)
- Hardware/storage layer: a Block Controller uses SPDK's user-space NVMe interface to bypass the kernel storage stack; APPEND reads and rewrites only the last block of a posting then atomically swaps the block-mapping entry; postings are ~3–4 blocks; block mapping is an in-memory dense array (40 B per posting, est. ~4 GB for 1B vectors / ~0.1B postings). The paper explicitly contrasts this with LSM-style read amplification. Crash recovery = periodic snapshots (~40 GB of in-memory state at billion scale, 2–3 s to flush on PCIe NVMe) + WAL, with a pre-release buffer for freed blocks — [arXiv HTML v1](https://arxiv.org/html/2410.14452v1)
- Evaluation hardware: Azure lsv3 VM, 16 vCPU (Xeon Platinum 8370C), 128 GB RAM, local NVMe with up to 400K guaranteed IOPS — [arXiv HTML v1](https://arxiv.org/html/2410.14452v1)
- Datasets/workloads: SIFT1B (1B×128 byte vectors) and SPACEV1B (1B×100 byte vectors from production search data). Workload A: 100M SPACEV, 1% daily updates for 100 days; B: same on 100M SIFT; C: billion-scale stress, 1% daily for 20 days. Update rate 600–1,200 QPS, justified by a cited ~100M updates/day at Alibaba — [arXiv HTML v1](https://arxiv.org/html/2410.14452v1)
- Baselines: "DiskANN (FreshDiskANN)" graph index with streaming merges every 30M vectors (run only at 100M because 1B would need several TB of DRAM), and "SPANN+" = append-only SPANN (SPFresh without split/reassign) — [arXiv HTML v1](https://arxiv.org/html/2410.14452v1)
- 100M results: SPFresh holds P99.9 search latency near 4 ms; DiskANN exceeds 20 ms during global rebuilds; SPANN+ rises from 4 ms to >10 ms; SPFresh averages 2.41× lower P99.9 than DiskANN; average insert cost 1.5 ms; ~0.4% of insertions trigger rebalancing (avg 2 splits, max 160, cascade length 3), merges ~0.1% of updates, each rebalance evaluates ~5,094 vectors and reassigns ~79; memory ~5.30× lower than baselines and under 20 GB (DiskANN needs +60 GB for streaming merge and +15 GB for a second index); DiskANN used 16 threads, SPFresh/SPANN+ 6 each. Recall: SPFresh/SPANN+ accuracy rises over time while DiskANN accuracy declines — [arXiv HTML v1](https://arxiv.org/html/2410.14452v1)
- Billion-scale stress: 4 update + 8 search + 3 background threads; ~4K search QPS and ~2K update QPS on one NVMe SSD with 15 cores; search throughput saturates disk IOPS at ~8 search threads (exceeding 400K IOPS); recall stays >0.862 (uniform) and >0.807 (skewed) searching 64 postings; memory ~74 GB, CPU ~1300% — [arXiv HTML v1](https://arxiv.org/html/2410.14452v1)
- Replication overhead: 86% of vectors have >1 replica, avg 5.47 replicas per vector (SPANN-style closure assignment) — [arXiv HTML v1](https://arxiv.org/html/2410.14452v1)
- Independent view of LIRE (Apple/UW-Madison, Ada-IVF paper): LIRE "reindexes eagerly, including partitions that recent queries never access"; on MSTuring10M with localized queries LIRE created ~3× as many partitions and needed ~4× the update time of Ada-IVF for similar QPS — [arXiv 2411.00970 HTML](https://arxiv.org/html/2411.00970v1)
- Independent view (NTU, LSM-VEC paper): SPFresh "offers better scalability but suffers from reduced recall due to coarse partitioning"; in their 100M SIFT "balanced" workload SPFresh Recall10@10 = 75.5% vs. DiskANN 82.0% vs. LSM-VEC 88.4% — [arXiv 2505.17152 HTML](https://arxiv.org/html/2505.17152v1)
- Baseline FreshDiskANN background: "FreshDiskANN: A Fast and Accurate Graph-Based ANN Index for Streaming Similarity Search" (Singh et al., 2021, arXiv:2105.09613) states that the industry practice "is to periodically re-build these indices, which can be prohibitively expensive"; the BigANN'23 streaming baseline ("DiskANN streaming in-memory index, using ideas from FreshDiskANN") processes insertions eagerly and deletions lazily, with a consolidation step that frees deleted vectors and repairs the graph — [FreshDiskANN arXiv](https://arxiv.org/abs/2105.09613v1); [BigANN'23 results](https://arxiv.org/html/2409.17424v1)

### Inferences
- SPFresh's advantage is specifically on drifting/skewed distributions: the paper itself notes that on near-uniform SIFT, append-only SPANN+ performs close to SPFresh, so the LIRE rebalancing pays off mainly when partition sizes skew.
- The "1% DRAM / 10% cores" headline comes from the intro's comparison to a rebuild-based baseline; the billion-scale run itself uses ~74 GB and ~13 cores, so the headline should be cited as the authors' relative framing, not an absolute footprint.
- The SPDK dependency means the reported update latencies assume kernel-bypass NVMe access; the paper does not report a POSIX-I/O variant.
- Two later papers (Ada-IVF, LSM-VEC) independently report that LIRE's eager, uniform rebalancing is either wasteful for cold partitions or leaves recall below graph indexes, so SPFresh should be presented as a strong baseline rather than the final word.

### Gaps
- The arXiv HTML page was read to ~100K of ~110K characters; the final section (likely related work/conclusion) was not read.
- SPANN itself (NeurIPS 2021, "SPANN: Highly-efficient Billion-scale Approximate Nearest Neighbor Search", arXiv:2111.08566) was not fetched in this session; its closure/replication rules are cited only through SPFresh.
- No SPFresh number for a single headline recall at 100M scale (the paper shows curves, not a scalar).

## KQ2. Other research on updatable disk-based / partition-based indexes, 2023–2026

### Takeaway
Follow-on research splits into (i) smarter IVF/partition maintenance (Ada-IVF's read-temperature-driven local re-clustering, DeDrift's quantizer adaptation, UBIS's balance-aware splitting + lock-free scheduling on top of SPFresh), (ii) LSM-structured graph indexes (LSM-VEC), and (iii) in-place graph updates (IP-DiskANN, MERIT, MN-RU, DGAI) that attack FreshDiskANN's lazy-delete/consolidate model. Reported gains are typically 1.5–5× update throughput or 2–3× lower update latency over LIRE/DiskANN at similar recall, but each is measured at 1M–100M scale, usually on a single node. No results were found for "DiskANN++", "AisLSM", "Vexless", "DEG", or RaBitQ-based dynamic indexes.

### Cited Findings

**Ada-IVF (Apple + UW-Madison, 2024)**
- Title: "Incremental IVF Index Maintenance for Streaming Vector Search", Jason Mohoney, Anil Pacaci, Shihabur Rahman Chowdhury, Umar Farooq Minhas, Jeffrey Pound, Cedric Renggli, Nima Reyhani, Ihab F. Ilyas, Theodoros Rekatsinas, Shivaram Venkataraman; arXiv:2411.00970 (Nov 2024, preprint; no venue stated on the page) — [arXiv HTML](https://arxiv.org/html/2411.00970v1)
- Mechanism: a per-partition "local indicator" combines a read-temperature factor (rises on access, decays otherwise), a size-imbalance term and a drift term (centroid change from initial state); partitions over threshold are "violators". A "global indicator" combines relative change in partition-size std-dev with a reconstruction-error comparison against an estimated full-rebuild error and triggers a full rebuild when exceeded — [arXiv HTML](https://arxiv.org/html/2411.00970v1)
- Local re-clustering: violators above target size are split with k-means, smaller ones removed; the nearest r_c = 25 neighbor partitions are gathered by centroid distance and balanced k-means runs over the combined vectors, initialized from previous centroids — [arXiv HTML](https://arxiv.org/html/2411.00970v1)
- Setup: internal recommendation trace (read-heavy, high write locality) on MSTuring10M; BigANN-SS (30M MSTuring subset, inserts/deletes of 10k–250k vectors); SIFT1M and GloVe1M microbenchmarks; AWS r5.24xlarge (96 vCPU, 768 GB); recall target 0.9. Baselines: periodic Rebuild (after 2.5% modified), Frozen, Update (centroid update, cites DeDrift), LIRE (re-implemented inside Ada-IVF) — [arXiv HTML](https://arxiv.org/html/2411.00970v1)
- Results normalized to Rebuild (search QPS / update throughput): Internal — Ada-IVF 0.89 / 6.7, LIRE 0.83 / 4.2; BigANN-SS — Ada-IVF 0.85 / 10.0, LIRE 0.89 / 4.7. Abstract headline: average 2× and up to 5× higher update throughput than state-of-the-art dynamic IVF strategies with comparable query throughput — [arXiv HTML](https://arxiv.org/html/2411.00970v1)

**DeDrift (Yandex + Meta AI, ICCV 2023)**
- Title: "DeDrift: Robust Similarity Search under Content Drift", Dmitry Baranchuk, Matthijs Douze, Yash Upadhyay, I. Zeki Yalniz; ICCV 2023 (peer-reviewed); arXiv:2308.02752 — [ICCV open access PDF](https://openaccess.thecvf.com/content/ICCV2023/papers/Baranchuk_DEDRIFT_Robust_Similarity_Search_under_Content_Drift_ICCV_2023_paper.pdf); [arXiv](https://arxiv.org/pdf/2308.02752)
- Mechanism/claims: "updates embedding quantizers to continuously adapt large-scale indexing structures on-the-fly" rather than re-indexing every stored vector; "almost eliminates the accuracy degradation due to the query and database content drift while being up to 100x faster than a full index reconstruction"; focused on IVF-style indexes because graph indexes "do not scale as well to large datasets" — [arXiv](https://arxiv.org/pdf/2308.02752)

**LSM-VEC (NTU, 2025)**
- Title: "LSM-VEC: A Large-Scale Disk-Based System for Dynamic Vector Search", Shurui Zhong, Dingheng Mo, Siqiang Luo (Nanyang Technological University); arXiv:2505.17152, submitted 22 May 2025 (preprint) — [arXiv abstract](https://arxiv.org/abs/2505.17152v1)
- Mechanism: HNSW split into a memory-resident upper layer (<1% of nodes) and a disk-resident bottom layer stored in AsterDB (a graph-oriented LSM-tree); edges are key-value pairs buffered in memory and pushed to deeper levels via compaction; vectors live in a separate contiguous on-disk array sorted by ID. Insert: random level, upper-layer search in memory, bottom-layer search on disk, link to top-M neighbors, write edges to LSM. Delete: neighbors relinked locally, edges removed from LSM, vector data deleted. Update = delete + insert ("out-of-place"). Search uses SimHash sign hashes kept in memory to skip candidates (threshold from Hoeffding's inequality, sampling ratio ρ). A periodic global reordering pass over the bottom layer aligns hot co-traversed nodes with compaction — [arXiv HTML](https://arxiv.org/html/2505.17152v1)
- Setup: Xeon Gold 6326 (64 cores), 256 GB, 2 TB NVMe; SIFT1B but experiments used a 100M subset; baselines only DiskANN and SPFresh — [arXiv HTML](https://arxiv.org/html/2505.17152v1)
- Numbers: Recall10@10 balanced workload LSM-VEC 88.4% / DiskANN 82.0% / SPFresh 75.5%; delete-heavy LSM-VEC 77.4% / DiskANN 61.0%. Update latency insert-only LSM-VEC 4.90 ms / SPFresh 6.10 ms / DiskANN 12.5 ms; delete-heavy LSM-VEC 4.60 ms / DiskANN 11.86 ms. Search latency LSM-VEC ~4.6–4.7 ms, DiskANN 8.0→12.0 ms, SPFresh ~7 ms. Memory insert-only: DiskANN 25→76 GB, LSM-VEC 22.4→26.5 GB; balanced: DiskANN peak 80 GB, LSM-VEC and SPFresh 27.0 GB. Sampling ratio 1.0 → 6.81 ms / 89.2% recall; 0.8 → 4.90 ms / 85.1% — [arXiv HTML](https://arxiv.org/html/2505.17152v1)
- Caveat noted while reading: the abstract's "no global rebuild" sits uneasily with the periodic global reordering pass; the "over 66.2%" memory reduction is not clearly derived from the tables (26.5 vs 76 GB ≈ 65%) — [arXiv HTML](https://arxiv.org/html/2505.17152v1)

**UBIS (2026)**
- Title: "Updatable Balanced Index for Stable Streaming Similarity Search over Large-Scale Fresh Vectors", Yuhui Lai, Shixun Huang, Sheng Wang; arXiv:2602.00563 (31 Jan 2026). The search summary says it is accepted to IEEE BigData 2025; the arXiv page itself does not name a venue — [arXiv abstract](https://arxiv.org/abs/2602.00563v1); [arXiv HTML](https://arxiv.org/html/2602.00563v1)
- Mechanism: builds on SPANN and reuses SPFresh's LIRE split/merge/reassign, persisted with RocksDB. Replaces SPFresh's posting-level locks with a "Posting Recorder" (per-posting 2-bit status normal/splitting/merging/deleted, 16-bit version weight, pointers to new postings, CAS-updated) and a high-concurrency controller; vectors arriving during split/merge go to a vector cache. A "Balance Detector" keeps posting lengths in memory and checks periodically; BalanceSplit runs k=2 k-means and, if the smaller side falls below a balance factor (default 0.15), moves its vectors to a nearer posting or the larger sub-posting — [arXiv HTML](https://arxiv.org/html/2602.00563v1)
- Baselines FreshDiskANN and SPFresh; datasets Argoverse 2 (~1M×256 with real timestamps), SIFT1M, Cohere1M (768-d), GloVe1M. Full-update Recall10@10 / TPS: Argoverse 2 — UBIS 0.679 / 595.4, SPFresh 0.583 / 325.5, FreshDiskANN 0.348 / 319.1; SIFT1M — UBIS 0.906 / 627.5, SPFresh 0.812 / 517.5, FreshDiskANN 0.469 / 457.0. Abstract: "up to 77% higher search accuracy and 45% higher update throughput on average" (body wording and abstract wording differ) — [arXiv HTML](https://arxiv.org/html/2602.00563v1)

**In-place graph-update line (for comparison with partition-based work)**
- IP-DiskANN, "In-place Updates of a Graph Index for Streaming Approximate Nearest Neighbor Search" (arXiv:2502.13826, Feb 2025): described as "the first algorithm to avoid batch consolidation by efficiently processing each insertion and deletion in-place"; motivation: the graph is singly linked so "there is no fast way to find in-neighbors of a deleted vertex" — [arXiv](https://arxiv.org/abs/2502.13826v1)
- "Enhancing HNSW Index for Real-Time Updates: Addressing Unreachable Points and Performance Degradation" (Wentao Xiao, Yueyang Zhan, Rui Xi, Mengshu Hou, Jianming Liao; arXiv:2407.07871, v2 Jul 2024): identifies the "unreachable points phenomenon" where HNSW updates leave points unreachable by search; proposes MN-RU to "suppress the growth rate of unreachable points"; abstract page gives no numbers — [arXiv](https://arxiv.org/abs/2407.07871)
- Topology-aware localized updates (arXiv:2503.00402, Mar 2025): batch updates raise throughput but "a large batch size leads to significant degradation in search accuracy" — [arXiv](https://arxiv.org/abs/2503.00402v2)
- DGAI (arXiv:2510.25401, Oct 2025, v4 Apr 2026): on disk graph indexes "I/O operations dominate the update latency, accounting for 57.9–80.5% of the total update time", attributed to coupled vector+neighbor storage; proposes a decoupled layout — [arXiv HTML](https://arxiv.org/html/2510.25401v4)
- MERIT, "Efficient In-Place Deletion for Dynamic Graph-Based Approximate Nearest Neighbor Indexes" (arXiv:2607.29173, 2026): in-place vertex removal during the stream instead of deferral to rebuild/compaction — [arXiv PDF](https://arxiv.org/pdf/2607.29173)
- "Disk-Resident Graph ANN Search: An Experimental Evaluation" (arXiv:2603.01779, Mar 2026) classifies methods as in-place vs out-of-place updates and notes in-place designs are "sensitive to random I/O and write interference" — [arXiv PDF](https://arxiv.org/pdf/2603.01779)
- Starling (SIGMOD 2024, arXiv:2401.02116) is a disk-resident graph index "on data segment" with in-memory navigation graph + reordered disk graph; reports 33M 128-d vectors in a 2 GB RAM / 10 GB disk segment with <1 ms latency at >0.9 recall@10 and 43.9× throughput over prior methods; the retrieved material covers queries/layout only, not updates — [arXiv](https://arxiv.org/abs/2401.02116v2)
- MicroNN ("MicroNN: An On-device Disk-resident Updatable Vector Database", arXiv:2504.05573) uses a threshold of 50% growth in average partition size to trigger a full rebuild (per the search summary) — [arXiv PDF](https://arxiv.org/pdf/2504.05573)
- OceanBase docs state IVF/IVF_PQ indexes "do not support incremental refresh" and recommend full rebuild for IVF indexes — [OceanBase docs](https://www.oceanbase.ai/docs/vector-index-monitor-and-maintain)

### Inferences
- The partition-based line (LIRE → Ada-IVF → UBIS) converges on "local re-clustering of a bounded neighborhood" plus some policy for *which* partitions to touch; Ada-IVF's read-temperature idea is the main novelty beyond LIRE, and UBIS's contribution is concurrency control plus balance-aware splits.
- Graph-based systems keep winning on recall at the same scale (LSM-VEC, UBIS tables show FreshDiskANN worse but DiskANN better than SPFresh on recall), while partition-based systems win on memory and update predictability; no 2025–2026 paper found claims both.
- Almost all of these are single-node, ≤100M evaluations; the only billion-scale dynamic numbers remain SPFresh's own stress test.

### Gaps
- No sources found for "DiskANN++", "AisLSM", "Vexless", "DEG/dynamic edge" indexes, or RaBitQ-based dynamic indexes; they may exist under different names or be too recent to be indexed.
- MUVERA was not researched because it concerns multi-vector retrieval, not updates.
- Venue of UBIS (BigData 2025 vs. preprint) is unconfirmed from the primary page; Ada-IVF's peer-review status is unknown.
- CANDY's per-algorithm numbers were not readable from the abstract page (see KQ5).

## KQ3. How production vector databases handle online updates (mechanisms, numbers, limitations)

### Takeaway
Every production system surveyed avoids mutating a large on-disk ANN index in place except Vespa (one mutable HNSW per field per node) and Redis (hnswlib-derived in-place updates). The rest use some combination of (1) a mutable write buffer searched by brute force (Milvus growing segments, Chroma brute-force buffer, Pinecone memtable, LanceDB unindexed rows), (2) immutable indexed segments plus tombstones/delete bitsets, and (3) background compaction/merge that rebuilds the index copy (Lucene/Elasticsearch, Milvus, Qdrant, Weaviate tombstone cleanup, LanceDB optimize). Published freshness numbers are sparse; most docs state only "eventually consistent" or "short delay".

### Cited Findings

**Milvus (vendor docs + design wiki + survey)**
- Write path: proxy splits writes into shard packages mapped to vchannels/pchannels bound to a Streaming Node; the Streaming Node assigns a TSO timestamp and writes to the WAL; "Once committed to the WAL, data is durable"; the Streaming Node asynchronously cuts committed WAL entries into segments — [Milvus docs: Data Processing](https://milvus.io/docs/data_processing.md)
- Growing vs sealed: "A growing segment holds data not yet persisted to object storage. A sealed segment holds data fully persisted to object storage and is immutable." Flush converts growing → sealed; Data Nodes build indexes per segment "so updates don't force frequent rebuilds"; at query time each Streaming Node "searches its local growing data and contacts Query Nodes for historical results" — [Milvus docs: Data Processing](https://milvus.io/docs/data_processing.md)
- Deletes are soft: Milvus storage is append-only, so a delete sets a flag on the entity; the Knowhere engine supports searching with a bitset marking deleted entities (original delete design doc) — [Milvus design wiki (search summary)](https://lf-aidata.atlassian.net/wiki/x/UQrL)
- MEP 16 (Compaction): compaction merges small segments and removes deleted rows; one trigger rule is deleted rows / total rows ≥ a configured ratio — [MEP 16 -- Compaction](https://wiki.lfai.foundation/display/MIL/MEP+16+--+Compaction)
- Segment levels (third-party blog, 2026): Legacy, L0 (channel-level delta for deletes/updates), L1 (normal data), L2 (extra distribution info); a delete first lands in an L0 delta segment and later compaction folds delete marks into L1/L2 segments; L0 must be compacted regularly or "bloom-filter bloat, query latency spikes, and write stalls occur"; default scheduling runs L0 compactions first — [besthub.dev: Four States a Milvus Delete Passes Through](https://www.besthub.dev/articles/four-states-a-milvus-delete-passes-through-uncovering-the-most-complex-operation-87d7b3846281); [besthub.dev: Why deleting 1M vectors doesn't shrink disk](https://www.besthub.dev/articles/why-deleting-1-million-vectors-in-milvus-doesn-t-shrink-disk-space-a-deep-dive-into-11-compactiontypes-43b5b2f193f3)
- Clustering compaction (vendor doc): redistributes entities across segments by a scalar clustering key and builds PartitionStats for segment pruning; disabled by default (`enable: false`, `autoEnable: false`, `newDataSizeThreshold: 512m`, `timeout: 7200`); Zilliz internal benchmark on 20M×768-d LAION shows up to 25× QPS with a specific key filter — [Milvus docs: Clustering Compaction](https://milvus.io/docs/clustering-compaction.md)
- An academic survey on write-read decoupling describes Milvus growing segments as in-memory and "brute-force searchable immediately after WAL acknowledgment" (arXiv:2605.01260, 2026) — [arXiv PDF](https://arxiv.org/pdf/2605.01260)

**Qdrant (vendor docs)**
- Optimization is per segment and the segment being rebuilt stays readable: "Changed data is placed in the copy-on-write segment, which has priority for retrieval and subsequent updates" — [Qdrant docs: Optimizer](https://qdrant.tech/documentation/concepts/optimizer/)
- Vacuum Optimizer: deletes are marked rather than removed immediately; vacuum later permanently removes them. Doc example config: `deleted_threshold: 0.2`, `vacuum_min_vector_number: 1000` — [Qdrant docs: Optimizer](https://qdrant.tech/documentation/concepts/optimizer/)
- Merge Optimizer: targets `default_segment_number` (0 = auto by CPU count), may merge the three smallest segments; `max_segment_size_kb` caps segment size to bound indexing time (auto by CPU count if unset) — [Qdrant docs: Optimizer](https://qdrant.tech/documentation/concepts/optimizer/)
- Indexing Optimizer: builds HNSW / memmap once a segment exceeds `indexing_threshold_kb` (doc example 10000); memmap storage "is disabled by default" — [Qdrant docs: Optimizer](https://qdrant.tech/documentation/concepts/optimizer/)
- Embedding-model migration tutorial: create a second collection, dual-write, background re-embed via scroll, then switch; with named vectors on ≥1.18 an in-collection option is "easier, faster, and uses fewer resources" — [Qdrant docs: Migrate to a New Embedding Model](https://qdrant.tech/documentation/tutorials-operations/embedding-model-migration/)

**Weaviate (vendor docs + forum)**
- HNSW deletes: "Prior to cleanup, objects are marked as deleted, but they are still connected to the HNSW graph"; a background cleanup "rebuilds the graph after deletes and updates", reassigning edges and permanently removing objects — [Weaviate docs: Vector index](https://docs.weaviate.io/weaviate/concepts/vector-index)
- Async indexing: `ASYNC_INDEXING=true` queues all HNSW/HFresh index operations (batch and single imports, deletes, updates); trade-off is "a short delay before new objects are searchable through HNSW"; queue is persistent on disk since v1.28 (in-memory, batch-only in v1.22–1.27) — [Weaviate docs: Vector index](https://docs.weaviate.io/weaviate/concepts/vector-index)
- Dynamic index (experimental since v1.25, needs async indexing): flat → HNSW at a default 10,000-object threshold; one-way switch — [Weaviate docs: Vector index](https://docs.weaviate.io/weaviate/concepts/vector-index)
- HNSW memory estimates: ~2–12 GB per 1M vectors for vectors plus ~200 MB per 1M for edges (10 B × 20 connections) — [Weaviate docs: Vector index](https://docs.weaviate.io/weaviate/concepts/vector-index)
- Env-var defaults: `ASYNC_INDEXING` = `false`; `TOMBSTONE_DELETION_CONCURRENCY` = "Half of the available cores"; `TOMBSTONE_DELETION_MAX_PER_CYCLE` = "none"; `TOMBSTONE_DELETION_MIN_PER_CYCLE` = `0` — [Weaviate docs: Environment variables](https://docs.weaviate.io/deploy/configuration/env-vars)
- Field reports: on v1.28.2 with MIN=30000/MAX=300000, a cleanup of 162,375 tombstones on one shard took ~45 s followed by "HNSW condensing", yet disk usage did not drop after deleting ~600K vectors; a maintainer explained storage is reclaimed only after LSM compaction runs multiple times — [Weaviate forum: Disk usage and tombstone cleanup](https://forum.weaviate.io/t/disk-usage-for-weaviate-and-tombstone-cleanup/9870); another user saw ~500% CPU during "tombstone_cleanup_begin" on a 1.2M-object instance — [Weaviate forum: CPU during tombstone cleanup](https://forum.weaviate.io/t/weaviate-using-tons-of-cpu-during-tombstone-cleanup-begin/7290)

**Vespa (vendor docs/blog)**
- "CRUD (Create, Add, Update, Remove) vectors in the index in true real time"; one mutable HNSW graph per tensor field per content node "so queries don't have to search multiple graph segments"; "The costly part when performing real time changes to the HNSW graph is distance calculations while searching the graph layers to find which links to change", done by multiple indexing threads — [Vespa docs: Approximate NN using HNSW](https://docs.vespa.ai/en/querying/approximate-nn-hnsw.html)
- Feed/query trade-off: higher `max-links-per-node` and `neighbors-to-explore-at-insert` raise recall (~70% vs ~92% recall@10 for the two example configs) but reduce indexing throughput and raise memory — [Vespa docs: Approximate NN using HNSW](https://docs.vespa.ai/en/querying/approximate-nn-hnsw.html)
- "Reindexing an HNSW-index is multithreaded since Vespa 7.436.31", making e.g. distance-function changes "as fast as regular multi-threaded updates to HNSW index" — [Vespa blog, Sept 2021 product update](https://blog.vespa.ai/vespa-product-updates-september-2021/)

**pgvector (open-source README)**
- Standard SQL INSERT/UPDATE/DELETE/`ON CONFLICT` upserts; "you will see different results for queries after adding an approximate index"; "There may be even less results due to dead tuples or filtering conditions"; recommendation: `REINDEX INDEX CONCURRENTLY` then `VACUUM` because vacuuming HNSW is slow; WAL-logged (replication/PITR) — [pgvector README](https://github.com/pgvector/pgvector)
- IVFFlat: create the index after loading data (`lists = rows/1000` up to 1M, `sqrt(rows)` above); too little data at build → fewer results, "Drop the index until the table has more data"; HNSW can be built on an empty table (no training). Iterative scans (`hnsw.iterative_scan`, `hnsw.max_scan_tuples` default 20,000) mitigate filtered-query result loss — [pgvector README](https://github.com/pgvector/pgvector)

**Elasticsearch / Lucene (vendor engineering blog)**
- Immutable segments; "an update doesn't modify a document in place": new segments are written and the old version flagged deleted; vectors are buffered in memory then serialized into segments; HNSW search per segment must consult live docs to exclude deleted ones; top-k merged across segments — [Elastic Search Labs: Vector search rationale](https://www.elastic.co/search-labs/blog/vector-search-elasticsearch-rationale)
- Merges (~10 input segments) do not merge graphs: "Lucene currently creates a copy of the HNSW graph from the largest input segment that doesn't have deletes" and inserts the other segments' vectors into it; listed as index-time overhead. Pros listed: lock-free search during concurrent indexing, add/remove/update "at any time without retraining", point-in-time consistency with other fields, incremental snapshots. Cons: merge cost, multi-segment top-k overhead, RAM scaling with vectors — [Elastic Search Labs: Vector search rationale](https://www.elastic.co/search-labs/blog/vector-search-elasticsearch-rationale)

**Pinecone (vendor blog/docs)**
- Log-structured design: writes go to an in-memory memtable; on size threshold it flushes to blob storage as an "L0 slab" indexed with fast methods (scalar quantization / random projections); when the slab count hits a threshold, compaction merges smaller slabs into larger ones and builds partition- or graph-based indexes out of band; slab index portions cached on local SSD/memory; re-caching evicted raw data ~250 ms — [Pinecone blog: Evolving Pinecone for knowledgeable AI](https://www.pinecone.io/blog/evolving-pinecone-for-knowledgeable-ai/)
- Freshness: reads routed through the memtable on the index builder (which holds the latest manifest) and fanned to executors over all valid slabs; an eventually consistent mode sends queries directly to executors (faster, "may be slightly stale"); strongly consistent reads promised "in the coming months"; no numeric freshness delay stated — [Pinecone blog: Evolving Pinecone](https://www.pinecone.io/blog/evolving-pinecone-for-knowledgeable-ai/)
- Docs: Pinecone is "eventually consistent"; serverless indexes expose `x-pinecone-request-lsn` on writes and `x-pinecone-max-indexed-lsn` on queries (per namespace) so clients can verify a write is visible; LSN check only for serverless via the Database API — [Pinecone docs: Check data freshness](https://docs.pinecone.io/guides/index-data/check-data-freshness)
- Earlier "freshness layer" description (third-party Medium post, 2024-era serverless): index builder runs ~10 min on average, so unindexed data is served from an in-memory freshness layer "to ensure the data is available to be read in seconds and not minutes" — [Medium (secondary)](https://abhtri.medium.com/pinecone-getting-started-with-vector-database-f4387afbec88)

**Redis (vendor docs + third party)**
- Redis Query Engine: "Realtime vector indexing" with FLAT and HNSW ("Modified version of nmslib/hnswlib") and "Realtime vector update/delete, triggering an update of the index" — [Redis docs: Vectors](https://redis.io/docs/interact/search-and-query/search/vectors/)
- Redis 8 vector sets: a third-party tutorial says `VREM` removes the member's vector, attributes and HNSW graph edges and the member is immediately excluded from `VSIM` — [OneUptime (secondary)](https://oneuptime.com/blog/post/2026-03-31-redis-vrem-vector-sets-remove-vectors/view)

**LanceDB (vendor docs)**
- "LanceDB doesn't immediately update the index until a reindex operation is complete"; new data "will always be included in query results, but queries on tables with unindexed data will fall back to slower search methods for the new parts of the table"; `index_stats()` reports indexed/unindexed row counts; OSS: `optimize()` runs compaction, cleanup and index update; Cloud/Enterprise auto-triggers index builds and `fast_search=True` searches only indexed data — [LanceDB docs: Reindexing](https://docs.lancedb.com/indexing/reindexing)

**Chroma (vendor docs + cookbook)**
- Distributed: gateway → Log (WAL; "All writes are recorded here before acknowledgment"); a Compactor periodically pulls from the WAL and builds new index versions (vector, full-text, metadata) written to object storage and registered in the system DB; SSD caching offsets object-storage latency; Query Executor serves consistent results by combining indexed state with recent WAL state — [Chroma docs: Distributed architecture](https://docs.trychroma.com/reference/architecture/distributed)
- Single-node (~v0.6.3): per collection "two binary indices: Bruteforce (in-memory, fast) and HNSW lib (persisted to disk...)"; the brute-force index "serves the role of a buffer that holds the uncommitted-to-HNSW persisted portion of the WAL"; `hnsw:batch_size` forces BF vectors into HNSW and `hnsw:sync_threshold` forces an on-disk dump — [Chroma cookbook: WAL](https://cookbook.chromadb.dev/core/advanced/wal)

### Inferences
- "Deleted vectors stay in the graph until segment merge/cleanup" is literally true for Lucene/Elasticsearch (live-docs filter until merge), Weaviate (tombstones until cleanup cycle), Milvus (bitset until compaction) and Qdrant (deleted flag until vacuum); only Vespa and Redis/hnswlib claim immediate graph modification. This has a direct recall/latency cost documented by BigANN'23 for lazy deletes (KQ5).
- The dominant freshness design is "query the write buffer by brute force + query sealed index + merge", which keeps freshness near-immediate but makes query cost grow with buffer size (LanceDB and Chroma docs say so explicitly). Systems differ mainly in how fast the buffer is folded in (Milvus flush, Chroma batch_size, Pinecone L0 slab, Lucene refresh).
- Only Pinecone exposes a user-checkable freshness primitive (LSN headers); all others document behavior qualitatively.

### Gaps
- Qdrant: the optimizer page gives thresholds as *example* config, not confirmed defaults (`deleted_threshold`, `vacuum_min_vector_number`, `indexing_threshold_kb`); appendable vs. non-appendable segment terminology appears in other Qdrant docs (storage page) that were not fetched.
- Milvus official docs fetched do not describe bitset/delta-log/L0 internals; those come from a 2021–2022 design wiki and a 2026 third-party blog. `milvus.io/docs/compaction.md` returned 404.
- Vespa: no doc or blog found that explains how removes are handled inside the mutable graph (edge repair vs. tombstone).
- Redis: no official statement on whether RediSearch HNSW deletes are soft (mark) or hard (edge repair).
- Weaviate: no official page found for the cleanup interval setting (`cleanupIntervalSeconds`) or its default.
- No published freshness latency numbers (write→visible) from any vendor except the secondary "seconds not minutes" claim for Pinecone.

## KQ4. Common architectural patterns and their freshness-vs-query-cost trade-offs

### Takeaway
Four patterns recur: (1) LSM-style immutable segments + background merge/compaction (Lucene/ES, Milvus, Qdrant, Pinecone slabs, Chroma distributed, LSM-VEC); (2) mutable write buffer searched by brute force over fresh data (Milvus growing segments, Chroma BF buffer, Pinecone memtable, LanceDB unindexed rows, FreshDiskANN's in-memory fresh index); (3) tombstone/bitset + periodic cleanup (Weaviate, Milvus, Qdrant, Lucene live docs, FreshDiskANN lazy deletes, SPFresh version map); (4) copy-on-write / in-place local repair (Qdrant COW segments during optimization, SPFresh LIRE, Vespa and hnswlib in-place graph edits, IP-DiskANN). Research consistently reports that the "secondary index + periodic global rebuild" pattern produces latency/recall oscillation and large resource peaks, which is exactly what SPFresh/LIRE and Pinecone's slab compaction aim to smooth.

### Cited Findings
- Problem statement for the rebuild pattern: existing systems "keep a secondary index for updates and periodically rebuild the main index", causing "high fluctuations of search latency and accuracy"; SPFresh's DiskANN baseline P99.9 exceeded 20 ms during global rebuilds vs. ~4 ms for in-place LIRE, and needed +60 GB for streaming merge and +15 GB for a second index — [SPFresh arXiv](https://arxiv.org/html/2410.14452v1)
- UBIS frames the two camps: buffer-based methods "are resource-intensive and inefficient due to the global rebuilding processes", while in-place methods "suffer from performance degradation because of update congestion and imbalanced distribution" — [UBIS arXiv](https://arxiv.org/abs/2602.00563v1)
- LSM segments + merge (Lucene): merges "create a copy of the HNSW graph from the largest input segment that doesn't have deletes" and re-insert the others (index-time overhead); search pays multi-segment top-k merge; benefit is lock-free concurrent search and no retraining — [Elastic Search Labs](https://www.elastic.co/search-labs/blog/vector-search-elasticsearch-rationale)
- LSM-structured graph (LSM-VEC): proximity graph edges spread across LSM levels enabling out-of-place updates; DiskANN memory grew 25→76 GB under insert-only vs. 22.4→26.5 GB for LSM-VEC — [LSM-VEC arXiv](https://arxiv.org/html/2505.17152v1)
- Memtable + L0 slabs + compaction (Pinecone): fast-indexed L0 slabs become queryable quickly; expensive partition/graph indexes built only at compaction; freshness by routing reads through the memtable — [Pinecone blog](https://www.pinecone.io/blog/evolving-pinecone-for-knowledgeable-ai/)
- Brute-force buffer cost: LanceDB warns "The more data that you add without reindexing, the impact on latency (due to exhaustive search) can be noticeable" — [LanceDB docs](https://docs.lancedb.com/indexing/reindexing); Chroma's BF index "serves the role of a buffer that holds the uncommitted-to-HNSW persisted portion of the WAL" — [Chroma cookbook](https://cookbook.chromadb.dev/core/advanced/wal)
- Tombstone cost: BigANN'23 notes that with lazy deletes "accumulating many deletes lowers index recall, even after normalizing for search parameters", and consolidation restores it — [BigANN'23 results](https://arxiv.org/html/2409.17424v1); Weaviate cleanup of 162K tombstones took ~45 s and disk is not reclaimed until LSM compaction — [Weaviate forum](https://forum.weaviate.io/t/disk-usage-for-weaviate-and-tombstone-cleanup/9870)
- Copy-on-write during rebuild (Qdrant): "Changed data is placed in the copy-on-write segment, which has priority for retrieval and subsequent updates" — [Qdrant docs](https://qdrant.tech/documentation/concepts/optimizer/)
- In-place graph edits: Vespa keeps one mutable graph per field, cost dominated by distance computations for link changes — [Vespa docs](https://docs.vespa.ai/en/querying/approximate-nn-hnsw.html); HNSW updates can make points unreachable ("unreachable points phenomenon") — [arXiv 2407.07871](https://arxiv.org/abs/2407.07871); in-place disk-graph designs are "sensitive to random I/O and write interference" — [arXiv 2603.01779](https://arxiv.org/pdf/2603.01779)
- Batch-size trade-off for graph updates: larger update batches raise throughput but "a large batch size leads to significant degradation in search accuracy" — [arXiv 2503.00402](https://arxiv.org/abs/2503.00402v2)
- I/O share of disk-graph update latency: 57.9–80.5% of update time is I/O when vectors and neighbor lists are stored together — [DGAI arXiv](https://arxiv.org/html/2510.25401v4)
- Write-read decoupling as a general pattern: a 2026 survey ("Write-Read Decoupling in Modern Large-Scale Search Engines", arXiv:2605.01260) describes Milvus growing segments as brute-force searchable immediately after WAL ack, and Chroma's wal3 + segment indexes — [arXiv PDF](https://arxiv.org/pdf/2605.01260)

### Inferences
- Trade-off summary: buffer+brute-force gives the best freshness (visible at WAL ack) but query cost rises linearly with buffer size; tombstones give O(1) deletes but recall and latency degrade until cleanup; segment-merge gives predictable immutability and snapshots but periodic CPU/memory spikes and graph rebuild cost; in-place local repair (LIRE, Vespa, IP-DiskANN) gives smooth latency but needs careful concurrency control and is sensitive to random I/O on disk.
- Partition-based indexes are structurally friendlier to in-place updates than graphs because membership is decided by centroid distance (a local, cheap test), whereas graph deletes require finding in-neighbors; this is why SPFresh/Ada-IVF/UBIS all choose IVF/SPANN as the substrate.

### Gaps
- No single peer-reviewed study quantifies all four patterns on the same workload; the comparisons above are assembled from separate papers and vendor docs.

## KQ5. Benchmarks that measure update performance of vector DBs/indexes and what they find

### Takeaway
BigANN NeurIPS'23 streaming track (peer-reviewed results paper) is the main academic benchmark: 10M MSTuring, 4:4:1 insert:delete:search batches, 1 h / 8 GB limits; corrected winner PyANNS at 0.8865 average recall vs. DiskANN baseline 0.7218, and the organizers document recall loss from accumulated lazy deletes. CANDY (2024) finds simpler AKNN baselines often beat complex ones under continuous ingestion. VectorDBBench's streaming case (vendor-maintained) measures QPS/recall/P99 during a fixed-rate insert stream and reports Pinecone outperforming Elasticsearch during ingestion; a 2026 OceanBase test reports concurrent/serial P99 jitter of 1.1×–10.3× across engines.

### Cited Findings
- BigANN'23 results paper: "Results of the Big ANN: NeurIPS'23 competition", arXiv:2409.17424 (Sept 2024), later a NeurIPS 2025 Datasets & Benchmarks paper — [arXiv HTML](https://arxiv.org/html/2409.17424v1); [NeurIPS 2025 proceedings](https://papers.nips.cc/paper_files/paper/2025/hash/63092d79154adebd7305dfd498cbff70-Abstract-Datasets_and_Benchmarks_Track.html)
- Streaming track setup: 10M-vector slice of MS Turing; index starts empty; insert/delete/search batches at ~4:4:1; final runbook 1,280 batches over 5 rounds (data clustered into 64 clusters; each round: insert cluster sample → search → delete a fraction → search); 1-hour limit for the whole runbook and 8 GB memory; final runbook differed from the released one to discourage overfitting — [arXiv HTML](https://arxiv.org/html/2409.17424v1)
- Baseline: DiskANN streaming in-memory index using FreshDiskANN ideas — eager insertions, lazy deletions, consolidation that frees deleted vectors and repairs the graph — [arXiv HTML](https://arxiv.org/html/2409.17424v1)
- Results (average recall, originally reported → corrected): puck 0.985 → 0.0921; hwtl_sdu_anns_stream 0.9674 → 0.7693; pyanns 0.9597 → 0.8865; diskann baseline 0.883 → 0.7218; cufe 0.8189 → 0.6481. Puck was first declared winner; a caching error measured recall only at the first snapshot instead of averaging over the runbook; after correction PyANNS won — [arXiv HTML](https://arxiv.org/html/2409.17424v1)
- Deletion finding: "accumulating many deletes lowers index recall, even after normalizing for search parameters"; consolidation improves recall; a more detailed DiskANN/HNSW analysis is in the framework notes — [arXiv HTML](https://arxiv.org/html/2409.17424v1)
- CANDY: "CANDY: A Benchmark for Continuous Approximate Nearest Neighbor Search with Dynamic Data Ingestion", Xianzhi Zeng, Zhuoyan Wu, Xinjing Hu, Xuanhua Shi, Shixuan Sun, Shuhao Zhang; arXiv:2406.19651 (June 2024); code at github.com/intellistream/candy; key finding: "simpler AKNN baselines often surpass more complex alternatives in terms of recall and latency"; also examines micro-batching and distribution-shift effects — [arXiv abstract](https://arxiv.org/abs/2406.19651)
- Related: "Approximate Nearest Neighbour Search on Dynamic Datasets: An Investigation" (arXiv:2404.19284, 2024) — [arXiv PDF](https://arxiv.org/pdf/2404.19284v2); CANDOR-Bench (SIGMOD 2026, per a secondary index) extends Big-ANN with high-rate ingestion, drift/modality shift, noise and concurrent query-update execution — [awesomepapers.io (secondary)](https://awesomepapers.io/similarity-search/papers/zeng2024candy)
- VectorDBBench (Zilliz-maintained): `StreamingPerformanceCase` sustains writes at a fixed rate (e.g., 500 rows/s across 5 processes) with searches triggered after every 10% of ingestion, alternating serial/concurrent; records P99, sustained QPS and recall; optional "optimize" step compares before/after index optimization; capacity test inserts until the DB rejects >10 requests — [Zilliz docs: VectorDBBench](https://docs.zilliz.com/docs/perf-benchmark-vectordb); [VDBBench 1.0 announcement](https://zilliz.com/blog/vdbbench-1-0-benchmarking-with-your-real-world-production-workloads)
- VDBBench 1.0 (vendor blog, Cohere 10M at 500 rows/s): "Pinecone maintained higher QPS and recall throughout the write cycle compared to Elasticsearch", which "showed more erratic behavior during active ingestion phases" (search-summary wording; the page body did not load on fetch) — [VDBBench 1.0 announcement](https://zilliz.com/blog/vdbbench-1-0-benchmarking-with-your-real-world-production-workloads)
- OceanBase (competing vendor, June 2026): streaming test on Cohere-10M across seekdb, Elasticsearch, Milvus, Qdrant, Chroma; concurrent-P99 / serial-P99 jitter ranged 1.1× to 10.3× across six engines on identical hardware — [OceanBase blog](https://en.oceanbase.com/blog/streaming-workload-benchmark-5-vector-databases-compared)
- benchANT (2025) used a VectorDBBench fork to compare Zilliz, Pinecone and SingleStore on 10M Cohere at two cluster sizes — [benchANT](https://benchant.com/blog/single-store-vector-vs-pinecone-zilliz-2025)
- Survey: "Survey of Vector Database Management Systems", James Jie Pan, Jianguo Wang, Guoliang Li, The VLDB Journal 33:1591–1615 (2024), DOI 10.1007/s00778-024-00864-x; arXiv:2310.14021 — [arXiv](https://arxiv.org/abs/2310.14021v1); [PDF (Tsinghua)](https://dbgroup.cs.tsinghua.edu.cn/ligl/papers/vldbj2024-vectordb.pdf). Companion tutorial "Vector Database Management Techniques and Systems", SIGMOD-Companion '24 — [tutorial PDF](https://www.cs.purdue.edu/homes/csjgwang/pubs/SIGMOD24_VecDB_Tutorial.pdf)
- Other survey: "A Comprehensive Survey on Vector Database: Storage and Retrieval Technique, Challenge" (arXiv:2310.11703) — [arXiv PDF](https://arxiv.org/pdf/2310.11703)

## KQ6. Embedding drift and re-embedding when the model changes

### Takeaway
Two distinct problems: content/query drift under a fixed model (DeDrift adapts IVF quantizers on-the-fly, up to 100× cheaper than rebuild) and model upgrades. For upgrades, vendor practice is blue-green dual collections with dual writes and background re-embedding (Qdrant tutorial); research (Drift-Adapter, 2025) learns a small map from new-model query embeddings into the old space so the existing ANN index keeps serving, recovering 95–99% of full re-embedding recall@10 at <10 µs query overhead, and explicitly warns that lazy partial re-embedding yields a "mixed-state index".

### Cited Findings
- DeDrift (ICCV 2023): content drift "degrades the search accuracy and efficiency" unless indexes are rebuilt frequently; DeDrift adapts quantizers on-the-fly and is "up to 100x faster than a full index reconstruction" — [arXiv 2308.02752](https://arxiv.org/pdf/2308.02752)
- Drift-Adapter: "Drift-Adapter: A Practical Approach to Near Zero-Downtime Embedding Model Upgrades in Vector Databases", Harshil Vejendla (Rutgers), arXiv:2509.23471 (27 Sep 2025); an ACL Anthology entry 2025.emnlp-main.805 exists per search results, so likely EMNLP 2025 main (unconfirmed from the arXiv page) — [arXiv HTML](https://arxiv.org/html/2509.23471v1); [ACL Anthology (preview)](https://preview.aclanthology.org/setup/2025.emnlp-main.805)
- Adapter types: Orthogonal Procrustes (closed-form SVD), Low-Rank Affine (r = 64), Residual MLP (1 hidden layer, 256 units, GELU), optional diagonal scaling; trained on 20,000 paired embeddings (2% of a 1M corpus); 5,000 pairs still give ARR > 0.97 on AG-News — [arXiv HTML](https://arxiv.org/html/2509.23471v1)
- Results: adapters recover 95–99% of full re-embedding recall@10 ("ARR"); AG-News R@10 ARR 0.974 (OP), 0.983 (LA), 0.992 (MLP); CLIP ViT-B/32 → ViT-L/14 image upgrade MLP 0.978; query overhead ~3.1 / 4.7 / 8.0 µs; ~0.5 GPU-hours adapter training vs. ~100 GPU-hours full re-index (1M AG-News) — [arXiv HTML](https://arxiv.org/html/2509.23471v1)
- Mixed-state index: lazy/background re-embedding "can lead to a mixed-state index (containing both old and new embeddings), complicating querying"; simulation refreshing 5% of 1M items hourly into a separate segment: hourly-retrained MLP adapter keeps ARR > 0.95 over 24 h, a fixed adapter trained at T=0 drops to ~0.83 — [arXiv HTML](https://arxiv.org/html/2509.23471v1)
- Qdrant migration tutorial (vendor): create a new collection for the new model, dual-write every upsert to both, background scroll re-embeds old points into the new collection, search stays on the old one until backfill completes; with named vectors on v1.18+ an in-place option is "easier, faster, and uses fewer resources" — [Qdrant docs](https://qdrant.tech/documentation/tutorials-operations/embedding-model-migration/)
- Open-source "aecp" tool: fits a linear map from ~2K calibration texts, reporting 87–91% retrieval retention on BEIR — [PyPI aecp](https://pypi.org/project/aecp/)
- Practitioner guidance (blogs): track `embedding_model`/`embedding_version` in metadata; expect 2× storage during migration; validate with a held-out query set and shadow 5–10% of traffic — [tianpan.co blog (secondary)](https://tianpan.co/blog/2026/07/05/retiring-an-embedding-model-reindex-without-downtime); [GSE blog (secondary)](https://www.gse.kz/en/blog/update-embeddings-without-downtime-blue-green)

### Inferences
- No system found supports true "migration without full re-index" of the stored vectors; the adapter line defers the re-index by transforming queries, and vendors do a full re-embed behind a dual-write facade. The adapter approach is only validated at 1M-item scale on text/image classification corpora.
- The Drift-Adapter hourly-retraining result implies that a migration with partial re-embedding needs continuous adapter maintenance, which is operationally similar to the index-maintenance loops in KQ2.

### Gaps
- Drift-Adapter's EMNLP 2025 acceptance is inferred from an ACL Anthology URL, not confirmed on the arXiv page.
- No vendor other than Qdrant was found to publish a formal embedding-model migration procedure; Milvus/Weaviate/Pinecone equivalents were not located in this session.
- No peer-reviewed work found that addresses re-indexing a *partition-based* (IVF/SPANN) index under model change specifically (DeDrift handles content drift, not model swaps).
