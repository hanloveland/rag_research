# RAG Knowledge Updates and Index Freshness at the Application Level (2023–2026)

Scope: how RAG systems *update* their knowledge (vs. static retrieval): streaming/online RAG, incremental GraphRAG, retrieval-based knowledge editing, freshness/evolving-corpus benchmarks, embedding-model migration, chunk-level change detection in LlamaIndex/LangChain, KV-cache RAG and CAG under document updates, and ANN-index insertion-visibility ("freshness") in vector DBs. Each item notes whether it is a peer-reviewed paper, an arXiv preprint, vendor documentation, or a third-party blog/benchmark. Research date: 2026-10-09.

---

## KQ1. Continually updated / streaming / dynamic / temporal RAG: what exists, how do they update the index, and what are the results?

### Takeaway
Work in this area splits into (a) systems that keep a vector index fresh under a document stream (Streaming RAG 2508.05662, LiveVectorLake 2601.05270), (b) temporal-graph RAG methods that add timestamped facts incrementally (TG-RAG 2510.13590, DyG-RAG 2507.13396), and (c) time-sensitive retrieval methods/benchmarks (MRAG/TempRAGEval, TA-RAG). Measured results are mostly on small custom setups; the most quantitative "update" evaluation is TG-RAG's ECT-QA protocol, which reports token cost of the update plus pre/post-update accuracy for GraphRAG, LightRAG, HippoRAG2 and TG-RAG.

### Cited Findings
- **"From Static to Dynamic: A Streaming RAG Approach to Real-time Knowledge Base"** (Yuzhou Zhu, arXiv:2508.05662, submitted 31 Jul 2025, cs.IR; preprint). Maintains a "compact prototype set" via multi-vector cosine screening, mini-batch clustering, and a counter-based heavy-hitter filter; an "incremental index upsert mechanism" refreshes prototypes without interrupting queries; proves an approximation bound linking retrieval quality to clustering variance. Reported: Recall@10 gains up to 3 points (p<0.01) on eight real-time streams, end-to-end latency <15 ms, throughput >900 documents/s under a 150 MB memory budget; on SQuAD with GPT-3.5 Turbo +3.2 EM / +2.8 F1. — [arXiv abs](https://arxiv.org/abs/2508.05662)
- **"LiveVectorLake: A Real-Time Versioned Knowledge Base Architecture for Streaming Vector Updates and Temporal Retrieval"** (Tarun Prajapati, arXiv:2601.05270, submitted 24 Nov 2025; preprint, sole author). Chunks identified by SHA-256 content hashes for deterministic change detection; dual-tier storage — hot tier Milvus/HNSW holds only *current* chunks, cold tier Delta Lake/Parquet keeps full version history; point-in-time queries routed via delta versioning with ACID consistency across tiers. Reported on a 100-document corpus versioned across five time points: only 10–15% of content re-processed per update vs 100% for full re-indexing; sub-100 ms current-knowledge retrieval; sub-2 s temporal queries across version history. — [arXiv abs](https://arxiv.org/abs/2601.05270)
- **"RAG Meets Temporal Graphs: Time-Sensitive Modeling and Retrieval for Evolving Knowledge" (TG-RAG)** (Han, Cheung, Wei, Yu, Wang, Zhu, Yang; arXiv:2510.13590, submitted 15 Oct 2025, cs.IR; preprint). Models the corpus as a bi-level temporal graph (temporal KG with timestamped relations + hierarchical time graph); incremental update extracts new temporal facts from incoming documents and merges them into the existing graph, storing identical facts at different times as distinct edges; the time hierarchy "generates reports only for new leaf time nodes and their ancestors." — [arXiv abs](https://arxiv.org/abs/2510.13590)
- TG-RAG's **ECT-QA** benchmark (earnings-call transcripts): base corpus 384 documents (2020–2023), new corpus 96 documents (2024) added as an incremental update; specific queries 656 base + 349 new (Table II total 1,005; text says 1,105 — inconsistent in paper), abstract queries 72 base + 28 new. Baselines: LLM-GT (oracle), NaiveRAG, QD-RAG, GraphRAG, LightRAG, HippoRAG2. **Update token cost (Table IV, prompt/completion)**: GraphRAG 30.0M/7.8M; LightRAG 4.6M/2.6M; HippoRAG2 0.8M/0.3M; TG-RAG 1.6M/2.0M. **Correct score before update → after update on base queries → on new queries**: GraphRAG 0.405→0.380→0.398; LightRAG 0.406→0.386→0.382; HippoRAG2 0.410→0.399→0.372; NaiveRAG 0.385→0.366→0.390; TG-RAG 0.599→0.587→0.617. Paper also argues most RAG evaluations assume one-time indexing, leaving update cost and retrieval stability unmeasured. — [arXiv HTML v1](https://arxiv.org/html/2510.13590v1)
- **"DyG-RAG: Dynamic Graph Retrieval-Augmented Generation with Event-Centric Reasoning"** (Sun, Yuan, He, Guan, Yuan, Fu, Li, Yu; arXiv:2507.13396, submitted 16 Jul 2025, cs.IR; preprint, code at RingBDStack/DyG-RAG). Parses documents into Dynamic Event Units (DEUs) with explicit temporal anchors, links DEUs sharing entities and close in time into an event graph, retrieves via joint semantic-temporal embeddings (Fourier-encoded time vectors), and uses Time Chain-of-Thought. Abstract claims significant accuracy/recall gains on three types of temporal QA; the abstract page gives no figures and does **not** describe incremental addition of new documents — "dynamic" here refers to temporal dynamics of knowledge, not online index updates. — [arXiv abs](https://arxiv.org/abs/2507.13396); [GitHub](https://github.com/RingBDStack/DyG-RAG)
- **"MRAG: A Modular Retrieval Framework for Time-Sensitive Question Answering"** (Findings of EMNLP 2025; peer-reviewed). Introduces **TempRAGEval**, built by repurposing TimeQA and SituatedQA with manual temporal perturbations and gold evidence on Wikipedia; finds "all existing retrieval methods struggle with these temporal reasoning-intensive questions" with remarkable retrieval degradation; MRAG decomposes the question into main content + temporal constraint (training-free). Motivating example: UK PM answer transition from Rishi Sunak to Keir Starmer in 2024. — [arXiv HTML](https://arxiv.org/html/2412.15540v2); [ACL Anthology](https://preview.aclanthology.org/dashboard/2025.findings-emnlp.167)
- **"Reading Between the Timelines: RAG for Answering Diachronic Questions" (TA-RAG / ADQAB)** (arXiv:2507.22917; preprint). Targets diachronic ("how did X change over time") questions with explicit temporal processing in retrieval, plus a benchmark. — [arXiv HTML](https://arxiv.org/html/2507.22917v1)
- **StreamingRAG (arXiv:2501.14101, Jan 2025)** and **Stream RAG (arXiv:2510.02044, Oct 2025)** both use "streaming" in a different sense: the former targets real-time multimodal video streams, the latter streaming tool use in spoken dialogue (reports QA accuracy from 11.1% to 34.2%); neither is about evolving document corpora. — [2501.14101](https://arxiv.org/abs/2501.14101); [2510.02044](https://arxiv.org/abs/2510.02044)
- **LiveRAG Challenge 2025** (arXiv:2506.22644) uses "dynamic test sets" — the *questions* evolve, not the corpus. — [arXiv](https://arxiv.org/html/2506.22644v1)
- **"ScalableRAG: High-Quality RAG at Zero Ingestion Cost"** (Hasson, Chakravarty, Thomas, Gogineni; arXiv:2607.25135, submitted 27 Jul 2026; preprint). Sidesteps the index-update problem by doing no ingestion at all (no vector DB in the zero-ingestion variant): a query-time workspace of document sets / value sets supports aggregative reasoning; a Limited-Ingestion variant uses a minimal vector DB with LLM calls capped regardless of corpus size. Reports average accuracy 7.36% above the next-best baseline across six corpora; does not discuss document updates. — [arXiv abs](https://arxiv.org/abs/2607.25135)

### Inferences
- The field lacks a common protocol; TG-RAG's ECT-QA "base vs. new split + pre/post-update accuracy + update token cost" is the most reusable template found. Its numbers show that graph-based methods lose 1–2.5 points on old queries after an update (GraphRAG 0.405→0.380), i.e., merging new material can slightly degrade retrieval of historical facts even without deletions.
- Several streaming/dynamic RAG papers are single-author preprints with small evaluations (LiveVectorLake: 100 docs); their latency/throughput claims should be treated as prototype-level.

### Gaps
- No peer-reviewed paper found that measures end-to-end "time from document arrival to correct answer" for a RAG stack under a continuous stream.
- Full-text quantitative tables for DyG-RAG and Streaming RAG (2508.05662) were not read; only abstracts.
- Reviews of arXiv:2509.19376 ("Freshness and the Limits of Heuristic Trend Detection in Temporal RAG") were found only via a third-party review site that questions its evaluation; not verified from the primary source.

## KQ2. Incremental / dynamic GraphRAG: how do systems add documents without re-running whole-corpus LLM extraction, and what are the cost savings?

### Takeaway
Microsoft GraphRAG ships a `graphrag update` command (methods `standard-update` / `fast-update`) that runs the pipeline on new documents only and merges by entity title, but as of Sept–Oct 2026 an open GitHub issue documents that community membership IDs are not remapped after the merge. LightRAG's incremental update is a union of node and edge sets after extracting from the new document only; the only head-to-head *update-cost* measurement found is TG-RAG's: GraphRAG 30.0M prompt tokens vs LightRAG 4.6M vs TG-RAG 1.6M for the same 96-document update.

### Cited Findings
- **Microsoft GraphRAG CLI (vendor docs)**: `graphrag update` "updates an existing knowledge graph index"; output goes to an `update_output` folder; `--method` accepts `standard`, `fast`, `standard-update`, `fast-update`; `--cache/--no-cache` toggles the LLM cache. The CLI page does not explain merge semantics, cost, or whether community reports are regenerated. — [GraphRAG CLI docs](https://microsoft.github.io/graphrag/cli/)
- GraphRAG indexing methods docs (vendor): "graph extraction is roughly 75% of indexing cost"; FastGraphRAG replaces LLM extraction with NLTK/spaCy noun-phrase entities and co-occurrence relationships; the page does not describe update modes. — [GraphRAG methods docs](https://microsoft.github.io/graphrag/index/methods/)
- **GraphRAG issue #2540** (opened 3 Sep 2026, last comment 2 Oct 2026; primary source on current `main` behavior): the update "runs the pipeline on only the new document," generating fresh IDs; entity merge keeps the existing row when titles match and returns a delta-ID→old-ID map; that map is applied **only** in the text-unit update step; relationship merge returns no map; delta communities are appended with `entity_ids`/`relationship_ids` unrewritten, so communities can reference IDs absent from `entities.parquet`/`relationships.parquet` (example: entity ALPHA never linked to its new community; `communities.size` = 2 but only one member resolvable). Reporter has a fix on a branch; not merged as of last comment; related earlier issues #2348, #2259, #1702, #1734. — [GitHub issue #2540](https://github.com/microsoft/graphrag/issues/2540)
- **GraphRAG issue #741** (design proposal, ~2024): intent was that unchanged documents skip re-chunking/extraction via cache, new entities try to join an existing community rather than triggering full Leiden re-run, and only communities whose membership changed get re-summarized. This is a proposal, not verified current behavior. — [GitHub issue #741](https://github.com/microsoft/graphrag/issues/741)
- Microsoft Tech Community PoC post (secondary, vendor blog): states GraphRAG "version 0.5.0 and above support incremental updates by maintaining consistent entity IDs." — [Tech Community post](https://techcommunity.microsoft.com/blog/azure-ai-foundry-blog/graphrag-end-to-end-poc/4361080)
- **LightRAG** ("LightRAG: Simple and Fast Retrieval-Augmented Generation", Guo, Xia, Yu, Ao, Huang; arXiv:2410.05779 v3 28 Apr 2025; GitHub README labels it "[EMNLP2025]"). Section 3.1 "Fast Adaptation to Incremental Knowledge Base": a new document goes through the same extraction; LightRAG "combines the new graph data with the original by taking the union of the node sets" and edge sets, keeping existing structure. Symbolic cost table: LightRAG update = T_extract + C_extract API calls on the new doc only, whereas GraphRAG must regenerate community reports — illustrated as ~1,399 communities × 2 × 5,000 tokens ≈ 14M tokens. Retrieval-phase cost (Legal dataset): GraphRAG ≈610K tokens (610 level-2 communities × ~1K tokens) and hundreds of API calls vs LightRAG <100 tokens and one API call. The paper gives no absolute indexing-token totals for LightRAG. — [arXiv abs](https://arxiv.org/abs/2410.05779); [arXiv HTML v3](https://arxiv.org/html/2410.05779v3)
- LightRAG GitHub (vendor/OSS docs): added "Document Deletion with automatic KG regeneration" (2025.08) that reuses the LLM cache from indexing to rebuild affected entities/relations; `kg_integrity_repair` tool audits recovery anchors so delete/retry can find orphaned contributions; entity/relation descriptions stop updating after `MAX_SOURCE_IDS_PER_RELATION` chunks unless `SOURCE_IDS_LIMIT_METHOD`/`FORCE_LLM_SUMMARY_ON_MERGE` are changed; README warns the embedding model must stay fixed because changing it "requires re-embedding all chunks, entities, and relations." Win rates vs GraphRAG: Agriculture 54.8/45.2, CS 52.0/48.0, Legal 52.8/47.2, Mix 49.6/50.4. — [LightRAG GitHub](https://github.com/HKUDS/LightRAG)
- **TG-RAG** update cost and accuracy (see KQ1): GraphRAG 30.0M/7.8M prompt/completion tokens, LightRAG 4.6M/2.6M, HippoRAG2 0.8M/0.3M, TG-RAG 1.6M/2.0M for adding 96 documents to a 384-document base. — [arXiv HTML](https://arxiv.org/html/2510.13590v1)
- **G2ConS, "Graph-Guided Concept Selection for Efficient Retrieval-Augmented Generation"** (arXiv:2510.24120; preprint): aims to cut LLM extraction cost and "includes an incremental update algorithm that dynamically integrates new data into the graph" (abstract-level only). — [arXiv HTML](https://arxiv.org/html/2510.24120v1)
- **DIAL-KG: "Schema-Free Incremental Knowledge Graph Construction via Dynamic Schema Induction and Evolution-Intent Assessment"** (arXiv:2603.20059; preprint): treats updates as transactions with consistency checks and "soft deprecation of outdated facts," so the graph evolves without full reconstruction (abstract-level only). — [arXiv HTML](https://arxiv.org/html/2603.20059v1)
- **"Towards Practical GraphRAG: Efficient Knowledge Graph Construction and Hybrid Retrieval at Scale"** (arXiv:2507.03226, revised Dec 2025; preprint): replaces LLM extraction with dependency parsing, reaching ~94% of LLM-extraction quality (per snippet) — cheaper extraction makes re-running on new docs affordable, but it is not described as incremental. — [arXiv abs](https://arxiv.org/abs/2507.03226)
- **M-RAG** (arXiv:2603.26667; preprint) reports 525 LLM invocations vs 5,507 for LightRAG on the same corpus by extracting document-level semantic markers once per document rather than per-chunk entities (full-indexing comparison, not incremental). — [arXiv PDF](https://arxiv.org/pdf/2603.26667)
- Third-party cost figures (unverified blogs): one GPT-4o-priced table reports GraphRAG indexing $51–$389 across four datasets vs $4–$37 for a RAPTOR/TREX approach; one blog claims entity extraction consumes 58% of indexing tokens. — [paperclipped.de blog](https://www.paperclipped.de/en/blog/graph-rag-production/)

### Inferences
- The structural reason community-based GraphRAG is expensive to update is that community reports are a *global* artifact: adding entities can change Leiden partitions and force re-summarization, whereas LightRAG/TG-RAG/HippoRAG2 store local artifacts (entity/relation descriptions, time-node reports) that can be unioned. TG-RAG's 30.0M vs 4.6M vs 1.6M prompt-token figures are consistent with this.
- Microsoft's incremental update is functional for text units and entities but, per issue #2540, community membership may silently reference dangling IDs after updates — a correctness risk for global (community-level) queries after `graphrag update`.

### Gaps
- No official Microsoft documentation page describing `standard-update`/`fast-update` merge semantics or measured cost savings was found; only CLI option names and GitHub issues.
- No measured absolute update cost (tokens or dollars) for Microsoft GraphRAG incremental mode from Microsoft itself.
- Incremental-update mechanics of G2ConS and DIAL-KG were read only from abstracts.

## KQ3. Benchmarks evaluating RAG freshness / corpus updates: what do they measure and what did they find about stale knowledge?

### Takeaway
Classic dynamic benchmarks (StreamingQA 2022, RealTime QA NeurIPS 2023, FreshQA 2023) established that retrieval over an updated store is the fastest way to incorporate new facts but that LLMs still return outdated answers when evidence is insufficient. 2025–2026 benchmarks move to versioned/evolving corpora (ECT-QA, DRAGON, Fiscal-FR-Bench, WikiBigEdit, FreshStack drift study) and show (i) static current-version RAG can be catastrophically wrong on version-sensitive questions (0% date-applicable retrieval in French tax law), (ii) RAG beats parameter-editing methods at scale, and (iii) benchmark rankings are fairly robust to a year of corpus drift (Kendall τ up to 0.978).

### Cited Findings
- **StreamingQA** ("StreamingQA: A Benchmark for Adaptation to New Knowledge over Time in Question Answering Models", Liška et al., ICML 2022, PMLR v162; peer-reviewed; arXiv:2205.11388). Questions asked on specific dates, answerable from 14 years of time-stamped news; evaluation is quarterly as new articles arrive. Findings: "adding new articles into the search space allows for rapid adaptation" for semi-parametric (retrieval) models with minimal forgetting; semi-parametric models with an outdated underlying LM underperform those with a retrained LM; parametric updates help most for high-frequency named entities. — [PMLR](https://proceedings.mlr.press/v162/liska22a/liska22a.pdf); [arXiv](https://arxiv.org/abs/2205.11388)
- **RealTime QA** ("RealTime QA: What's the Answer Right Now?", Kasai et al., NeurIPS 2023 Datasets & Benchmarks; peer-reviewed; arXiv:2207.13332). Weekly multiple-choice questions from CNN/The Week/USA Today news. Finding: GPT-3 "can often properly update its generation results, based on newly-retrieved documents," but "tends to return outdated answers when retrieved documents do not provide sufficient information." — [NeurIPS proceedings](https://papers.neurips.cc/paper_files/paper/2023/hash/9941624ef7f867a502732b5154d30cb7-Abstract-Datasets_and_Benchmarks.html); [arXiv](https://arxiv.org/pdf/2207.13332)
- **FreshLLMs / FreshQA** ("FreshLLMs: Refreshing Large Language Models with Search Engine Augmentation", Vu et al., arXiv:2310.03214, v1 Oct 2023, v2 Nov 2023; preprint as listed on arXiv). FreshQA has never-changing, slow-changing, fast-changing and false-premise questions; >50K human judgments; all models struggle with fast-changing knowledge and false premises regardless of size; FreshPrompt (few-shot prompting with up-to-date search results) "substantially boosts" performance and outperforms Self-Ask and Perplexity.AI; number and order of retrieved evidences affect correctness. — [arXiv abs](https://arxiv.org/abs/2310.03214)
- **EvolvingQA / "Carpe Diem: On the Evaluation of World Knowledge in Lifelong Language Models"** (Kim et al., NAACL 2024 per arXiv comments; arXiv:2311.08106). Temporally evolving QA benchmark on an evolving Wikipedia database, LLM-generated QA pairs based on knowledge changes; finding: continual-learning baselines "suffer from updating and removing outdated knowledge," attributed to small weight gradients; models particularly fail on numerical/temporal changes. — [arXiv abs](https://arxiv.org/abs/2311.08106)
- **WikiBigEdit** ("WikiBigEdit: Understanding the Limits of Lifelong Knowledge Editing in LLMs", ICML 2025; peer-reviewed; arXiv:2503.05683 v2 Sep 2025). 502,382 QA pairs (~6.9M tokens) from real Wikidata edits across 8 timesteps, Feb–Jul 2024 (per-timestep: 26,922; 29,835; 54,504; 43,443; 121,116; 101,728; 69,403; 55,431); ~82% of edits unsolved by base LLMs. **RAG performed best overall**, nearly tripling accuracy on training edits relative to editing methods at up to ~2× inference time (avg 78.64% on rephrased, 66.16% on persona questions); only ~10% of multi-hop samples retrieved both hops. ROME/R-ROME/MEMIT collapsed within the first few hundred updates; WISE avoided collapse but converged back to pre-edit levels within 10K updates; LoRA-FT competitive for ~100K updates then degraded; LoRA-Merge outperformed editing methods after ~100K edits. — [arXiv HTML](https://arxiv.org/html/2503.05683); [arXiv abs](https://arxiv.org/abs/2503.05683)
- **ECT-QA (TG-RAG)**: base/new corpus split with pre- and post-update accuracy and update token cost (numbers in KQ1/KQ2). — [arXiv HTML](https://arxiv.org/html/2510.13590v1)
- **DRAGON: Dynamic RAG Benchmark On News** (arXiv:2507.05713, first titled "DRAGOn: Designing RAG On Periodically Updated Corpus"; preprint; Russian-language). Regularly updated corpus of Russian news/public documents; questions auto-generated from a KG over the corpus in four types (simple, comparison, multi-hop, conditional); new versions mitigate leakage/contamination; leaderboard recomputes open-model metrics on each new version (e.g., v1.34.1, 600 questions, 3 Jul 2025); limited to Russian. — [arXiv HTML v3](https://arxiv.org/html/2507.05713v3); [leaderboard](https://ai-forever-rag-leaderboard.hf.space/)
- **Fiscal-FR-Bench / "Temporal Misgrounding in Legal RAG: A Versioned-Corpus Benchmark for French Tax Law"** (Cymbler, Guez, Fabre; arXiv:2608.09393, submitted 10 Aug 2026; accepted ICML 2026 AI4Law Workshop). Versioned corpus of 32,436 article-versions of the French tax code (1938–2031); 209 scored expert-reviewed questions across 33 articles; deterministic nugget scoring. Findings: parametric knowledge 3.0% mean strict accuracy across 11 models; **RAG over a static current-version corpus 2.7%**, retrieving the date-applicable version **0% of the time** while confidently citing a real but inapplicable version; an end-to-end retriever over a multi-version index reaches 98.3% (oracle-article ablation 99.1%). — [arXiv abs](https://arxiv.org/abs/2608.09393)
- **"Still Fresh? Evaluating Temporal Drift in Retrieval Benchmarks"** (Kuissi, Subrahmanyan, Thakur, Lin; arXiv:2603.04532, 4 Mar 2026; preprint). Compares FreshStack LangChain corpus snapshots from Oct 2024 vs Oct 2025: all but one 2024 query remained fully supported by the 2025 corpus (relevant docs shifted to competitor repos such as LlamaIndex); retrieval-model rankings correlated with Kendall τ up to 0.978 at Recall@50; conclusion: benchmarks re-judged against evolving corpora remain reliable. — [arXiv abs](https://arxiv.org/abs/2603.04532)
- **TempRAGEval (MRAG, Findings of EMNLP 2025)**: temporal perturbations cause "remarkable degradation of retrieval performance" for existing retrievers. — [arXiv](https://arxiv.org/html/2412.15540v2)
- A 2025 survey (arXiv:2407.13193) states that "few benchmarks test whether RAG systems prioritize up-to-date information" and that temporal retrieval evaluation "is not yet mainstream in end-to-end RAG benchmarking." — [arXiv PDF](https://arxiv.org/pdf/2407.13193)
- **ConflictRAG** (arXiv:2605.17301; preprint) evaluates knowledge-conflict detection/resolution in RAG on ConflictQA, NQ-Conflict and AmbigQA. — [arXiv PDF](https://arxiv.org/pdf/2605.17301)

### Inferences
- The strongest empirical message across benchmarks: keeping *old versions* in the index and selecting by applicability date matters more than mere freshness. Fiscal-FR-Bench's 2.7%→98.3% jump comes entirely from indexing multiple versions and retrieving the right one; "latest-only" indexing (the default of most pipelines, including LiveVectorLake's hot tier) can be worse than no retrieval for version-sensitive domains.
- WikiBigEdit's result (RAG ≫ parameter editing at 500K edits) is the most rigorous evidence that application-level index updates, not weight edits, are the practical path for large volumes of fact changes.

### Gaps
- **ConflictBank**: no primary source found in searches; only ConflictRAG surfaced. Its existence/details are unverified here.
- EvolvingQA snapshot dates and numeric results not read (abstract only).
- No benchmark found that measures answer quality as a function of *index-update latency* (how long after a document arrives it is used correctly).

## KQ4. Embedding-model drift and re-embedding: updating the embedding model without re-embedding the corpus

### Takeaway
Two research lines exist: backward-compatible training (BCT, CVPR 2020; BC-Aligner, 2022) which must be planned when training the new model, and post-hoc adapters — notably Drift-Adapter (EMNLP 2025) which maps *queries* from the new model into the legacy embedding space, recovering 95–99% of full re-embedding Recall@10/MRR with <10 µs added latency and >100× lower compute. Vendor docs (LightRAG README) and practitioner guides treat embeddings as append-only and recommend dual-write/shadow indexes with gradual cutover.

### Cited Findings
- **Drift-Adapter: "A Practical Approach to Near Zero-Downtime Embedding Model Upgrades in Vector Databases"** (Harshil Vejendla, Rutgers; arXiv:2509.23471; published EMNLP 2025 main, paper 805; peer-reviewed). A small learned layer (Orthogonal Procrustes, Low-Rank Affine, or Residual MLP) trained on a small set of paired old/new embeddings maps new-model query embeddings into the legacy space so the existing ANN index keeps serving. Results on MTEB text corpora and a CLIP image upgrade (1M items): recovers 95–99% of Recall@10 and MRR of full re-embedding with <10 µs added query latency; MLP variant R@10 0.992 (+8.0 µs) vs 1.0 for full re-index (described as ~4–8 h downtime) and ~0.995 for dual-index serving; adapter training ≈0.5 GPU-hours vs ≈100 GPU-hours for re-embedding; recompute cost reduced >100×; under larger simulated drift the misaligned baseline fell to 0.213 ARR while the MLP adapter kept 0.715. — [arXiv HTML](https://arxiv.org/html/2509.23471v1); [ACL Anthology](https://preview.aclanthology.org/setup/2025.emnlp-main.805)
- **"Towards Backward-Compatible Representation Learning"** (Shen et al., CVPR 2020; peer-reviewed): BCT trains the new model against the old model's classifier so new embeddings are directly comparable with old ones, "enabling backfill-free model updates"; requires planning at training time. — [CVPR PDF](https://openaccess.thecvf.com/content_CVPR_2020/papers/Shen_Towards_Backward-Compatible_Representation_Learning_CVPR_2020_paper.pdf)
- **"Learning Backward Compatible Embeddings" (BC-Aligner)** (Stanford/SNAP, arXiv:2206.03040; KDD 2022 per talk listing): each new embedding model is learned together with a lightweight backward-compatibility transformation aligning it to the previous version; transformations compose to reproduce any historical version. Code: github.com/snap-stanford/bc-emb. — [arXiv PDF](https://arxiv.org/pdf/2206.03040)
- **"Multi-modal Knowledge Preserving Adapter for Embedding Backward Compatibility" (MKP-Adapter)** (arXiv:2609.16875; preprint, 2026): adapter-only backward compatibility for multimodal LLM embeddings, motivated by BCT methods requiring costly backbone updates. — [arXiv abs](https://arxiv.org/abs/2609.16875v1)
- LightRAG README (OSS docs): the embedding model must remain fixed after indexing because changing it "requires re-embedding all chunks, entities, and relations." — [LightRAG GitHub](https://github.com/HKUDS/LightRAG)
- Practitioner guidance (blogs, unverified): embeddings are "append-only; you can't update them in-place"; recommended rollout is dual-write/shadow index (new chunks embedded by both models; historical corpus backfilled gradually), mixed queries across both spaces or a translation layer, and A/B gradual cutover; main risk is "silent accuracy degradation" so recall should be measured against the old index before cutover. — [DEV Community](https://dev.to/gabrielanhaia/embedding-model-upgrades-without-re-indexing-100-upfront-134p); [HackerNoon](https://hackernoon.com/your-embedding-model-will-deprecate-heres-what-to-do); [tianpan.co](https://tianpan.co/blog/2026-04-19-embedding-drift-long-lived-rag-systems)
- Third-party blog note: Drift-Adapter "works best when the model change is incremental (same architecture, more training) rather than a fundamental architecture change." — [tianpan.co](https://tianpan.co/zh/blog/2026-04-09-embedding-models-production-versioning-index-drift)

### Inferences
- Drift-Adapter is the first peer-reviewed treatment of this problem in the vector-DB/RAG setting specifically; earlier BCT work is from computer vision. Its design (adapt the query side, keep the corpus index) means incremental inserts after the upgrade still need the *old* model or a reverse adapter — the paper's dual-index numbers suggest operators still backfill eventually.

### Gaps
- The Zilliz "embedding model updates" FAQ page fetched empty; no vendor-authored (Milvus/Pinecone/Weaviate/Qdrant) official recommendation on embedding-model migration was retrievable.
- Matryoshka Representation Learning was not researched here (no source fetched); its relevance to migration (truncatable dims rather than model swap) is not documented in these notes.
- No RAG-specific measurement of answer-quality loss under embedding drift beyond Drift-Adapter's retrieval metrics.

## KQ5. Chunk-level update strategies in production pipelines (LlamaIndex, LangChain): change detection, delete modes, consistency

### Takeaway
Both frameworks detect changes by hashing: LlamaIndex's IngestionPipeline keeps a `doc_id → document_hash` map in a docstore and re-processes/upserts only documents whose hash changed; LangChain's indexing API uses a RecordManager with four cleanup modes (`None`, `incremental`, `full`, `scoped_full`) that differ in when stale chunks are deleted and whether deleted source documents are removed. Both require vector stores that support add-by-id and delete-by-id, and both warn against mixing with stores populated outside the API.

### Cited Findings
- **LlamaIndex IngestionPipeline document management (vendor docs)**: attaching a docstore enables dedup/update using `document.doc_id` or `node.ref_doc_id`; works by "Storing a map of `doc_id` -> `document_hash`"; with a vector store attached, "If a duplicate `doc_id` is detected, and the hash has changed, the document will be re-processed and upserted," and unchanged hashes are skipped; without a vector store "we can only check for and remove duplicate inputs"; "embeddings must be a stage of your pipeline" when connecting a vector store; per-node transformation results are cached ("each node + transformation combination is hashed and cached") locally via `pipeline.persist` or remotely via RedisCache/MongoDBCache/FirestoreCache. The page does not document deletion of documents removed from the source and does not name the hash function. — [LlamaIndex docs](https://developers.llamaindex.ai/python/framework/module_guides/loading/ingestion_pipeline/)
- **LangChain indexing API (vendor docs / API reference)**: `cleanup` ∈ {`None`, `incremental`, `full`, `scoped_full`}. `None`: "does not do any automatic clean up." `incremental`: cleans continuously as it writes, "minimizes this period of time" when old and new versions can both be returned, but "If the source document has been deleted ... the full cleanup mode will delete it from the vector store correctly, but the incremental and scoped_full mode will not"; redundant work if a source id's documents span batches. `full`: cleanup after all batches; "the loader should be returning the entire dataset ... Otherwise, the auto_cleanup will remove documents that it is not supposed to." `scoped_full` (added langchain-core 0.3.25): "only deletes all documents that haven't been updated AND that are associated with source IDs that were seen during indexing"; keeps source IDs in memory, so 10M+ docs likely need parallelization. Requirements: "Do not use with a store that has been pre-populated with content independently of the indexing API, as the record manager will not know that records have been inserted previously"; vector store must support `add_documents(ids=...)` and `delete(ids=...)`. — [LangChain reference: index()](https://reference.langchain.com/python/langchain-core/indexing/api/index); [LangChain how-to (redirects)](https://python.langchain.com/docs/how_to/indexing)
- **LiveVectorLake** (preprint) uses SHA-256 content hashes per chunk and reports re-processing only 10–15% of content per update vs 100% for full re-index. — [arXiv abs](https://arxiv.org/abs/2601.05270)

### Inferences
- Neither framework offers transactional consistency: LangChain's own docs acknowledge a window in which old and new chunks coexist (`incremental` minimizes it; `full` has a longer window and requires a complete reload). For deletions, only `full` mode removes orphaned chunks, which conflicts with the typical "load only what changed" pattern — practitioners must choose between cheap incremental loads and correct deletes, or run periodic `full` passes.
- Both frameworks hash at the *document* level (LlamaIndex: doc_id→hash; LangChain: content+metadata hash per chunk under a source_id), so a one-line edit re-chunks and re-embeds the whole document unless chunk boundaries are stable — consistent with LiveVectorLake's chunk-level hashing being the finer-grained alternative.

### Gaps
- LlamaIndex docstore strategy enum names (`UPSERTS`, `DUPLICATES_ONLY`, `UPSERTS_AND_DELETE`) were not present on the fetched page; their exact semantics (esp. `UPSERTS_AND_DELETE`) remain uncited.
- No vendor documentation found quantifying the inconsistency window in LangChain `incremental` mode.

## KQ6. KV-cache / cache-augmented "RAG without re-retrieval" (CacheBlend, RAGCache, TurboRAG, CAG): how do they handle updated documents?

### Takeaway
None of the four primary papers describes an invalidation or refresh mechanism for changed source documents; all precompute per-chunk (or whole-corpus) KV state offline and treat it as immutable. CacheBlend's selective recomputation (<15% of tokens) addresses cross-chunk attention, not document edits. Secondary sources uniformly state CAG's knowledge is frozen at preload time and must be rebuilt, which re-incurs the preprocessing cost.

### Cited Findings
- **CacheBlend: "Fast Large Language Model Serving for RAG with Cached Knowledge Fusion"** (Yao et al.; arXiv:2405.16444 v1 May 2024, v3 Apr 2025; an ACM DOI 10.1145/3790254 exists for a published version — venue not confirmed from the arXiv page). Reuses precomputed KV caches "regardless prefix or not" and "selectively recomputes the KV values of a small subset of tokens"; TTFT reduced 2.2–3.3×, throughput +2.8–5× vs full recompute "without compromising generation quality" (3 LLMs, 4 datasets). The page does not say how stored caches are refreshed after source text changes. — [arXiv abs](https://arxiv.org/abs/2405.16444); [ACM](https://dl.acm.org/doi/pdf/10.1145/3790254)
- LMCache docs (vendor) on CacheBlend: "an update fraction of less than 15% can typically generate same-quality responses"; API `precompute_kv(doc) -> doc_id` returns a document ID for later reuse; nothing stated about re-uploading edited documents invalidating old entries. — [LMCache docs](https://docs.lmcache.ai/kv_cache_optimizations/cacheblend.html)
- **TurboRAG: "Accelerating Retrieval-Augmented Generation with Precomputed KV Caches for Chunked Text"** (Lu, Wang, Rong, Chen, Tang; EMNLP 2025 main, pp. 6588–6601; peer-reviewed). Chunk-level KV caches precomputed offline, combined at inference with independent-attention masks and reordered RoPE; TTFT reduced up to 9.4× (avg 8.6×) with "comparable" accuracy; no model/inference-system changes. The paper does not address cache invalidation or refresh when documents change. — [ACL Anthology](https://aclanthology.org/2025.emnlp-main.334/)
- **RAGCache: "Efficient Knowledge Caching for Retrieval-Augmented Generation"** (arXiv:2404.12457 v2 Apr 2024; preprint, cs.DC). Organizes intermediate KV states of retrieved knowledge in a knowledge tree across GPU/host memory with an LLM/RAG-aware replacement policy and overlaps retrieval with inference; TTFT up to 4× lower and throughput up to 2.1× higher than vLLM+Faiss. No discussion of invalidation on document updates. — [arXiv abs](https://arxiv.org/abs/2404.12457)
- **CAG: "Don't Do RAG: When Cache-Augmented Generation is All You Need for Knowledge Tasks"** (Chan, Chen, Cheng, Huang; arXiv:2412.15605 v2 Feb 2025; accepted as short paper at WWW '25; peer-reviewed). Preloads all documents into the context window and caches runtime KV parameters, "bypasses real-time retrieval," intended for knowledge "of a limited and manageable size"; abstract claims comparable or superior results to RAG with reduced complexity; does not discuss refreshing preloaded knowledge. — [arXiv abs](https://arxiv.org/abs/2412.15605); [GitHub hhhuang/CAG](https://github.com/hhhuang/CAG)
- **"Enhancing Cache-Augmented Generation (CAG) with Adaptive Contextual Compression"** (arXiv:2505.08261; preprint): states a preloaded cache is a snapshot — newer research, breaking news or edited entries "stay invisible until someone rebuilds it"; proposes hybrid designs keeping a static cache for stable knowledge and on-demand retrieval for dynamic content, triggering retrieval only on low confidence. — [arXiv PDF](https://arxiv.org/pdf/2505.08261)
- **CacheClip** (arXiv:2510.10129; preprint) observes that blending updated and original KV caches "can break contextual integrity, particularly when recomputation ratios fall in intermediate ranges." — [arXiv HTML](https://arxiv.org/html/2510.10129v1)
- Secondary (blogs, unverified): freshness comparisons list RAG as "always current" vs CAG as "needs cache invalidation for updates"; updating CAG "means paying the preprocessing cost again"; CAG is recommended only for rarely changing data (e.g., compliance guidelines). — [Lumenova](https://www.lumenova.ai/blog/cag-what-is-cache-augumented-generation/); [datanorth.ai](https://datanorth.ai/blog/cache-augmented-generation-cag-a-performance-driven-alternative-to-rag)

### Inferences
- Because TurboRAG/CacheBlend caches are keyed per chunk and computed independently of other chunks, a document edit should in principle require recomputing only the edited chunks' caches (same locality as re-embedding), but no paper measures this cost or defines a doc_id-based invalidation path. CAG (whole-corpus single cache) has the worst update locality: any change invalidates the whole prefix cache.
- Combining chunk-hash change detection (KQ5) with per-chunk KV caches is an obvious but unreported integration.

### Gaps
- No paper found that measures stale-cache effects (answering from an outdated KV cache after the source changed) or the cost of partial KV-cache refresh after edits.
- CacheBlend's peer-reviewed venue was not confirmed from the fetched page (ACM DOI exists but venue name unverified).

## KQ7. ANN-index update latency vs. RAG answer quality: how fast does an inserted document become retrievable (Milvus/Pinecone/Weaviate/Qdrant), and any "freshness SLA"?

### Takeaway
Vendor docs describe three distinct visibility mechanisms — Milvus (growing-segment brute-force scan gated by a GuaranteeTs/consistency level), Weaviate (in-place HNSW insert, or async queue with a "short delay" before vector search), Qdrant (brute-force over unindexed segments below `indexing_threshold`), Pinecone (eventually consistent, with LSN headers to check whether a write is reflected). A third-party benchmark reports p50 write-ack→search-visible latencies of 2–41 ms across seven open-source engines. No study was found that links this insertion latency to downstream RAG answer quality, and no vendor publishes a freshness SLA.

### Cited Findings
- **Milvus consistency docs (vendor)**: levels Strong, Bounded staleness (default), Session, Eventually; implemented via GuaranteeTs — "tells query nodes not to process a search or query until all data before that timestamp is visible"; Strong = newest system timestamp, Bounded = slightly earlier, Session = client's latest write timestamp, Eventually = very small value (skips check). — [Milvus docs](https://milvus.io/docs/consistency.md)
- **Pinecone data-freshness docs (vendor)**: "Pinecone is eventually consistent, so there can be a short delay before new or changed records appear in query results." Serverless indexes expose a per-namespace monotonically increasing log sequence number: write LSN in `x-pinecone-request-lsn`, query LSN in `x-pinecone-max-indexed-lsn`; if query LSN ≥ write LSN the write is reflected. Alternative: compare `describe_index_stats` vector counts (misleading if inserts and deletes net out, or for value updates). No latency figures are given. — [Pinecone docs](https://docs.pinecone.io/guides/index-data/check-data-freshness)
- **Weaviate vector-index docs (vendor)**: synchronous HNSW inserts update the index in step with the object store (index can become the bottleneck); with asynchronous indexing, inserts/deletes/updates go through a queue, "the object store is updated right away, while the vector index updates in the background," and "there will be a short delay between object creation and the object being available for vector search using the HNSW index"; the async queue is persisted on disk since v1.28 and queue size is observable per node; the dynamic index (requires async) starts flat and swaps to HNSW after 10,000 objects by default. — [Weaviate docs](https://docs.weaviate.io/weaviate/concepts/vector-index)
- **Qdrant (vendor articles)**: HNSW is built/updated only once unindexed vectors in a segment exceed `indexing_threshold`; below it, "no dense vector index will be built" and search uses brute-force scans (slower but still returns results); setting `indexing_threshold=0` defers indexing entirely for bulk loads at the cost of RAM; the experimental `prevent_unoptimized` flag (since 1.17.1) makes points written after a segment crosses the threshold "deferred points, durably stored but held back from search until the segment finishes optimizing," while the older `indexed_only` search parameter skips large unindexed segments at query time, which "can make points blink in and out of results." — [Qdrant indexing optimization](https://qdrant.tech/articles/indexing-optimization/); [Qdrant optimizer tuning](https://qdrant.tech/articles/tuning-qdrant-optimizer/index.md)
- **Third-party benchmark (AIMultiple, page updated Oct 2026; not peer-reviewed)**: p50 write-ack→search-visible latency on a MedRAG-50k live-churn workload (~150 writes checked, 0 invisible, 8-vCPU/32 GB box): Redis 2 ms, Weaviate 4 ms (corrected ≈5 ms; run at 3,000 initial docs vs 30,000 for others), Qdrant 9 ms, Milvus 12 ms, pgvector 14 ms, LanceDB 31 ms, Chroma 41 ms; versions Qdrant 1.18.1, Milvus 2.6.0, Weaviate 1.38.0, pgvector 0.8.x, Chroma 1.5.0, Redis 8.2, LanceDB 0.34.0; Milvus figure explained as "a strong-consistency scan of the not-yet-sealed growing segment" (vector enters HNSW later); index parameters and per-engine consistency settings not listed. — [AIMultiple](https://aimultiple.com/open-source-vector-databases)
- Academic note (arXiv:2606.08950, preprint): Milvus and Qdrant "place new vectors in unindexed segments that must be searched with an exhaustive scan, increasing query latency," whereas Weaviate "directly updates the active HNSW index while queries are running," with concurrent inserts able to hurt query tail latency. — [arXiv PDF](https://arxiv.org/pdf/2606.08950)
- **LiveVectorLake** (preprint) is the only RAG-level system found that explicitly engineers around index freshness (hot Milvus tier with current chunks only + versioned cold tier), reporting sub-100 ms current-knowledge retrieval; it does not report insertion-to-visibility latency. — [arXiv abs](https://arxiv.org/abs/2601.05270)
- Secondary opinion (blog): for most RAG pipelines "eventual consistency is acceptable — a new document becoming searchable within seconds is fine." — [tianpan.co](https://tianpan.co/blog/2026/04/17/ai-native-database-selection-vector-production)

### Inferences
- In every engine the new vector is *searchable* (via brute-force/growing-segment scan or in-place HNSW insert) long before it is *indexed*; the practical freshness bottleneck for RAG is therefore upstream (change detection, chunking, embedding, LLM extraction for GraphRAG — minutes to hours) rather than the vector DB's millisecond-scale visibility. This is consistent with LiveVectorLake's and TG-RAG's focus on reducing re-processing rather than DB latency.
- Pinecone's LSN headers are the only vendor-provided primitive found for building an application-level read-your-writes check (a de facto "freshness SLA" test harness); Milvus Session consistency and Weaviate's queue-size metric serve similar roles.

### Gaps
- No paper or vendor doc found that measures RAG answer quality as a function of ANN insertion/visibility delay, nor any published "freshness SLA" from Milvus, Pinecone, Weaviate or Qdrant.
- Pinecone write-to-visible latency numbers: not published; the third-party benchmark excludes Pinecone.
- The AIMultiple benchmark does not report run date, index parameters, or the consistency settings used per engine, limiting comparability.
