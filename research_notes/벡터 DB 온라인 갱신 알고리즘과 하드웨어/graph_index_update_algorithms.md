## KQ1. FreshDiskANN (Singh et al., 2021): how do StreamingMerge and delete consolidation work, and what numbers does it report?

### Takeaway
FreshDiskANN (arXiv preprint, never listed at a peer-reviewed venue) introduces lazy deletes (DeleteList tombstones) plus a batched "delete consolidation" that reconnects each in-neighbor of a deleted node to that node's out-neighbors and re-prunes with alpha>1 (alpha-RNG), and a two-pass SSD StreamingMerge (Delete / Insert / Patch phases) that merges an in-memory TempIndex into an SSD long-term index in ~8.5% of full-rebuild time; steady state on an ~800M–1B SIFT index is 1800 inserts/s + 1800 deletes/s, >95% 5-recall@5, <128 GB DRAM.

### Cited Findings
**Why naive deletion fails (motivation)**
- The paper tested HNSW, NSG and Vamana with two natural delete policies on SIFT1M, cycling delete-then-reinsert of 5% of points: "Delete Policy A" (remove all in/out edges of p, add nothing) and "Delete Policy B" (remove edges, then add (p_in, p_out) for every pair of in/out edges and prune with the algorithm's own pruning, i.e. alpha=1). "All of the algorithms show a consistently deteriorating trend in search performance (the recall drops for a fixed candidate list size)" over 20 cycles (Figure 1, L_s = 44/20/27 for HNSW/Vamana/NSG). — [FreshDiskANN PDF](https://arxiv.org/pdf/2105.09613)
- The paper cites the HNSW discussion of supporting deletes "by adding them to a blacklist and omitting from search results" as evidence that deletions were unsolved for graph indexes. — [FreshDiskANN PDF](https://arxiv.org/pdf/2105.09613)

**FreshVamana update rules (in-memory)**
- Insert (Algorithm 2): GreedySearch(s, x_p, 1, L) returns visited set V; N_out(p) = RobustPrune(p, V, alpha, R); then for each j in N_out(p) add reverse edge p to N_out(j), and if |N_out(j)| > R run RobustPrune(j, N_out(j) ∪ {p}, alpha, R). RobustPrune (Algorithm 3) keeps the closest candidate p* and removes any p' with alpha·d(p*, p') <= d(p, p'). Concurrency: "lock-based concurrency control to guard access to N_out(p)"; "Due to the fine granularity of locking and the short duration for which the locks are held, insertion throughput scales near-linearly with threads." — [FreshDiskANN PDF](https://arxiv.org/pdf/2105.09613)
- Delete (Algorithm 4, Delete(L_D, R, alpha)): for every surviving p whose N_out(p) intersects the delete set L_D: D = N_out(p) ∩ L_D; C = N_out(p) \ D; for each v in D, C = C ∪ N_out(v); C = C \ D; N_out(p) = RobustPrune(p, C, alpha, R). "The crucial feature being using the relaxed alpha-pruning algorithm to retain density of the modified graph." — [FreshDiskANN PDF](https://arxiv.org/pdf/2105.09613)
- Lazy deletion: "when a point p is deleted, we add p to a DeleteList without changing the graph ... At search time, a modified Algorithm 1 uses nodes in the DeleteList for navigation, but filters them out from the result set." Delete Consolidation: "After accumulating a non-trivial number of deletions (say 1-10% of the index size), we batch-update the graph using Algorithm 4 ... This operation is trivially parallelized using prefix sums to consolidate the vertex list, and a parallel map operation to locally update the graph around the deleted nodes." — [FreshDiskANN PDF](https://arxiv.org/pdf/2105.09613)
- Recall stability (Figure 2): FreshVamana indices on SIFT1M/Deep1M and SIFT100M run 50 cycles of deleting and re-inserting 5%, 10% and 50% of the index; with L_s chosen for ~95% 5-recall@5 at cycle 0, recall stays stable (same L, alpha, R used for static build and updates). Figure 3 sweeps alpha ∈ {1, 1.1, 1.2, 1.3} for build+update; the text states alpha > 1 is what ensures stability. — [FreshDiskANN PDF](https://arxiv.org/pdf/2105.09613)

**FreshDiskANN system and StreamingMerge (SSD)**
- Architecture: one SSD-resident Long-Term Index (LTI) over most points (memory holds only compressed PQ vectors, ~24 GB for 800M points), one RW-TempIndex (in-memory FreshVamana ingesting inserts), zero or more read-only RO-TempIndex snapshots, and a DeleteList. Searches fan out to LTI + all TempIndexes and filter by DeleteList. TempIndex total capped at M = 30M points (~13 GB: 128 B vector + 256 B neighbors at R=64 + ~100 B aux per point); at most 60M points of TempIndex (~26 GB) live at any time. — [FreshDiskANN PDF](https://arxiv.org/pdf/2105.09613)
- StreamingMerge runs "Algorithm 4" then "Algorithm 2" against the SSD index in three phases: (1) Delete Phase: a sequential pass over the LTI blocks; each block's nodes are processed with Algorithm 4 in parallel using PQ (approximate) distances, written to an intermediate-LTI; (2) Insert Phase: for each new point, simulate Algorithm 2 by searching the intermediate-LTI from SSD (about 100 random 4 KB reads per inserted point, "a little more than the candidate list size parameter, which we typically set to 75"), prune to get N_out(p), and record backward edges in an in-memory Delta structure (size O(|N|·R); ~7 GB for |N|=30M, R=64) instead of writing to SSD; (3) Patch Phase: a second sequential pass that adds the backward edges block-by-block (pruning when degree exceeds R). "The procedure does exactly two sequential passes over the SSD-resident data structure". Delete phase cost bounded as O(|D|·R^2) expected plus a fixed scan. — [FreshDiskANN PDF](https://arxiv.org/pdf/2105.09613)
- Recall stability of StreamingMerge (Figure 4): starting from an 80M-point SSD index (from SIFT100M), each cycle applies 8M deletes + 8M inserts (10%) via StreamingMerge for 40 cycles; the index "stabilizes at a lower recall value compared to the static index it starts out with, due to the use of approximate distances", with stabilization after ≈20 cycles; similar on the 800M subset of SIFT1B. — [FreshDiskANN PDF](https://arxiv.org/pdf/2105.09613)
- Crash recovery: all update ops go to a redo-log; RW-TempIndex and DeleteList are rebuilt by replay; RO-TempIndex/LTI reloaded from disk; rebuilding RW-TempIndex from log takes ~2.5 min for 5M points vs 16 min for 30M (48 cores). — [FreshDiskANN PDF](https://arxiv.org/pdf/2105.09613)

**Headline numbers (week-long experiments, ~800M–1B SIFT1B subset, 2x Xeon 8160 / 48 cores / 3.2 TB Samsung PM1725a SSD)**
- "The system uses less than 128GB of DRAM at all times." Peak footprint ≈100 GB for 800M steady-state (TempIndexes ~26 GB + LTI PQ ~24 GB + merge working set ≤50 GB). — [FreshDiskANN PDF](https://arxiv.org/pdf/2105.09613)
- "The StreamingMerge can merge a 10% change to the index (5% inserts + 5% deletes) to a billion-scale index in ∼10% of the time than it takes to rebuild the index." Specifically: 40-thread StreamingMerge of 30M inserts + 30M deletes into an 800M index takes ~16,000 s (16,277 s reported), "8.5% of the ≈190000 seconds it would take to rebuild the index from scratch with a similar thread-count." Insert-only merge of 30M into 800M takes ~8,400 s/cycle. — [FreshDiskANN PDF](https://arxiv.org/pdf/2105.09613)
- "FreshDiskANN can support a steady-state throughput of 1800 inserts and 1800 deletes per second while retaining freshness and without backlogging background merge. The system can also support short bursts of much higher change rate, up to even 40,000 inserts/second." During ramp-up (inserts only) inserts were throttled to ~3,500/s. Insert latency ~1 ms; delete ~0.1 µs (DeleteList append); "The user latency of insertion and deletion is under 1ms, even when a background merge is underway." — [FreshDiskANN PDF](https://arxiv.org/pdf/2105.09613)
- Search: "1000 searches/sec with 95+% 5-recall@5 ... mean search latency well under 20ms"; with L_s=100 a query does ~120 random 4 KB reads and ~8,000 distance comparisons; with 64 search threads ~6,500 QPS. Search latency rises during merge (figure shows ~5–15 ms band with spikes in the Patch phase; the text attributes it to head-of-line blocking from the large sequential I/O). — [FreshDiskANN PDF](https://arxiv.org/pdf/2105.09613)
- Merge-thread trade-off: more merge threads T = faster merge and higher sustainable update rate, but higher SSD bandwidth use hurts search throughput/99% latency; "3600 updates/sec require 40 threads". — [FreshDiskANN PDF](https://arxiv.org/pdf/2105.09613)
- The abstract frames the result as "a 5-10x reduction in the cost of maintaining freshness" relative to periodic rebuilds (one rebuild of a billion index estimated at 1.5–2 hours on dedicated machines). — [arXiv abstract](https://arxiv.org/abs/2105.09613)

**How the open-source DiskANN exposes this**
- DiskANN's dynamic-index workflow doc: "eager deletes can be supported by DiskANN, but lazy_deletes are the preferred method"; "a sequence of lazy deletions must be followed by an invocation of the consolidate_deletes method that frees up slots in the index and edits the graph to maintain good recall"; "insertions, searches and lazy deletions can be performed concurrently, and consolidation of lazy deletes can be performed synchronously or concurrently with insertions and deletions." — [DiskANN dynamic_index.md (fork mirror)](https://github.com/bytetopia/DiskANN/blob/main/workflows/dynamic_index.md)
- The BigANN'23 report describes the DiskANN streaming baseline the same way: inserts eager, deletes lazy (marked immediately, graph cleaned later), and "accumulating a large number of deletes leads to a drop in index recall, normalizing for search parameters" until consolidation runs. — [BigANN'23 results](https://arxiv.org/html/2409.17424v1)

### Inferences
- FreshDiskANN's delete repair is "Policy B with alpha>1": the alpha-RNG relaxation, not the connect-in-to-out idea itself, is what keeps recall stable; later work (Wolverine, IP-DiskANN) attacks precisely the O(R^2) edge blow-up and the full-index scan this implies.
- The sustainable update rate (1,800+1,800/s) is bounded by merge time, not by in-memory insert latency; i.e., the SSD merge is the real throughput ceiling, which motivates the later in-place and localized-update lines of work.

### Gaps
- The paper is a 2021 arXiv preprint; I found no peer-reviewed version.
- Exact recall values in Figures 2–4 are only in plots (not in extracted text), so I report the stated qualitative trend and the L_s targets, not per-cycle numbers.

## KQ2. In-place deletion for DiskANN-style graphs (IP-DiskANN, 2025) and HNSW: algorithms and comparison to lazy deletion

### Takeaway
IP-DiskANN (preprint, Feb 2025) approximates the in-neighbors of a deleted point by re-running a greedy search for its vector and taking visited nodes that point to it, then adds only c (=3) replacement edges per affected neighbor instead of R^2 edges, leaving only a cheap, distance-free periodic dangling-edge sweep; it reports +0.03 to +2.3 recall points over FreshDiskANN batch consolidation with lower deletion time at >=10M scale, and far cheaper updates than hnswlib's replace-deleted path. 2026 follow-ups (MERIT, Yi, GrAND) claim 3–19x faster in-place deletion or higher throughput, but all are preprints.

### Cited Findings
**IP-DiskANN algorithm**
- Problem statement: "since the graph is singly-linked, deletions are hard because there is no fast way to find in-neighbors of a deleted vertex"; maintaining explicit in-neighbor lists is rejected because of memory and "locking complexity in a highly concurrent system. In practice, all these reasons make maintaining in-neighbors unacceptable." — [IP-DiskANN PDF](https://arxiv.org/pdf/2502.13826)
- Critique of FreshDiskANN consolidation: connecting all in-neighbors to all out-neighbors adds R^2 edges per deleted vertex (many prune invocations) and "Some unnecessary short range edges will be added forcing out a few useful long range ones due to the degree limit, degrading the overall connectivity." — [IP-DiskANN PDF](https://arxiv.org/pdf/2502.13826)
- Algorithm 5 In-place Deletion(G, p, l_d=128, k=50, c=3, alpha=1.2, R): [Visited, Candidates] = GreedySearch(G, x_p, k, l_d); N'_in(p) = {z in Visited : p in N_out(z)} (approximate in-neighbors, justified because the visited list at insert time was the source of p's in-neighbors); for each z in N'_in(p): C_z = closest-c points to x_z among Candidates; N_out(z) = N_out(z) ∪ C_z \ {p}, RobustPrune if degree > R; for each w in N_out(p): find C_w = closest c nodes to x_w in Visited and add edges C_w -> w. Added edges are O(cR) vs O(R^2). "It is important to use a parameter alpha > 1 to preserve the navigability of the graph (here we use 1.2 as in prior work)." — [IP-DiskANN PDF](https://arxiv.org/pdf/2502.13826)
- Residual dangling edges: because Algorithm 5 "does not guarantee all incoming edges to p are deleted", a periodic Algorithm 6 Consolidation simply does N_out(p) = N_out(p) \ D for every p, "usually after the number of deletions exceed a certain fraction of the index size"; it "does not do any distance calculations". — [IP-DiskANN PDF](https://arxiv.org/pdf/2502.13826)

**Experimental setup**
- Runbooks: SlidingWindow (T_max=200 parts; each point lives T_max/2 steps), ExpirationTime (points live forever / long / short), Clustered (64 k-means clusters; whole clusters inserted/deleted, "the most challenging"). Datasets: MSTuring-10M/30M, Wiki-1M/10M/35M (Cohere). High-recall params R=64, l_b=l_s=128, alpha=1.2; low-recall R=32, l_b=l_s=64. "Consolidation is triggered for both algorithms when 20% of the points in the graph are marked deleted." HNSW baseline: hnswlib commit c1b9b79, M=48, ef_construction=ef_search=128 (chosen for similar memory), replace op invoked when >=20% nodes marked deleted. Hardware: 16 threads on a 32-vCPU Azure L32s_v3 (Xeon 8370C), closed-source Rust implementation consistent with the BigANN'23 FreshDiskANN code. — [IP-DiskANN PDF](https://arxiv.org/pdf/2502.13826)

**Results**
- Average recall@10 improvement over FreshDiskANN of "0.4, 0.7, 2.3, 0.03 and 0.2 percentages" across the five high-recall runbooks, "while using fewer distance computations and providing higher query throughput" (explanation: cR rather than O(R^2) edges per deletion gives a slightly sparser graph). — [IP-DiskANN PDF](https://arxiv.org/pdf/2502.13826)
- Table 1 (high-recall; seconds for deletion incl. consolidation / insertion / search; recall@10):
  - MSTuring-10M SlidingWindow: FreshDiskANN 1710/1452/143, 94.4; IP-DiskANN 1110/1461/136, 94.8; HNSW N/A/4016/66, 91.8.
  - MSTuring-30M Clustered: Fresh 3611/3187/845, 91.8; IP 3146/3133/807, 92.5; HNSW N/A/15296/859, 89.5.
  - Wiki-1M ExpirationTime: Fresh 38/88/63, 94.8; IP 92/100/71, 97.1; HNSW N/A/240/42, 95.9.
  - Wiki-10M ExpirationTime: Fresh 3222/2633/148, 97.9; IP 2170/2592/141, 97.9.
  - Wiki-35M ExpirationTime: Fresh 14535/12347/619, 97.3; IP 10027/11886/584, 97.5. (HNSW "insertion" time includes deletions because deletes are implemented as replacement.) — [IP-DiskANN PDF](https://arxiv.org/pdf/2502.13826)
- Table 2 (low-recall R=32): MSTuring-10M SW: Fresh del 720 / rec 76.7 vs IP 394 / 77.9; MSTuring-30M Clustered: 1376 / 71.3 vs 1170 / 73.1; Wiki-1M Exp: 11 / 83.1 vs 53 / 88.3. — [IP-DiskANN PDF](https://arxiv.org/pdf/2502.13826)
- Scaling: "IP-DiskANN spends more time on deletion for the 1 million scale dataset but becomes considerably faster as the scale of data grows to 10 million and beyond ... most of the deletion time is spent searching for alternative edge connections, the complexity of which grows sublinearly ... FreshDiskANN scans through the entire index ... which scales linearly." — [IP-DiskANN PDF](https://arxiv.org/pdf/2502.13826)
- Versus rebuild-from-scratch on MSTuring-30M-Clustered (snapshots every 64 steps): IP-DiskANN is reported to reach near the optimal (rebuilt) recall, better than the FreshDiskANN baseline (Figure 2). — [IP-DiskANN PDF](https://arxiv.org/pdf/2502.13826)
- Ablations on MSTuring-30M-Clustered (Table 3/4): k=10/50/100 -> recall 91.8/92.5/92.6, deletion time 2983/3082/3099 s; c=1/2/3/5 -> 91.0/92.2/92.5/92.8, time 2400/2740/3148/3753 s; l_d=60/128/200 -> 91.8/92.6/92.9, time 1898/3160/4576 s ("recall stops increasing when l_d reaches 200"); consolidation threshold t=30%/20%/10% -> recall 92.2/92.5/92.6, time 3136/3146/3207 s ("fewer dangling edges make it less likely that the greedy search reaches dead ends"). — [IP-DiskANN PDF](https://arxiv.org/pdf/2502.13826)

**HNSW deletion (hnswlib) as characterized by IP-DiskANN**
- hnswlib "handles deletions by marking them deleted and avoiding returning them for queries (see Github issues 249 and 275)"; incoming inserts may "replace" deleted nodes: it "updates all of the deleted point p's one-hop neighbors by adding all of p's two-hop neighbors to each of them, and then trimming them back down to respect the degree limit, first by retaining only the closest ef_construction to each node, then calling their prune process to retain at most M neighbors. Then, it proceeds like a standard insert". Cost argument: "HNSW's deletion adds all the two-hop neighbors of the deleted point to all its one-hop neighbors, it adds O(R^3) edges per deletion, compared with O(cR) for IP-DiskANN and O(R^2) for FreshDiskANN"; non-deleted nodes "might be pruned up to tens of times for a set of deletions of 20% of the index size, as opposed to only once in the amortized context of FreshDiskANN." — [IP-DiskANN PDF](https://arxiv.org/pdf/2502.13826)
- hnswlib API semantics: `mark_deleted(label)` "marks the element as deleted, so it will be omitted from search results"; `unmark_deleted` reverses it; `add_items(..., replace_deleted=True)` "replaces deleted elements. Note it allows to save memory" and requires `init_index(allow_replace_deleted=True)`; add_items is "Thread-safe with other add_items calls, but not with knn_query." — [hnswlib README mirror](https://codegraph.jelmer.uk/hnswlib/0.9.0-2/README.md)
- FAISS: `remove_ids` is "not supported by all indexes"; community threads and a 2025 paper state hnswlib/FAISS HNSW "does not support in-place deletions" and that the practical approach is soft-delete. Milvus's (older) engineering note says FAISS deletion required scanning the whole dataset and was supported only for FLAT/IVF_FLAT/IDMAP. — [faiss docs](https://faiss.ai/cpp_api/struct/structfaiss_1_1IndexHNSW.html); [Milvus delete article](https://dzone.com/articles/how-milvus-realizes-the-delete-function)

**Production adoption**
- Azure Cosmos DB's DiskANN integration runs two async processes: IndexBuilder (inserts/replaces/deletes, using "a recently developed in-place delete algorithm" that works even though the deleted vector's coordinates are unavailable at delete time) and IndexVacuum (removes stale edges left by deletes, defragments). Tested with BigANN-style expiration (1:2:10 lifespans, MSTuring-1M, Wiki-Cohere-10M) and clustered (64 clusters, 5 rounds) runbooks; the baseline that drops deleted vectors without repair "resembles many other vector databases". Recall values are only in plots. — [Cosmos DB blog](https://devblogs.microsoft.com/cosmosdb/azure-cosmos-db-with-diskann-part-4-stable-vector-search-recall-with-streaming-data/)

**2026 in-place deletion follow-ups (all preprints)**
- MERIT (arXiv 2607.29173, v3 Aug 2026): three techniques — bounded search-based recovery that "combines a deleted vertex's outgoing neighbors with its readily searchable in-neighbors"; k_r-Minimum-Spanning-Tree local repair "to improve local connectivity while keeping multiple routing choices"; versioned-edge invalidation that "immediately filters stale edges to the deleted vertex and removes them progressively as adjacency lists are rewritten". Works with HNSW and Vamana. Claims deletion "nearly the cost of inserting one vector", 3.02x–18.87x faster deletion than state-of-the-art, and recall that "stays stable or even improves as deletions accumulate". Datasets not named on the abstract page. — [MERIT abstract](https://arxiv.org/abs/2607.29173)
- Yi (arXiv 2607.15576, Jul 2026): argues out-of-place graph methods "update slowly because they periodically merge update batches"; a search summary of this paper states it criticizes IP-DiskANN's delete as incurring "a full scan" and relying on "a global lock" (I could not verify this wording in the abstract itself). Yi does vector-level in-place updates with a tasklet execution engine, async buffer manager and a vector file system; claims 1.75x higher update throughput and 1.8x higher concurrent search throughput than SOTA on an 800M dataset at 73% of their peak memory. — [Yi abstract](https://arxiv.org/abs/2607.15576)
- GrAND (arXiv 2608.21163, Aug 2026): GPU-native dynamic Vamana/CAGRA; consolidates graph repair across a batch, uses a "lock-free find-and-replace strategy for parallel adjacency-list updates", builds an on-demand reverse graph on GPU to find in-edges "without permanently duplicating the index", and deletes in place with it; 2.2x–8.7x throughput over SVFusion and 6.5x–25.4x over a FreshDiskANN-GPU port on 7 datasets / 5 streaming workloads. — [GrAND abstract](https://arxiv.org/abs/2608.21163)

### Inferences
- The consistent design pattern across IP-DiskANN, MERIT, Wolverine and GrAND is "recover in-neighbors by search (or by a transient reverse graph), repair locally, defer stale-edge removal to a cheap sweep" — i.e., in-place deletion still keeps a lightweight tombstone/sweep component; the heavy FreshDiskANN scan-and-reprune is what is removed.
- IP-DiskANN's small per-runbook recall gains (<=2.3 pts) matter less than the operational point that recall no longer dips between consolidations and no merge-time memory spike occurs.

### Gaps
- MERIT, Yi and GrAND numbers come from abstracts only; datasets, baselines and configurations are not verified from full text.
- Yi's specific critique of IP-DiskANN (full scan, global lock) could not be confirmed from the abstract page; treat as unverified.

## KQ3. Recall degradation / unreachable points / connectivity loss in HNSW under delete and update churn: measurements and fixes

### Takeaway
Multiple independent studies (MN-RU 2024, Wolverine VLDB'25, CleANN, LR-RN 2026, a usearch issue, and an unreviewed vector-DB churn benchmark) measure the same failure: deletion plus replacement in HNSW-style graphs leaves nodes with no in-edges or broken monotonic paths, so recall drifts down by roughly 3–10 points over thousands of churn cycles and cannot be recovered by raising ef; proposed fixes restrict repair to mutual/affected neighbors, repair monotonic paths via in-edges to out-neighbors, or add bridge edges, and a 2026 preprint finds signal-triggered repair no better than fixed-cadence repair at equal budget.

### Cited Findings
**MN-RU (UESTC, arXiv 2407.07871, preprint)**
- Definition: a point is "unreachable" if it has outgoing edges but no incoming edges in any layer. In hnswlib's replaced_update path (addPoint/updatePoint/repairConnectionsForUpdate), edges from one-hop neighbors to their original neighbors "might be deleted", leaving those neighbors with no in-edges. — [MN-RU HTML](https://arxiv.org/html/2407.07871v1)
- Measurement on SIFT1M (M=16, efC=200): randomly deleting and re-inserting 5% per iteration, "the number of unreachable points in HNSW consistently increases"; after ~3,000 iterations unreachable points reach 3–4% of the dataset and recall falls ~3%; "this decrease in accuracy ... cannot be mitigated by adjusting HNSW searching parameters, such as increasing the ef_ parameter." After 200 iterations of native HNSW-RU: ~3–4% unreachable on GIST (M=32, efC=600) and 2–3% on ImageNet (2.34M, M=64, efC=800). — [MN-RU HTML](https://arxiv.org/html/2407.07871v1)
- Update cost: on GIST and ImageNet at ~90% recall, insertion via replaced_update is 5–10x slower than a query (Fig. 1). — [MN-RU HTML](https://arxiv.org/html/2407.07871v1)
- Fix (MN-RU): only neighbors whose lists include the deleted point are updated; candidate set = their original neighbors plus the deleted point's neighbors, reducing per-layer cost from O(M^3) to O(M^2). Variants: MN-RU-alpha (reselect for mutually connected points, alpha=1), MN-RU-beta (add each candidate's neighbors, alpha=1), MN-RU-gamma (beta with alpha=1.1; Algorithm 2), MN-THN-RU (gamma + two-hop neighbors connected to the deleted point). Result: MN-RU variants are "2-4 times faster" than HNSW-RU in update time and suppress unreachable-point growth; MN-RU-gamma and MN-THN-RU reach better K=1 accuracy than HNSW-RU at equal time budgets (exact recall values only in figures). A "backup index" variant (rebuilt every four iterations, GIST, tau=40,000) yields significantly fewer unreachable points. Hardware: Xeon E5-2678 v3, 110 GB, 40 threads. — [MN-RU HTML](https://arxiv.org/html/2407.07871v1)

**Wolverine (PVLDB 2025, peer-reviewed) — delete-policy study on HNSW and FreshDiskANN**
- Baseline update operations on HNSW, SIFT1M, delete-and-reinsert at 5% update rate (HNSW ef=200; FreshDiskANN in-memory theta_d=32, L=200): Pseudo-deletion (tombstone only) keeps accuracy at first but "the index cannot shrink"; after 100 rounds "both Search_OPS and Insert_OPS of Pseudo drop to about 25% of the values before updates. To handle the performance decline, periodic rebuilding is required." Deletion-Only (remove all edges of p) "decreases sharply and eventually stabilizes at 0.92"; Deletion-with-Full-Connections (in-to-out edges, i.e. the FreshDiskANN idea) stabilizes at 0.937 but "exhibits a faster accuracy decline than HNSW+Do in first few rounds"; FreshDiskANN "also exhibits this behavior in the first 5 rounds. This suggests that indiscriminately adding edges to compensate for connectivity loss does not improve accuracy; instead, it can degrade performance in high-recall regions." — [Wolverine PDF](https://vbn.aau.dk/ws/files/851508848/Open_Access_Article.pdf)
- Root-cause analysis: deletion "disrupts monotonic search paths"; approximate SNGs (HNSW, NSG, DiskANN) "provide fewer monotonic search paths than exact SNGs", so "once a monotonic search path is destroyed, there are only few, if any, alternative monotonic search paths ... some nodes become unreachable during the greedy search." In-to-out edges (p_in, p_out) are "not always effective, because there is no guarantee that p_in is close to p_out". — [Wolverine PDF](https://vbn.aau.dk/ws/files/851508848/Open_Access_Article.pdf)

**CleANN (MIT, SIGMOD'26 per PDF header; arXiv preprint)**
- FreshVamana (in-memory FreshDiskANN) with batch consolidation: "throughput of FreshVamana can decrease by more than 10x during consolidation but consolidation is required to achieve good Search recalls". Also, the plain Vamana insert routine "is not robust" to insertion order: with a clustered insertion order "FreshVamana has about a 10% lower recall" than with uniformly random ordering (observed under distribution shift). — [CleANN PDF](https://arxiv.org/pdf/2507.19802v1)

**LR-RN (SIGIR eCom'26 workshop)**
- "under heavy update workloads, existing graph-based index repair strategies silently accumulate unreachable nodes ... affected products are silently excluded from search results"; LR-RN (Local Rewiring — Representative Neighbor) "reduces unreachable node growth by two thirds on standard ANN benchmarks, and arrests growth entirely on production-grade product catalog data, while keeping recall degradation within 1-3% across cumulative update cycles" (SIFT-1M, Deep-100K, Amazon-100K; updates up to 10% of dataset). An alpha sweep found roughly ~100 unreachable nodes at build time, growing to ~10,000 for alpha < 1.1 while "at alpha > 1.1, unreachable node counts remain" low. Compared against Native-RU (hnswlib replaced update) and cites FreshDiskANN/Wolverine as related. — [LR-RN paper](https://ceur-ws.org/Vol-4250/paper776.pdf)

**Open-source bug report and unreviewed benchmark**
- usearch (ISCC fork) issue: after remove()+add() churn, "surviving nodes can become unreachable from the HNSW graph"; contains(key) and get(key) succeed but search() with the exact vector never returns it; damage persists across save()/load(); cause: remove() is a lazy deletion that stamps the slot free and "does not repair the inbound links held by surviving nodes", and when freed slots are reused by new adds, bystander nodes are cut off; reproduced with stock Hamming/Tanimoto metrics. No upstream fix/status was found. — [usearch issue #8 (fork)](https://github.com/iscc/usearch/issues/8)
- VecOps-Bench (GitHub, "VLDB 2026 submission / under review", not peer-reviewed): 9.99M Cohere-Wikipedia 768-d vectors, each cycle deletes the 100K oldest and inserts 100K new, 10 cycles = 10% turnover, HNSW M=16/efC=128/ef=100. Recall@10 initial -> after 10 cycles: pgvector 83.13 -> 75.06 (-9.71), Milvus 97.84 -> 89.28 (-8.75), Chroma 88.99 -> 81.61 (-8.29), Weaviate 81.80 -> 79.06 (-3.35). Full delete+insert cycle time: Milvus 37 s, Weaviate 190 s, pgvector 1,395 s, Chroma 1,453 s. — [VecOps-Bench](https://github.com/debu-sinha/vecops-bench)

**Repair-trigger policy (preprint, v2 withdraws v1)**
- "When to Repair a Graph ANN Index" (Jul 2026): Vamana on SIFT-128 and Fashion-MNIST-784 under a bursty delete-heavy/insert-heavy stream with an exact live-set recall oracle. At matched repair budget, a signal-triggered local repair's tail-recall advantage over fixed-cadence consolidation "is indistinguishable from zero at every operating point, graph degree, and index scale. At several points the clock is better." "Recall is sharply concave in repair budget, and one consolidation captures over half of the achievable gain." The navigability probe "is not a leading indicator"; one control shows the trigger firing on insert-only streams (wasted consolidation). v1's positive claim came from an "interpolated baseline that was never executed". — [arXiv 2607.00728](https://arxiv.org/abs/2607.00728)

### Inferences
- Across sources the drift magnitude at ~5–10% churn per cycle is a few recall points after hundreds-to-thousands of cycles for plain hnswlib replace-updates; the systems-level benchmark shows 3–10 points after only 10% cumulative turnover in production DBs, suggesting DB-level tombstoning/segment behavior amplifies the effect beyond the pure-graph case (but that benchmark is unreviewed).
- The "alpha > 1" pruning relaxation recurs as the single most important knob for post-delete connectivity (FreshDiskANN, IP-DiskANN, MN-RU-gamma, LR-RN all converge on alpha ≈ 1.1–1.2).

### Gaps
- No paper titled "The Hidden Cost of Updates" was found; the closest academic match is MN-RU (arXiv 2407.07871).
- MN-RU's recall curves are figure-only; absolute recall values are not in the text.
- No peer-reviewed, cross-library head-to-head churn benchmark (hnswlib vs faiss vs DiskANN) was found for 2025–2026; the Big ANN streaming track is the closest.

## KQ4. Reverse-edge (in-neighbor) tracking approaches to fix stale inbound edges after updates

### Takeaway
Research systems avoid persistent in-neighbor lists (memory + locking cost) and instead recover in-neighbors on demand: by re-searching the deleted vector (IP-DiskANN, MERIT), by restricting to 2-hop neighborhoods (Wolverine+), by a lightweight topology index that locates affected vertices without a full scan (Greator), by lazily consolidating neighborhoods when a search encounters a tombstone (CleANN), or by building a transient reverse graph on GPU (GrAND); the only full-scan approach is FreshDiskANN's consolidation.

### Cited Findings
- Explicit in-neighbor lists rejected: "An obvious fix is to doubly-link the graph ... [but it costs memory and] locking complexity in a highly concurrent system. In practice, all these reasons make maintaining in-neighbors unacceptable." — [IP-DiskANN PDF](https://arxiv.org/pdf/2502.13826)
- Search-based recovery: IP-DiskANN runs GreedySearch(x_p, k=50, l_d=128) and takes visited nodes with an out-edge to p as the approximate in-neighbor set; larger l_d finds more in-neighbors (recall 91.8/92.6/92.9 at l_d=60/128/200, deletion time 1898/3160/4576 s on MSTuring-30M-Clustered). — [IP-DiskANN PDF](https://arxiv.org/pdf/2502.13826)
- MERIT: "bounded search-based recovery that combines a deleted vertex's outgoing neighbors with its readily searchable in-neighbors" plus "versioned-edge invalidation" to filter stale edges immediately and remove them progressively when adjacency lists are rewritten. — [MERIT abstract](https://arxiv.org/abs/2607.29173)
- Wolverine: plain Wolverine must "search all nodes in the graph to identify which nodes are affected" (complexity at least O(n·theta_d·ln n)); Wolverine+ restricts candidates to Hop2(p) (2-hop neighbors of the deleted point) and selects candidate in-neighbors for each p_out from there; Wolverine++ adds a geometric "monotonic search region" candidate filter; deletion is done in two stages, first removing in-edges of a batch in parallel (reducing thread competition), then repairing out-neighbors' monotonic paths. — [Wolverine PDF](https://vbn.aau.dk/ws/files/851508848/Open_Access_Article.pdf)
- Greator: "the system scans the entire index file to find affected vertices, causing excess unnecessary I/O"; fix: "A lightweight index topology identifies affected vertices efficiently, avoiding the full scan", then only affected vertices are modified in the index file. Reported 2.47x–6.45x higher update throughput than FreshDiskANN (arXiv version) / "up to 4.16x faster" continuous update integration (VLDB version). — [Greator arXiv](https://arxiv.org/abs/2503.00402); [PVLDB 19](https://www.vldb.org/pvldb/vol19/p495-yu.pdf)
- CleANN: "query-adaptive on-the-fly neighborhood consolidation" — when a best-first search encounters a tombstoned node from an in-neighbor v, it consolidates v's neighborhood then; "Early Stopping of Consolidations" avoids immediately removing a deleted node after a single in-neighbor detects it; "semi-lazy memory cleaning" removes stale nodes later while maintaining graph quality. Observed that clearing incoming edges in FreshVamana is a global batch operation that delays memory reuse. — [CleANN PDF](https://arxiv.org/pdf/2507.19802v1); [CleANN abstract](https://arxiv.org/abs/2507.19802)
- GrAND: "reverse edges are handled by building an on-demand reverse graph on the GPU. This identifies incoming edges without permanently duplicating the index." — [GrAND abstract](https://arxiv.org/abs/2608.21163)
- hnswlib's replaced-update: it repairs by pushing all two-hop neighbors to one-hop neighbors (O(R^3) edges), without explicit in-neighbor tracking (as characterized by IP-DiskANN); MN-RU reduces this to "only neighbors that include the deleted point in their lists" using mutual-neighbor information. — [IP-DiskANN PDF](https://arxiv.org/pdf/2502.13826); [MN-RU HTML](https://arxiv.org/html/2407.07871v1)
- DEG (Hezel et al.): keeps an undirected even-regular graph (so every edge is bidirectional by construction) with "guaranteed connectivity and therefore reachability of all vertices"; the 2023 paper left deletions for future work; a 2026 follow-up ("Dynamic Exploration Graph: A Novel Approach..." arXiv 2607.27640, metadata unverified) removes all SIFT1M vertices gradually and restores connectivity with a BFS that finds subgraphs reachable from other vertices missing an edge, reporting that BFS outperformed a pairwise RangeSearch check. — [DEG arXiv](https://arxiv.org/abs/2307.10479); [DEG follow-up PDF](https://arxiv.org/pdf/2607.27640)

### Inferences
- "Undirected graph" designs (DEG) sidestep the in-neighbor problem at the price of a fixed even degree and heavier edge-optimization; directed Vamana/HNSW designs instead pay a search per delete. No paper I found quantifies the memory cost of explicit in-neighbor lists at scale — the argument is made qualitatively.

### Gaps
- No source gives measured overhead of maintaining true bidirectional in-neighbor lists on Vamana/HNSW; the rejection is argued, not benchmarked.

## KQ5. Edge pruning under updates (RNG / alpha-pruning, keepPrunedConnections) and effects on update cost and recall

### Takeaway
Evidence is consistent that alpha > 1 (alpha-RNG, typically 1.1–1.2) is necessary for recall stability under deletes, that pruning is the dominant update cost (each delete can trigger many reprunes), and that adding too many edges during repair hurts high-recall operating points; no study isolating HNSW's keepPrunedConnections under churn was found.

### Cited Findings
- FreshDiskANN: alpha-RNG keeps an edge (p, p'') only if no retained p' satisfies d(p', p'') < d(p, p'')/alpha; "the graphs become denser as alpha increases"; Figure 3 sweeps alpha ∈ {1, 1.1, 1.2, 1.3} for build+update on SIFT1M/Deep1M and the text says alpha > 1 is what gives stability; the naive Policy B with alpha=1 pruning deteriorated. — [FreshDiskANN PDF](https://arxiv.org/pdf/2105.09613)
- IP-DiskANN: "alpha > 1 (e.g., 1.2) is critical for maintaining recall"; replacement edge count c trades recall vs prune cost (c=1..5: recall 91.0 -> 92.8, deletion time 2400 -> 3753 s, "due to an increase in the number of prunes per delete"). — [IP-DiskANN PDF](https://arxiv.org/pdf/2502.13826)
- Wolverine: FreshDiskANN's relaxed trimming "needs to connect more edges between the inserted nodes and their neighbors ... modifying the edge tables of a large number of nodes ... more thread contention", making its Insert_OPS 3.6–4.8x lower than HNSW+Wolverine++; HNSW's EdgeTrim reduces a node to < theta_d/2 when it exceeds theta_d (lowering average degree), whereas Wolverine++ only trims to <= theta_d, so average degree and recall rise after updates at some search-latency cost, tunable via delta_in (new in-neighbors per p_out, set to 32; candidate set 2x delta_in). Also, "indiscriminately adding edges to compensate for connectivity loss does not improve accuracy; instead, it can degrade performance in high-recall regions." — [Wolverine PDF](https://vbn.aau.dk/ws/files/851508848/Open_Access_Article.pdf)
- Greator: "Repairing affected vertices adds many new neighbors, which often triggers costly neighbor pruning"; fix is "similar neighbor replacement": connect each affected vertex to only a small number (typically one) of the deleted vertex's most similar out-neighbors. — [Greator arXiv](https://arxiv.org/abs/2503.00402)
- MN-RU: MN-RU-gamma uses alpha = 1.1 vs alpha = 1 for the alpha/beta variants and reaches better accuracy at equal time; LR-RN's alpha sweep shows unreachable nodes ~10,000 at alpha < 1.1 vs low counts at alpha > 1.1 on 100K-scale data. — [MN-RU HTML](https://arxiv.org/html/2407.07871v1); [LR-RN paper](https://ceur-ws.org/Vol-4250/paper776.pdf)
- HNSW's original heuristic neighbor selection includes a keepPrunedConnections option "which allows getting fixed number of connection per element" (backfilling discarded candidates to reach M). — [HNSW paper](https://arxiv.org/pdf/1603.09320)
- ParlayANN: batch insertion collects all (u,v) reverse edges for a batch, sorts so edges to the same existing v are contiguous, adds them without locks and prunes only vertices exceeding the degree bound — so pruning is batched once per batch per vertex rather than once per insert. — [ParlayANN PDF](https://arxiv.org/pdf/2305.04359)

### Inferences
- A practical rule emerging from these sources: keep alpha ≈ 1.1–1.2, cap the number of replacement edges per affected vertex (c ≈ 1–3), and batch reprunes, because reprune count (not distance computations per search) is what dominates delete cost.

### Gaps
- I found no measured study of HNSW keepPrunedConnections (on/off) under insert/delete churn; the only description is the original HNSW paper's parameter definition.

## KQ6. Concurrency and lock-free / parallel insertion algorithms (ParlayANN, concurrent HNSW variants, GPU, distributed) and their update throughput

### Takeaway
ParlayANN (PPoPP'24) removes per-vertex locks via prefix-doubling batch insertion with deterministic reverse-edge merging and scales past 100 threads (1.2x–28x over original implementations, with lock-based DiskANN/HNSW degrading beyond ~50 threads); CleANN is the first index claiming full concurrent insert/delete/search with 7–1200x search-throughput gains over FreshVamana at 56 hyperthreads; GrAND reports lock-free GPU adjacency updates. FreshDiskANN itself uses fine-grained per-node locks with near-linear insert scaling.

### Cited Findings
- FreshDiskANN: fine-grained per-N_out(p) locks; "insertion throughput scales near-linearly with threads"; StreamingMerge "scales near linearly with the number of threads" (merge with 40 threads ≈ half the time of 20). — [FreshDiskANN PDF](https://arxiv.org/pdf/2105.09613)
- ParlayANN: "most existing implementations tend to only scale well to tens of threads"; locks cause non-determinism ("different graphs due to lock acquisition order"). Techniques: prefix-doubling (insert points in exponentially growing batches, each batch searching a snapshot of the index built from prior batches; batch size capped at theta, with "2% of the input ... more than enough to utilize all threads"), and lock-free batch insertion/pruning (collect (u,v) reverse edges, deterministic semisort so edges to the same v are consecutive, prune only over-degree vertices). The prefix-doubling index "achieved similar quality as the sequentially-built index" at the same QPS. Results on BIGANN-1M (48 cores w/ hyperthreads): ~1.2x over DiskANN (which scales to 30–60 threads then degrades due to locks), 1.4x over HNSW (which "suffers from similar locking-related issues"), 12x over HCNNG, 28x over PyNNDescent; builds billion-scale indexes (Table 1 lists 100M-scale build times in hours; e.g., HNSW .35/.37/.94 h across three datasets). The library is deterministic. — [ParlayANN PDF](https://arxiv.org/pdf/2305.04359); [PPoPP'24 listing](https://ppopp24.sigplan.org/details/PPoPP-2024-papers/9/ParANN-Scalable-and-Deterministic-Parallel-Graph-Based-Approximate-Nearest-Neighbor-)
- CleANN: targets "insertions, deletions and searches running at the same time"; components: workload-aware linking (GuidedBridgeBuild: adds bridge edges among "cousin" nodes in the search tree during insert/search to counter distribution shift and insertion-order sensitivity), on-the-fly neighborhood consolidation, semi-lazy memory cleaning. "In the in-memory setting using 56 hyper-threads, with updates running concurrently with searches, our searches are 7–1200x faster than that of FreshVamana, while maintaining similar query quality"; single-thread it is "1.2x and 3x faster for searches and updates". Evaluated on 7 datasets; query quality at least as good as a static index built on the same data. — [CleANN PDF](https://arxiv.org/pdf/2507.19802v1); [CleANN abstract](https://arxiv.org/abs/2507.19802)
- Wolverine: 64 update threads on an AMD EPYC 7K62; two-stage batch deletion (parallel in-edge removal first) "making the deletion of in-edges more efficient"; Delete_OPS 2.7–11.0x and Insert_OPS 3.6–4.8x higher than in-memory FreshDiskANN (UR=1%, w=10M for SWQ; 9 datasets incl. SIFT1M/10M/100M, GIST1M, DEEP1M/10M/100M, SPACEV10M); Search_OPS 1.4–1.7x faster on small datasets but slower on GIST1M and on large datasets. — [Wolverine PDF](https://vbn.aau.dk/ws/files/851508848/Open_Access_Article.pdf)
- GrAND (GPU): "lock-free find-and-replace strategy for parallel adjacency-list updates", batch-consolidated repair; 2.2x–8.7x over SVFusion and 6.5x–25.4x over FreshDiskANN-GPU. — [GrAND abstract](https://arxiv.org/abs/2608.21163)
- jVector in OpenSearch (vendor blog, not peer-reviewed): "concurrent, lock-free vector graph construction that achieves near-perfect linear scalability while maintaining search quality", snapshot-based coordination so a new node's search sees both a graph snapshot and in-progress insertions; table shows 163,755 ms -> 25,297 ms (6.5x) for unquantized build (configuration truncated). — [OpenSearch blog](https://opensearch.org/blog/breaking-the-single-thread-bottleneck-concurrent-vector-graph-construction-in-opensearch)
- hnswlib: add_items is thread-safe with other add_items but "not with knn_query". — [hnswlib README mirror](https://codegraph.jelmer.uk/hnswlib/0.9.0-2/README.md)

### Inferences
- Lock-free designs so far are batch-oriented (ParlayANN, GrAND): determinism and lock-freedom come from processing a batch against a snapshot; fully concurrent single-point updates with deletes (CleANN) still appear to use some synchronization (details not extracted).

### Gaps
- I did not find a peer-reviewed lock-free single-insert HNSW paper; Pyramid/distributed graph update throughput numbers were not located within the call budget.
- CleANN's per-dataset speedup breakdown and memory overhead were not extracted from the PDF text.

## KQ7. Batch vs. single update strategies and background compaction/rebuild policies (when to rebuild, how systems decide)

### Takeaway
Published systems use simple threshold triggers (consolidate when deleted fraction reaches 1–30% of the index, or when the in-memory delta reaches a size cap such as 30M points), and the one study that tested a smarter, signal-driven trigger found it no better than a clock at equal budget; batch size trades update throughput against recall (large batches hurt accuracy, Greator), and in-place methods eliminate the recall sawtooth and the merge-time 10x throughput drop.

### Cited Findings
- FreshDiskANN: consolidate "after accumulating a non-trivial number of deletions (say 1-10% of the index size)"; StreamingMerge triggers when TempIndex memory exceeds cap (30M points); inserts throttled (3,500/s ramp-up; 1,800/s steady state) so the TempIndex does not exceed 30M before the previous merge finishes; merge threads T tuned against search-latency impact. Rebuild cost: ~190,000 s for an 800M index vs ~16,000 s merge. — [FreshDiskANN PDF](https://arxiv.org/pdf/2105.09613)
- IP-DiskANN: lightweight dangling-edge consolidation at t = 10/20/30% deleted, with recall 92.6/92.5/92.2 and deletion time 3207/3146/3136 s — more frequent sweeps slightly help recall at small cost. — [IP-DiskANN PDF](https://arxiv.org/pdf/2502.13826)
- BigANN'23 baseline: DiskANN runs consolidation "when the index is close to running out of space for inserting new vectors"; "accumulating a large number of deletes leads to a drop in index recall" until consolidation. — [BigANN'23 results](https://arxiv.org/html/2409.17424v1)
- Greator: "Graph-based ANNS systems use batch updates to raise update throughput under frequent insertions and deletions, but large batches reduce search accuracy"; small-batch updates suffer a full index-file scan and pruning storms; Greator's localized approach gives 2.47x–6.45x (arXiv) / up to 4.16x (VLDB) higher update throughput than FreshDiskANN. — [Greator arXiv](https://arxiv.org/abs/2503.00402); [PVLDB 19](https://www.vldb.org/pvldb/vol19/p495-yu.pdf)
- CleANN: FreshVamana throughput "can decrease by more than 10x during consolidation but consolidation is required to achieve good Search recalls"; CleANN replaces global consolidation with search-triggered local consolidation plus semi-lazy cleaning. — [CleANN PDF](https://arxiv.org/pdf/2507.19802v1)
- Wolverine: tombstone-only (Pseudo) deletion degrades Search_OPS and Insert_OPS to ~25% after 100 rounds at 5% churn, "periodic rebuilding is required". — [Wolverine PDF](https://vbn.aau.dk/ws/files/851508848/Open_Access_Article.pdf)
- MN-RU: a "backup index" rebuilt every four iterations (tau = 40,000) gives significantly fewer unreachable points than continuous HNSW-RU on GIST. — [MN-RU HTML](https://arxiv.org/html/2407.07871v1)
- When-to-repair study: at matched budget, navigability-signal-triggered repair is not better than fixed cadence; "one consolidation captures over half of the achievable gain"; the probe fired on insert-only streams (wasted work). — [arXiv 2607.00728](https://arxiv.org/abs/2607.00728)
- Yi: "Existing out-of-place graph-based methods update slowly because they periodically merge update batches into the graph"; claims 1.75x update throughput at 73% of peak memory vs SOTA on 800M. — [Yi abstract](https://arxiv.org/abs/2607.15576)
- LSM-VEC: distributes the proximity graph across LSM-tree levels to support "out-of-place vector updates" on disk; claims >66.2% memory reduction and higher recall/lower latency than existing disk-based systems (baseline unnamed on the abstract page). — [LSM-VEC abstract](https://arxiv.org/abs/2505.17152)
- Cosmos DB: maintenance split into IndexBuilder (synchronous-ish per update) and IndexVacuum (background stale-edge removal + defragmentation), frequency "depends on embedding size, document count, and spare throughput (RU/s)". — [Cosmos DB blog](https://devblogs.microsoft.com/cosmosdb/azure-cosmos-db-with-diskann-part-4-stable-vector-search-recall-with-streaming-data/)
- Segment/merge-based alternatives (Lucene-style) are criticized by IP-DiskANN as causing CPU/memory spikes on merge and less efficient multi-segment search (citing Apache Lucene issues "Make HNSW merges faster" / "cheaper on heap"). — [IP-DiskANN PDF](https://arxiv.org/pdf/2502.13826)

### Inferences
- No source offers a principled, validated adaptive rebuild policy; the state of practice is fixed thresholds (deleted-fraction or delta-size), and the only test of an adaptive trigger was negative. The strongest lever found is to make repair cheap enough (in-place/localized) that the trigger question matters less.

### Gaps
- No paper quantifies the recall "sawtooth" amplitude between consolidations as a function of deleted-fraction threshold beyond IP-DiskANN's 10/20/30% sweep.

## KQ8. What the NeurIPS BigANN 2023 streaming track (and later tracks) reveals about which update algorithms win, and the numbers

### Takeaway
On the corrected scoring, the streaming track (MSTuring-10M, 8 GB, 1 h, 1,280-batch runbook with ~4:4:1 insert:delete:search) was won by PyANNS — stock DiskANN streaming index plus 8-bit scalar quantization (recall@10 0.8865) — ahead of hwtl_sdu_anns_stream (0.7693), the DiskANN baseline (0.7218), CUFE (0.6481) and Puck (0.0921); the originally announced numbers (e.g., Puck 0.985) were wrong because a caching bug scored only the first snapshot rather than the runbook average.

### Cited Findings
- Setup: 10M-vector slice of MS Turing; final runbook of 1,280 batches over 5 rounds (10M points clustered into 64 clusters; each round 256 steps of insert/search/delete/search per cluster), roughly 4:4:1 insert:delete:search; memory capped at 8 GB; whole runbook within 1 hour; scored by recall averaged over runbook checkpoints (the paper is internally inconsistent, one passage says max recall). — [BigANN'23 results](https://arxiv.org/html/2409.17424v1)
- Baseline: DiskANN streaming in-memory index (FreshDiskANN ideas): eager inserts, lazy deletes, consolidation reclaims space and repairs the graph; recall drops as deletes accumulate and recovers after consolidation. — [BigANN'23 results](https://arxiv.org/html/2409.17424v1)
- Entries: Puck (Baidu) — four-level hierarchical cluster index (VQ then PQ), inserts extend the build, deletes via a flag array filtered at query time; PyANNS (Zihao Wang, SJTU) — "the out-of-the-box DiskANN index with 8-bit scalar quantization, which the authors say leaves more time to search deeper into the graph"; hwtl_sdu_anns_stream and CUFE not described. — [BigANN'23 results](https://arxiv.org/html/2409.17424v1)
- Leaderboard, recall@10 original (incorrect) -> corrected: puck 0.985 -> 0.0921; hwtl_sdu_anns_stream 0.9674 -> 0.7693; pyanns 0.9597 -> 0.8865; diskann 0.883 -> 0.7218; cufe 0.8189 -> 0.6481. "More than six months after the competition, the organizers found a caching error. The original results reflected recall at the first runbook snapshot rather than the average over the whole runbook." — [BigANN'23 results](https://arxiv.org/html/2409.17424v1)
- Filter track (for context): ParlayANN ~37,900 QPS public / 37,671 private, Puck ~19,200, hwtl ~15,059; top entry >11x the Faiss baseline. — [BigANN'23 results](https://arxiv.org/html/2409.17424v1)
- The arXiv report (Sep 2024) was subsequently published in the NeurIPS 2025 Datasets & Benchmarks track. — [NeurIPS 2025 proceedings](https://proceedings.nips.cc/paper_files/paper/2025/hash/63092d79154adebd7305dfd498cbff70-Abstract-Datasets_and_Benchmarks_Track.html)
- Reuse of the track's runbooks: IP-DiskANN's SlidingWindow/ExpirationTime/Clustered runbooks and Cosmos DB's evaluation both use the BigANN streaming framework; IP-DiskANN notes its implementation is consistent with the BigANN'23 FreshDiskANN code (v0.5.0.rc3.post1). — [IP-DiskANN PDF](https://arxiv.org/pdf/2502.13826); [Cosmos DB blog](https://devblogs.microsoft.com/cosmosdb/azure-cosmos-db-with-diskann-part-4-stable-vector-search-recall-with-streaming-data/)

### Inferences
- The corrected results favor graph indexes with proper delete repair (DiskANN-based entries) over cluster/flag-array deletion (Puck's corrected 0.09 average recall indicates the flag-array approach without graph repair — or an evaluation interaction — collapsed over the runbook; the paper does not diagnose this).
- Under the 8 GB / 1 h constraint, the winning lever was quantization that frees time for deeper search, not a new update algorithm; this is consistent with the 2025 in-place work being published after the challenge.

### Gaps
- Per-entry query/update times and the full recall-over-time curves are not in the paper text; the paper does not state why Puck's corrected recall is so low.
- I did not find a later BigANN streaming-track edition (2024–2026) with published results within the call budget.
