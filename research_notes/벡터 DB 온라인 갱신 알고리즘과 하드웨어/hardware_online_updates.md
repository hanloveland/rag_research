# Hardware and Systems-Architecture Work Targeting Online Updates of Vector/ANN Indexes (2021–2026)

Scope note: this file covers hardware- and systems-level work (GPU, SSD/NVMe/SPDK/io_uring, in-storage/NDP, CXL, persistent memory, PIM, RDMA/disaggregated memory, many-core) whose contribution touches the *update* path of a vector index: insertion, deletion, construction/rebuild, rebalancing, compaction. Peer-review status is marked for each entry: [PR] = peer-reviewed venue, [preprint] = arXiv only at the time of research, [vendor] = vendor documentation/blog, [thesis] = dissertation.

Headline finding up front: the only hardware feature that has been *deliberately* exploited for the update path at billion scale in a peer-reviewed system is the raw NVMe block interface via SPDK (SPFresh, SOSP'23) and fixed-size-record/overprovisioned page layouts on NVMe SSDs via io_uring (OdinANN, FAST'26; NAVIS, 2026 preprint). GPU work on *dynamic* (insert/delete) graph indexes exists only as 2026 preprints (Jasper, ETALE, GrAND, SIVF) plus one VLDB'26 CPU–GPU–disk system (SVFusion). In-storage (SmartSSD/NDP), CXL, and PIM designs for ANN are, without exception among the sources found, search-only: none performs graph insertion, edge repair, or rebalancing inside the device. Persistent-memory crash-consistent HNSW exists as one 2025 journal paper (P-HNSW). That asymmetry (search accelerated everywhere; updates accelerated only on CPU+SSD and, recently, GPU) is itself the central result.

## KQ1. GPU index construction and GPU incremental insert/delete (CAGRA, GGNN, Faiss GPU IVF, GPU HNSW construction, cuVS extend)

### Takeaway
GPU bulk construction is mature (CAGRA 2.2–27× faster than CPU HNSW; GGNN builds SIFT1B in 33–79 min on 8 V100s; cuVS/Faiss IVF builds 4.7× faster), but until 2026 every GPU graph index was effectively static and required rebuilds. A cluster of 2026 preprints (Jasper, ETALE, GrAND, SIVF) and one VLDB'26 paper (SVFusion) now provide GPU-native streaming insert/delete, with reported insertion throughput in the 10^5–10^6 vectors/s range on A100-class GPUs, but all are capacity-bound by HBM (~100–200M vectors per GPU) and most alternate update and query phases rather than running them concurrently.

### Cited Findings

**CAGRA (bulk build, static) [PR: ICDE 2024; arXiv 2308.15136]**
- "CAGRA: Highly Parallel Graph Construction and Approximate Nearest Neighbor Search for GPUs" (Ootomo, Naruse, Nolet, Wang, Feher, Wang). Construction is 2.2–27× faster than CPU HNSW, 1.1–31× faster than GGNN, 1.0–6.1× faster than GANNS; the measured construction time includes memory allocation, dataset load and data movement. Build starts from an initial k-NN graph produced by IVF-PQ or NN-Descent, then prunes; it explicitly "diverges from the iterative insert-update method used by HNSW graphs on CPUs". — [arXiv 2308.15136](https://arxiv.org/abs/2308.15136)
- Tagore (SIGMOD'26) characterizes CAGRA as optimizing pruning but leaving graph initialization as a bottleneck, and says "scalability with large datasets also remains a challenge". — [Tagore, arXiv 2508.08744](https://arxiv.org/abs/2508.08744)

**cuVS vendor documentation on build and extend [vendor]**
- CAGRA indexing guide: "The dataset must be in GPU memory during index build"; IVF-PQ initial-graph build can run in batches so CAGRA can train on datasets larger than GPU memory, but "The iterative builder requires the aligned dataset to fit in GPU memory"; scratch headroom of 20% (IVF-PQ) or 30% (NN-Descent/iterative) is recommended; worked example 1M×1024-d fp32, degree 64 ≈ 4,520 MB build peak. On `extend`: the caller concatenates old and new vectors into one padded device dataset and "extend only grows the graph and rebinds the index to that view". No deletion API is described; filtered search is the closest mechanism. The page does not use the term "dynamic batching"; it documents `max_queries` ("Maximum number of queries searched concurrently") and "persistent search" (a resident kernel) for throughput. — [cuVS CAGRA indexing guide](https://docs.nvidia.com/cuvs/user-guide/api-guides/indexing-guide/cagra)
- Multi-GPU Python API: `cagra.extend` takes new vectors that "MUST be in host memory (CPU)". Go API exposes `ExtendIndex` on a row-major device tensor. — [cuVS multi-GPU CAGRA](https://docs.nvidia.com/cuvs/api-reference/python-api-neighbors-mg-cagra); [cuVS Go API](https://docs.nvidia.com/cuvs/api-reference/go-api-cagra)
- CAGRA→HNSW conversion: the resulting HNSW index "is mutable and can be extended with additional vectors only when the CPU hierarchy is used"; the GPU-hierarchy variant is immutable. — [hipVS/cuVS hnsw docs](https://rocm.docs.amd.com/projects/hipVS/en/latest/autoapi/cuvs/neighbors/hnsw/index.html); [cuVS C++ neighbors](https://docs.rapids.ai/api/cuvs/stable/cpp_api/neighbors/)
- KDB-X cuVS module: `cagra.insert` "Build or extend the index with vectors"; indexes are in-memory and not persisted automatically. — [KDB-X cuVS reference](https://code.kx.com/kdb-x/modules/cuvs/reference.html)
- NVIDIA cuVS product page claims cuVS "enables real-time updates to search indexes by dynamically integrating new embeddings and data without rebuilding the entire index" (marketing copy; no index type or limits stated). — [NVIDIA cuVS](https://developer.nvidia.com/cuvs)

**Faiss + cuVS IVF/CAGRA build numbers [vendor]**
- NVIDIA: HNSW graphs "sometimes taking hours or days at scale" on CPU; CAGRA graphs "can be built up to 12x faster" and exported as HNSW for CPU serving; IVF-PQ and IVF-Flat built "up to 4.7x faster" with cuVS than classic Faiss GPU. Benchmark: Deep100M (100M × 96-d) at 95% recall. — [NVIDIA blog](https://developer.nvidia.com/blog/enhancing-gpu-accelerated-vector-search-in-faiss-with-nvidia-cuvs)
- Meta: CAGRA build "up to 12.3x" faster than CPU HNSW, search latency up to 4.7× lower; IVF build 4.7× faster, search latency up to 8.1× lower. — [Meta Engineering, May 2025](https://engineering.fb.com/2025/05/08/data-infrastructure/accelerating-gpu-indexes-in-faiss-with-nvidia-cuvs/)
- Milvus 2.4 CAGRA integration blog reports CAGRA building roughly 10× faster than alternatives (vendor, different setup). — [Zilliz](https://zilliz.com/blog/Milvus-introduces-GPU-index-CAGRA)
- Zilliz Cloud's answer to GPU real-time ingestion is architectural, not GPU-native: new embeddings land in a small growing segment searched by brute force while background processes merge/index into sealed segments. — [Zilliz FAQ](https://zilliz.com/ai-faq/how-does-blackwell-enable-realtime-embedding-ingestion-in-zilliz-cloud)

**GGNN (bulk build, static) [PR: IEEE TBD 2023; arXiv 1912.01059]**
- Build times: SIFT1M 21.8 s (9.2 s fast config) on one V100; GIST1M 11.9 min; SIFT1B 78.6 min (128 shards, 152 GiB) or 33.4 min (16 shards, 75 GiB) on 8 GPUs; DEEP1B 47.5 min (32 shards, 90 GiB) on 8 GPUs. Paper cites FAISS construction at 4–24 h on DEEP1B and ~100 h for HM-ANN billion-scale graphs. Construction is a batch merge of sub-graphs; no incremental insertion is described (the text only says build time matters for "dynamically growing or changing datasets"). Internal inconsistency: intro says billion-scale build "<2 hours", conclusion "<1 hour". — [GGNN ar5iv](https://ar5iv.labs.arxiv.org/html/1912.01059)

**GPU HNSW/NSG construction (2025–2026)**
- CMANNS [PR: SIGMOD 2026, DOI 10.1145/3802027] (Huan, Yao, Gu, Chen, Yang, Ma, Wang, Zhang, Xi, Chen, Tian; Tsinghua MADSys): "compute–memory disaggregation" — distance evaluation recast as high-arithmetic-intensity GEMMs on Tensor Cores with fused epilogues; memory-intensive phases use shared-memory staging and warp-cooperative gathers/scatters; device-sized shards stream through a double-buffered pipeline, only compact adjacency written back. Preserves the construction rules/query procedure of NSG and HNSW. End-to-end build time reduced up to 13.05× vs FAISS and 2.20× vs FLASH across seven benchmarks; cache hit rate +58.7%. No incremental insert/delete reported. — [CMANNS page (PDF linked)](https://madsys.cs.tsinghua.edu.cn/publication/cmanns-gpu-accelerated-graph-index-construction-for-anns-via-computememory-disaggregation/)
- Tagore [PR: SIGMOD 2026; arXiv 2508.08744] (Li, Ke, Zhu, Yu, Zheng, Gao): GPU NN-Descent variant "GNN-Descent" (two-phase descent) for k-NN graph init, "CFS" pruning via two GPU kernels, and an asynchronous GPU–CPU–disk framework with cluster-aware caching for datasets exceeding GPU memory; targets refinement-based graphs (NSG, Vamana). 1.32×–112.79× speedup across 7 datasets. Incremental updates not addressed. — [arXiv 2508.08744](https://arxiv.org/abs/2508.08744)
- GRNND [preprint, Oct 2025]: GPU-parallel RNN-Descent; 2.4–51.7× over existing GPU methods, 17.8–49.8× over CPU. — [arXiv 2510.02774](https://www.arxiv.org/abs/2510.02774)
- CPU counterpoint, Flash [PR: SIGMOD 2025; arXiv 2502.18113] (Wang, Wu, Ke, Gao, Zhu, Zhou): distance computation dominates graph-index construction; compact coding (Flash) exploits SIMD and reduces random memory accesses; 10.4×–22.9× construction speedup on eight datasets of 10M–1B vectors. Notes GPU re-implementations of HNSW reach "an order of magnitude speedup compared to single-thread CPU-based construction, but ... GPU-specific limitations reduce their practicality". Offline build only. — [arXiv 2502.18113](https://arxiv.org/abs/2502.18113)

**GPU dynamic (insert/delete) indexes — the 2026 wave**
- Jasper [preprint, Jan–Jul 2026, v5] "GPU-Accelerated ANNS: Quantized for Speed, Built for Change" (McCoy, Wang, Pandey). GPU Vamana with batch-parallel construction enabling "lock-free streaming insertions": beam searches run independently, candidate edges are accumulated and sorted by target vertex, pruning applied per vertex, all fused into fixed GPU kernels. GPU RaBitQ quantization (up to 8× memory reduction). Hardware: NVIDIA A100 80 GB, CUDA 12.9; CPU baseline Xeon Gold 5218 (32c/64t). Build times (s; Jasper / CAGRA / ParlayANN-CPU / GANNS): BigANN-100M 327.7 / 1323.3 / 1418.2 / DNF; Deep-100M 296.2 / 825.6 / 4336.9 / DNF; Gist-1M 12.2 / 14.1 / 210.6 / 151.9; OpenAI-ArXiv-2.3M 89.0 / 127.8 / 1379.4 / 899.2; Text2Image-10M 24.3 / 619.2 / 184.0 / 1017.4. Peak bulk construction ≈1,179K inserts/s on BigANN. Incremental insertion on Deep falls from 814K/s at 5% full to 247K/s at 99% full. Batch-size sensitivity: BigANN-10M 233K/s at 0.5% batches → 753K/s at 16% then plateau. Inserts and queries alternate in phases (cannot run concurrently); new vectors are searchable only after their batch completes, and the delay is not quantified. Deletions follow FreshDiskANN's mark/consolidate/compact; mark ≈10^8 vertices/s, consolidate ≈10^4 tombstones/s; after deleting 10% + consolidating, BigANN-10M recall@10 0.986→0.988, QPS 575K→564K; Gist-1M recall 0.922→0.925 but QPS 54.5K→42.5K because average degree rose 24.4→30.6. 100M builds use ~72 GB of the A100's 80 GB; "largest GPUs handle roughly 200M vectors"; scaling beyond GPU memory listed as open. Query throughput up to 1.84× CAGRA; 10–74× faster than BANG. — [arXiv 2601.07048](https://arxiv.org/abs/2601.07048); [HTML v5](https://arxiv.org/html/2601.07048v5)
- ETALE [preprint, Jun 2026] "ETALE: Evolving Topology with Accelerated Lock-free Execution for Dynamic Graph ANN Search on GPUs" (Dongfang Zhao). Lock-free copy-on-write slab graph; deletion state and adjacency share one atomically published word → claimed "deletion-monotonicity invariant" and GPU memory reclaim that grows sublinearly with accumulated deletions. Under continuous churn, index maintenance takes hundreds of ms per round at recall > 0.95; 4.8–8.8× faster than CAGRA per-window rebuild, 1.8–2.5× faster than Tagore, 3.3–147× faster than CPU dynamic indexes (DIGRA, HNSW); memory stays bounded "whereas tombstone-only systems grow indefinitely". Absolute throughput, GPU model, dataset names not in abstract. — [arXiv 2607.02543](https://arxiv.org/abs/2607.02543)
- GrAND [preprint, Aug 2026] "GrAND: GPU-based Dynamic Graph Indexes for ANN Search" (Venkatasubba, Deshpande, S, Vedurada). GPU-native dynamic updates for Vamana and CAGRA: consolidates graph repair across a batch to remove redundant pruning, lock-free find-and-replace for parallel adjacency updates, and on-demand reverse graph on GPU for in-place deletion (instead of a permanently stored reverse index). 2.2–8.7× workload throughput over SVFusion and 6.5–25.4× over a GPU adaptation of FreshDiskANN, on seven datasets / five streaming workloads. — [arXiv 2608.21163](https://arxiv.org/abs/2608.21163)
- SIVF [preprint, Jan–Mar 2026] "SIVF: GPU-Resident IVF Index for Streaming Vector Search" (Dongfang Zhao). Problem statement: GPU IVF lists sit in pre-allocated contiguous buffers to preserve coalescing, so updates "necessitate expensive CPU-GPU data transfers ... causing system latency to spike from milliseconds to seconds"; tombstones give logical deletion only and do not reclaim space. SIVF uses conflict-free slab allocation and coalesced search over non-contiguous memory; integrated into Faiss; 12-GPU cluster aggregate ingestion 4.07M vectors/s and deletion 108.5M vectors/s with near-linear scaling. — [arXiv 2601.11808](https://arxiv.org/abs/2601.11808)
- SVFusion [PR: PVLDB 19(5):1074–1087, 2026; arXiv 2601.08528] (Peng, Yang, Xie, Sun, Shou, Chen, Chen; Zhejiang Univ./Huawei). CPU–GPU–disk hierarchical index: GPU (extends CAGRA, cuVS 24.02) holds hot vectors/subgraphs uncompressed with compact device IDs; CPU holds the full graph; cold vectors spill to disk. Insert: GPU search finds candidates (on-demand transfers), CPU reorders candidates with a detour-count heuristic and adds reverse edges. Delete: lazy bitset; localized repair when >50% of a vertex's neighbors are deleted (≤8 edges added per affected vertex); global consolidation asynchronously on a snapshot at ~20% deletion ratio. Modified neighbor lists are versioned on CPU and pushed to GPU in asynchronous batches; fine-grained R/W locks + bounded multi-version snapshots; GPU queries hitting a version conflict fall back to CPU. Hardware: A100 40 GB PCIe 3.0, 2× Xeon Gold 5218, 376 GB DRAM. Datasets: Wikipedia 35M×768, MSMARCO 101M×768, MSTuring 200M×100, Deep1B, Text2Image 100M×200. Results: up to 9.5× search and 71.8× insertion throughput vs FreshDiskANN; averages 20.9× search and 3.5× insertion throughput over FreshDiskANN and HNSW; latency 1.3–50.7× lower; Recall@10 91–96%; at 10K QPS, p99 16.5 ms search / 45.3 ms insert vs baselines >900 ms. Disk-extended Deep1B: construction 5.26× faster than DiskANN, 2.3× throughput. CPU–GPU transfer is the largest insert cost (45.4%); disk merging is the main bottleneck of the disk-tier build. — [arXiv 2601.08528](https://arxiv.org/html/2601.08528v1); [PVLDB PDF](https://www.vldb.org/pvldb/vol19/p1074-yang.pdf)
- Helmsman [PR: OSDI'26; arXiv 2606.13145] (Huang et al., deployed at RedNote/Xiaohongshu): lists "slow index construction" as a problem of clustering-based ANNS and answers it with "GPU-accelerated pipelines of construction" enabling "billion-scale index (re)builds within hours"; 40 machines replace ~35,000 cores and 0.35 PB DRAM; >90% hardware-cost savings. Updates are handled by (re)builds; no incremental update detail in abstract. A related industrial SPANN note states single-node CPU-only construction "incurs a heavy expenditure of time, violating the freshness of services". — [arXiv 2606.13145](https://arxiv.org/abs/2606.13145)

### Inferences
- GPU dynamic indexing has moved from "rebuild per window" (CAGRA, GGNN, Tagore, CMANNS) to true streaming inserts only in 2026, and only as preprints except SVFusion; none has been independently benchmarked against cuVS's own `extend` path.
- The GPU update designs converge on the ParlayANN pattern (search on an immutable snapshot, group candidate edges by target vertex, prune per vertex, no locks); the GPU-specific novelty is memory management (slab allocators, copy-on-write words, on-demand reverse graphs) rather than new graph algorithms.
- Deletion consolidation (10^4 tombstones/s in Jasper) is 4 orders of magnitude slower than marking (10^8/s), so GPU indexes still defer the expensive part of deletion exactly as FreshDiskANN does on SSD.

### Gaps
- No source gives CAGRA `extend` quality degradation or rebuild-trigger guidance; the cuVS docs are silent on it.
- No billion-scale CAGRA or NN-Descent build benchmark was found; published CAGRA comparisons use ≤100M datasets.
- ETALE, SIVF, GrAND abstracts omit GPU model, dataset names and absolute throughput; full texts were not read.
- No source reports energy for GPU index updates.

## KQ2. SPFresh (SOSP'23) and successors: which hardware features (SPDK, in-place SSD block updates, NVMe) are exploited and the numbers; follow-ups toward computational storage

### Takeaway
SPFresh is the one peer-reviewed billion-scale update system that is explicitly built on SPDK's raw NVMe block interface with append-only postings and last-block rewrites; its successors (OdinANN FAST'26, Yi 2026 preprint, NAVIS 2026 preprint, PipeANN OSDI'25) stay on the host and exploit io_uring, fixed-size record layouts, space overprovisioning, and decoupled vector/edge files on NVMe SSDs. No follow-up pushes the update path into a SmartSSD or near-data processor.

### Cited Findings

**SPFresh [PR: SOSP 2023, DOI 10.1145/3600006.3613166; arXiv 2410.14452]** (Xu, Liang, Li, Xu, Chen, Zhang, Li, Yang, Yang, Yang, Cheng, Yang; USTC + MSRA)
- Mechanism: In-place Updater appends a new vector to the tail of its nearest posting; version map tracks deletions and replicas. Local Rebuilder: when a posting exceeds its length limit it first garbage-collects deleted vectors, then splits with balanced clustering; merges postings that fall below a lower threshold; LIRE reassigns only boundary vectors in neighbouring postings, confirmed by compare-and-swap on the version map. — [SPFresh HTML](https://arxiv.org/html/2410.14452v1)
- Storage engine ("Block Controller"): a user-space engine built on SPDK using the raw NVMe block interface, bypassing the legacy storage stack; postings are append-only; `APPEND` reads and rewrites only the last block (not the whole posting) and then atomically updates an in-memory block mapping (~40 B per posting). The paper says APPEND "significantly reduces read/write amplification compared with posting-level read-modify-write" but gives no numeric write-amplification value. — [SPFresh HTML](https://arxiv.org/html/2410.14452v1)
- Setup: Azure Lsv3 VM, 16 vCPUs (Xeon Platinum 8370C), 128 GB DRAM, locally attached NVMe (model not named; Azure guarantees 400K IOPS). Datasets SIFT1B (128-d uint8) and SPACEV1B (100-d int8). Workloads A/B: 100M subsets, 1% of vectors deleted and re-inserted daily for 100 days; Workload C: 1B scale, 20 days at 1%/day. Baselines: DiskANN (global streaming merge every 30M vectors) and SPANN+ (append-only, no split/reassign). DiskANN could not run 1B fresh updates on this machine. — [SPFresh HTML](https://arxiv.org/html/2410.14452v1)
- Results (100M, 100 days): P99.9 search latency stays ≈4 ms; DiskANN exceeds 20 ms during global rebuilds; SPANN+ rises from 4 ms to >10 ms; average P99.9 latency 2.41× lower than DiskANN; average insert latency 1.5 ms; >600 inserts/s per insert thread; only 0.4% of insertions trigger rebalancing (avg 2 splits per trigger, max 160, cascade length 3); merges are 0.1% of updates; each rebalance evaluates ~5,094 vectors and reassigns ~79. Memory < 20 GB over 100 days (5.30× lower than baselines); DiskANN needed +60 GB for streaming merge and +15 GB for a second index. Global rebuild costs (Table 1): DiskANN 1100 GB/32 cores/2 days (or 64 GB/16 cores/5 days); SPANN 260 GB/45 cores/4 days. — [SPFresh HTML](https://arxiv.org/html/2410.14452v1)
- Billion-scale stress test: ~4K search QPS and 2K update QPS with 15 cores on one SSD; SPFresh saturated the SSD's IOPS (above the 400K guarantee); memory ~74 GB, CPU ~1300%; recall stayed above 0.862 (uniform) and 0.807 (skewed) searching 64 postings. Recall of SPFresh and SPANN+ rises gradually over the 100 days; DiskANN recall declines over time. Lock contention < 1%. Conclusion: single-node design as the foundation for a future distributed version. — [SPFresh HTML](https://arxiv.org/html/2410.14452v1); [MSR SOSP PDF](https://microsoft.com/en-us/research/uploads/prod/2023/08/SPFresh_SOSP.pdf)
- Third-party critiques: LSM-VEC reports SPFresh reaches only ≈0.75 Recall10@10 after initial construction because of coarse cluster granularity. — [LSM-VEC](https://arxiv.org/html/2505.17152v1). Yi reports SPFresh at 1.2K QPS vs Yi 4.8K on DEEP100M and starting recall 67.8%. — [Yi](https://arxiv.org/abs/2607.15576). OdinANN reports SPFresh reads 198 pages per search vs OdinANN's 41, and OdinANN achieves 62.1% of SPFresh's median latency with ~15% higher accuracy; SPFresh at 1B shows >200 GB memory and P99 spikes. — [OdinANN PDF](https://storage.cs.tsinghua.edu.cn/papers/fast26-odinann.pdf)

**OdinANN [PR: FAST'26, pp. 133–147]** (Hao Guo, Youyou Lu; Tsinghua) — "Direct Insert for Consistently Stable Performance in Billion-Scale Graph-Based Vector Search"
- Motivation measured against DiskANN buffered insert: merge raises frontend median search latency to 1.54×; merging 3% of vectors into a billion-scale index needs 125 GB; merge throughput capped at ~3000 QPS regardless of batch size because neighbor finding via on-disk ANNS "can not be batched efficiently"; index rebuild takes days at billion scale. — [OdinANN PDF](https://storage.cs.tsinghua.edu.cn/papers/fast26-odinann.pdf)
- Hardware co-design: graph stored as fixed-size records on disk (vector + ≤R out-neighbour IDs). "GC-free update combining": disk space is overprovisioned to reserve free record slots per page so that multiple record updates are combined into a single page write and old records are recycled without garbage collection; default doubles disk space, giving 2× space consumption and 2× write amplification versus a log-structured layout (which would need GC). "Approximate concurrency control": per-record isolation (search needs a consistent snapshot per record; insert links to an approximate neighbour snapshot), plus two optimizations tailored for disk I/O and compute in critical sections. I/O engine: io_uring in place of libaio. — [OdinANN PDF](https://storage.cs.tsinghua.edu.cn/papers/fast26-odinann.pdf)
- Setup: 2× 28-core Xeon Gold 6330 @ 2.0 GHz; 1× Samsung PM9A3 3.84 TB; SIFT100M/DEEP100M (R=96) and SIFT1B (R=128); workloads insert another 100M into 100M, and 200M into an 800M SIFT1B index. — [OdinANN PDF](https://storage.cs.tsinghua.edu.cn/papers/fast26-odinann.pdf)
- Results: median search latency fluctuation 1.07× (max/min) vs DiskANN 2.44×; 1.15× and 1.99× search throughput vs DiskANN and SPFresh on average; at SIFT1B simultaneously 5000 QPS search and 1100 QPS insert with ~3 ms stable median latency; insert latency ~11.1 ms (vs buffered in-memory insert); memory 83.8 GB at 1B (design estimate ~58 B/vector = 58 GB); update combining raises insert throughput 5.12×. Deletes: lightweight merge at 20% deleted vectors; delta pruning left for future work. — [OdinANN PDF](https://storage.cs.tsinghua.edu.cn/papers/fast26-odinann.pdf); [USENIX page](https://www.usenix.org/conference/fast26/presentation/guo); [slides](https://www.usenix.org/system/files/fast26_slides_guo.pdf)
- Code lives in the PipeANN repository (OSDI'25 "Achieving Low-Latency Graph-Based Vector Search via Aligning Best-First Search Algorithm with SSD", Guo & Lu). Repo: insert/delete added July 2025 with "minimal search interference (1.07x fluctuation)"; SPDK backend "fastest option, with multi-SSD scaling" — 70K QPS at 2 ms tail on 1B vectors with 4 SSDs via SPDK; 20K QPS single SSD; ~40 GB memory for 1B with 32 B PQ codes; benchmark SSD Samsung PM9A3. — [thustorage/PipeANN](https://github.com/thustorage/PipeANN)

**Yi [preprint, Jul 2026]** "Efficient and Effective In-place Graph-based Vector Index Updates" (Haotian Liu, Yujun He, Bo Tang)
- Framing: graph is singly linked so deletion needs in-neighbours, requiring a full scan in the baseline; out-of-place merge cost grows with index size (OdinANN 100M→800M raised merge cost of 20M updates by 2.67×). Four challenges: excessive vector visits, suboptimal CPU utilization (OdinANN averages 61% CPU inserting 20M into 100M), ineffective cache, inefficient layout. — [Yi HTML](https://arxiv.org/html/2607.15576)
- Design: tasklet engine on C++20 coroutines (tasks suspend on page I/O or conflicts); asynchronous buffer manager with fixed budget (4 GB in experiments), free/dirty lists, refcounts, CAS flags, copy-on-write, asynchronous write-back; a "vector file system" separating graph topology from raw vectors into block types (meta, bitmap, schema, PQ, vector mapping, vector index, vector data) with bitmap slot tracking. Deleted vectors wait in an LRU delete list. SPDK appears only as future work. — [Yi HTML](https://arxiv.org/html/2607.15576)
- Setup/results: Xeon Gold 6542Y, Intel SSDPF2KX076T1 7 TB; DEEP100M (30M inserts + 30M deletes): ~1.6K updates/s = 2.8× OdinANN, 4.7× DiskANN; search ~4.8K QPS vs 2.9K OdinANN, 2.8K DiskANN, 1.2K SPFresh; memory ~15.4 GB; SIFT800M (40M+40M): 2.3× OdinANN update throughput at 8M batch, 1.5× at 20M; search ~1.8×; peak memory 73%/71% of OdinANN; Yi uses 12 threads vs 24. Breakdown (DEEP10M): tasklets 4.02×, buffer manager 1.33×, layout 1.04×; cache hit 66%→78%. ~3× update throughput vs IP-DiskANN on DEEP10M. Recall less stable under spatially clustered (out-of-distribution) insertions. Future work: SPDK acceleration of the file system; multi-tenancy. — [Yi HTML](https://arxiv.org/html/2607.15576)

**NAVIS [preprint, May 2026]** "Concurrent Search and Update with Low Position-Seeking Overhead in On-SSD Graph-Based Vector Search" (Song, Jang, Shin, Park, Ryoo, Park, Lee)
- "Position seeking" (full graph traversal per update to locate neighbours) accounts for up to 85% of update latency in OdinANN; packed layouts tie each edge fetch to a full vector load (44.34% of read volume wasted on MSMARCO); static entrance graph drifts from newly inserted regions. — [NAVIS summary](https://www.emergentmind.com/papers/2605.11523)
- Design: decoupled vector and edgelist files with an indirection table and convergence-aware reranking for selective vector reads; incremental entrance-graph updates reusing insertion traversals (<1% overhead); 16 GB entrance-graph-aware cache (90% frozen high-reuse edgelists, 10% LRU admission). Out-of-place writes reduce "five full-page writes to two edgelist-page writes and one vector-file write, decoupling vector write volume from the graph's out-degree R", which the authors say improves SSD endurance. — [NAVIS arXiv PDF](https://arxiv.org/pdf/2605.11523)
- Results: insertion throughput up to 2.74× (MSMARCO), concurrent search throughput up to 1.37× (FineWeb), average search latency −25.26%, recall ~97–98% ≈ OdinANN; datasets FineWeb 60M×768, MSMARCO 100M×768, DEEP 120M×96, ImageNet 1.3M×512; single server with PCIe 5.0 SSD, 22 search + 10 insert threads; baselines FreshDiskANN, OdinANN (+NAVIS cache), Qdrant and SPFresh on ImageNet. — [NAVIS summary](https://www.emergentmind.com/papers/2605.11523)

**Other SSD-tied update designs (host-side)**
- FreshDiskANN [preprint 2021, arXiv 2105.09613] (Singh, Subramanya, Krishnaswamy, Simhadri; MSR India): inserting one point may update up to R neighbourhoods → up to R random SSD writes (R=64/128), and heavy writes also hurt SSD read latency; hence an in-memory TempIndex + SSD long-term index + StreamingMerge. Week-long run on ~1B SIFT1B subset, 48-core machine, 3.2 TB SSD: <128 GB DRAM; merging a 10% change (5% ins + 5% del) takes ~10% of rebuild time; steady state 1800 inserts + 1800 deletes/s without backlog, bursts to 40,000 inserts/s; insert/delete user latency <1 ms during merge; 1000 searches/s at 95+% 5-recall@5 with mean latency well under 20 ms; 5–10× lower cost of freshness than prior methods. Recall drops over repeated update cycles without the α-pruning delete policy (Fig. 2, 50 cycles). TempIndex limit 30M points; if too many insert threads run, inserts backlog before merge completes. — [arXiv 2105.09613](https://arxiv.org/abs/2105.09613)
- IP-DiskANN [preprint, Feb 2025] (Xu, Dobson Manohar, Bernstein, Chandramouli, Wen, Simhadri): first algorithm avoiding batch consolidation, processing each insertion/deletion in place; approximates in-neighbours from the search's visited set; stable recall over long update sequences in high- and low-recall regimes; better query throughput and update speed than batch consolidation and HNSW. Notes that a billion-scale SIFT merge incurred a large peak memory and that systems must be provisioned for merge spikes. — [arXiv 2502.13826](https://arxiv.org/abs/2502.13826)
- DGAI [preprint, Oct 2025] "Decoupled On-Disk Graph-Based ANN Index for Efficient Updates and Queries": co-located vector+topology layouts create >79% redundant I/O during topology updates; physically separating them yields 10.05× faster insertions and 6.89× faster deletions vs coupled storage, at the cost of query I/O amplification mitigated by similarity-aware dynamic layout and a PQ-filtered three-stage query; speedup over FreshDiskANN 1.85× at 10% batch, 10.04× at 0.1% batch (Gist). — [arXiv 2510.25401](https://arxiv.org/abs/2510.25401)
- Greator (DiskANN-based small-batch updates; auxiliary topology to find affected vectors; fine-grained incremental I/O + lightweight repair). A VLDB vol. 19 paper on topology-aware localized small-batch updates reports 2.39–5.96× higher update throughput; the search excerpt did not confirm it is Greator. — [arXiv 2503.00402](https://arxiv.org/abs/2503.00402v1); [PVLDB vol19 p495](https://www.vldb.org/pvldb/vol19/p495-yu.pdf)
- LSM-VEC [preprint, May 2025] (NTU): HNSW upper layers in memory, bottom layer on disk managed by the graph-oriented LSM-tree AsterDB; out-of-place updates distributed across LSM levels; probabilistic projection-based neighbour filtering; reordering during compaction co-locates co-traversed nodes. SIFT1B: up to 2.6× lower average update latency and >66.2% lower memory than DiskANN. — [arXiv 2505.17152](https://arxiv.org/abs/2505.17152). AisLSM (ShanghaiTech) is an unrelated LSM-tree compaction paper making fsync-bound compaction I/O asynchronous; no link to LSM-VEC found. — [AisLSM ar5iv 2307.16693](https://ar5iv.labs.arxiv.org/html/2307.16693)
- Turbocharging Vector Databases using Modern SSDs [PR: PVLDB 18(11):4710–4722, 2025] (Shim, Oh, Roh, Do, Lee; SNU/Dnotitia): disk-resident HNSW in pgvector; (1) parallel I/O via io_uring (depth 2×m) overlapping asynchronous neighbour page reads with distance computation; (2) spatially-aware insertion reordering grouping similar inserts for cache locality; (3) locality-preserving colocation. Up to 11.1× query throughput, 3.23× cache-hit ratio, and 98.4% reduction in index build time (DBpedia-1M); older SSD (Samsung 850 Pro) shows only 6.4× gain due to legacy controller/fewer NAND channels. Hardware: Xeon Gold 6442Y (24 cores), 64 GB DRAM, Samsung PM1743, Fadu Delta, Samsung 980 Pro, Samsung 850 Pro. Argues static PQ/IVF indexes make incremental updates "infeasible or highly inefficient" and that FreshDiskANN's offline consolidation "incurs latency spikes". — [PVLDB PDF](https://www.vldb.org/pvldb/vol18/p4710-do.pdf)
- MicroNN (Apple) [preprint, Apr 2025]: on-device disk-resident updatable vector DB; buffers updates in a delta store and merges into SSD posting lists in background. — [arXiv 2504.05573](https://arxiv.org/abs/2504.05573)
- Onyx [preprint, Apr 2026] "Cost-Efficient Disk-Oblivious ANN Search": decoupled index layout; appendix applies it to FreshDiskANN's update primitives. — [arXiv 2604.20401](https://arxiv.org/pdf/2604.20401)

### Inferences
- The hardware "features" exploited for updates are modest: user-space NVMe (SPDK) to raise IOPS and avoid kernel overhead (SPFresh; PipeANN backend), io_uring for asynchronous page I/O (OdinANN, Turbocharging), and SSD-page-aware layouts (fixed-size records with free slots, decoupled vector/edge files) to cut write amplification. The core bottleneck every paper names — neighbour finding ("position seeking") requiring random reads — remains on the host CPU.
- SPFresh's throughput numbers (2K updates/s at 1B on one SSD) and OdinANN's (1100 inserts/s + 5000 QPS at 1B) are of the same order; successors trade SPFresh's cluster-level coarse recall for graph-level recall rather than raising raw update throughput by orders of magnitude.

### Gaps
- SPFresh reports no numeric write amplification, no separate delete throughput, no per-day recall table.
- No SPFresh follow-up on SmartSSD/NDP exists in the sources found; the only "near-data" successor-like item is a scheduler inside a vector-DB SSD (see KQ3), not a graph/cluster update engine.
- OdinANN's and NAVIS's write-amplification figures come from the authors' analysis (2× by construction), not from measured SSD-internal WAF.

## KQ3. In-storage / near-data processing (NDP) work and whether it supports updates (NDSearch, SmartSSD HNSW, CSD, in-storage index maintenance)

### Takeaway
All in-storage/NDP ANN accelerators found (NDSearch ISCA'24, SmartSSD-HNSW 2022, GraphAccel talk) are search-only; the graph is built offline on the host and loaded once. The closest thing to in-storage *update* work is a 2026 Sogang dissertation (PRESCAR) that schedules online ingestion against search inside a "vector-database SSD", and even there the location of HNSW construction is not stated.

### Cited Findings
- NDSearch [PR: ISCA 2024; arXiv 2312.03141] (Wang et al.; Duke/UCLA/Samsung): near-data processing for graph-based ANNS; in-storage architecture "SEARSSD" runs ANNS kernels inside the SSD exploiting LUN-level parallelism in NAND; two-level scheduling and speculative search. Throughput up to 31.7×, 14.6×, 7.4×, 2.9× over CPU, GPU, a SmartSSD-only design, and DeepStore; two orders of magnitude higher energy efficiency than CPU/GPU. No update support described in the sources. — [arXiv 2312.03141](https://www.arxiv.org/pdf/2312.03141); [IEEE Xplore](https://ieeexplore.ieee.org/document/10609615)
- "Accelerating Large-Scale Graph-based NN Search on a Computational Storage Platform" [preprint 2022, arXiv 2207.05241] (Kim, Park, Do, Ji, Kim): SmartSSD (Xilinx KU15P FPGA, 4 GB DRAM, 3.84 TB NAND, U.2); HNSW database on the SSD, FPGA fetches graph segments via P2P; HLS and RTL accelerators; up to 4 SmartSSDs. SIFT1B: 75.59 QPS at 258.66 W; 12.83×/17.91× throughput and 10.43×/24.33× energy efficiency vs CPU/GPU servers; recall 0.94 @K=10, ef=40. The graph "was already constructed in a downtime"; loading the DB to the SSD is "a single-time event that initializes the SSD"; no on-device construction/insertion; future work is scaling to tens of TB and more devices. — [ar5iv 2207.05241](https://ar5iv.labs.arxiv.org/html/2207.05241)
- GraphAccel (SNU seminar, "Accelerating Vector Similarity Search with Near-Storage Processing"): near-storage accelerator using page packing to minimize SSD page accesses per query and speculative search using idle SSD chips/channels — a talk summary, not a paper; search-side only. — [SNU seminar](https://cse.snu.ac.kr/en/community/seminar/1071)
- Sogang University Ph.D. dissertation (Donghyun Min, advisor Young-Jae Kim, Aug 2026) "Architectural Design of In-Storage Processing Systems for High-Performance Query Processing" [thesis]: Chapter 3 PRESCAR — a preemptive, SLO-aware scheduler for "vector database SSDs (VDSSDs)" that handles concurrent online data ingestion and similarity search under tight device resource limits, estimating per-operation latency and resource demand to balance "freshness, availability, and query performance". The VDSSD execution model lists "Offline Vector Insert", "Offline Index (HNSW) Build", and "Online Vector Search" but the page does not state where HNSW construction runs; no PRESCAR numbers on the record page (other chapters: ISO-KVSSD 2.9× read throughput; CERBERUS 9.31× faster query processing). — [Sogang dcollection](https://dcollection.sogang.ac.kr/dcollection/srch/srchDetail/000000083035)
- The SIGMOD'26 tutorial "Vector Search for the Future" (Song, Zhou, Jensen, Xu) does not mention GPU, CXL, PIM, SmartSSD, NDP or FPGA acceleration at all in its heterogeneous-storage/update coverage. — [arXiv 2601.01937](https://arxiv.org/html/2601.01937v1)
- Write-amplification context from FreshDiskANN: inserting one point may touch up to R neighbour lists → up to R random SSD writes. — [arXiv 2105.09613](https://arxiv.org/abs/2105.09613)

### Inferences
- A natural partition for an in-storage update design would run position seeking (random-read traversal) and neighbour-list patching on the device FPGA/controller while the host keeps the in-memory fresh layer and merge scheduling; no source implements or evaluates this — it is an inference from the OdinANN/NAVIS cost breakdowns (85% of update latency in position seeking) and the NDSearch/SmartSSD search kernels.
- Because SPFresh already saturates the SSD's IOPS at 2K updates/s + 4K QPS on 15 cores, the host CPU is not the sole bottleneck; moving traversal into the device would need to exploit internal NAND bandwidth (as NDSearch does for search) to help.

### Gaps
- No paper titled or framed as "in-storage vector index maintenance", "DiskANN on CSD", or "graph insertion inside the SSD controller" was found for 2021–2026.
- NDSearch's full text was not read; its update stance is inferred from abstracts and secondary descriptions (search-only).
- PRESCAR's quantitative results and whether its ingestion path updates an on-device index were not retrievable from the catalogue page.

## KQ4. CXL / tiered memory for mutable indexes; persistent-memory (Optane/PM) ANN indexes with crash-consistent updates

### Takeaway
CXL-ANNS (ATC'23) and Cosmos (CAL 2025) accelerate billion-scale *search* over CXL memory pools with near-memory distance computation; neither discusses insertion, deletion or on-CXL index construction (the only "update" in CXL-ANNS is the kNN candidate-array update of the search loop). The sole persistent-memory crash-consistent HNSW found is P-HNSW (Applied Sciences, Oct 2025), using two logs (NLog, NlistLog); HM-ANN (NeurIPS 2020) uses DRAM+Optane tiering for static billion-scale search only.

### Cited Findings
- CXL-ANNS [PR: USENIX ATC 2023] (Jang, Choi, Bae, Lee, Kwon, Jung; KAIST/Panmnesia): DRAM disaggregated via CXL with all datasets in the pool; node-level relationship-aware caching of frequently visited neighbours in local memory; prefetching of nodes likely to be visited; collaborative search across CXL network hardware; relaxed execution dependency of neighbour search. Prototype on 16nm FPGA with adapted RISC-V CXL CPU, Linux 5.15.36; EPs have 10 PEs and four memory controllers; datasets BigANN, Yandex-T, Yandex-D (1B each), Meta-S, MS-T, MS-S. 111.1× higher QPS and 93.3% lower latency than tested ANNS platforms; beats a DRAM-only oracle by 68.0% (latency) and 3.8× (throughput). The full text's only "update" mentions are the search loop's "candidate update" subtask (split into urgent and deferrable parts); graph construction appears only as "Graph construction for local caching" (an SSSP-based preprocessing to pick cached nodes). No index insertion/deletion discussion. — [ATC'23 page](https://www.usenix.org/conference/atc23/presentation/jang); [PDF](https://usenix.org/system/files/atc23-jang.pdf); extended version in ACM TOS, DOI 10.1145/3639471 — [KAIST record](https://dspace.kaist.ac.kr/handle/10203/319075)
- Cosmos [PR: IEEE Computer Architecture Letters 2025, DOI 10.1109/LCA.2025.3570235; arXiv 2505.16096] (Ko, Shim, Doh, Yun, So, Kwon, Park, Roh, Yoon, Song, Ahn): general-purpose cores integrated inside CXL memory devices to offload the full ANNS workload; rank-level parallel distance computation; adjacency-aware data placement balancing load across CXL devices; up to 6.72× throughput over baseline CXL and 2.35× over a state-of-the-art CXL solution on SIFT1B/DEEP1B. No mention of insertion, updates or index building. — [arXiv 2505.16096](https://arxiv.org/abs/2505.16096)
- CXL survey (Dec 2024) characterizes CXL-ANNS-style work as placing complete datasets in CXL memory then tuning tiered CXL memory with cache and prefetching — i.e., read-path tiering. — [arXiv 2412.20249](https://arxiv.org/pdf/2412.20249)
- Memory-tiering context for mutable indexes: the SIGMOD'26 tutorial lists its open directions as tier-aware index co-design ("index construction and query strategies must jointly consider SSD- and object-storage-aware data layout"), adaptive/predictive caching, efficient querying from object storage, elasticity/auto-scaling with "online repartitioning", and cost optimization "jointly reducing compute overhead, SSD writes, and object-storage bandwidth". It names no CXL work. — [arXiv 2601.01937](https://arxiv.org/html/2601.01937v1)
- HM-ANN [PR: NeurIPS 2020] (Ren, Zhang, Li; Microsoft): graph-based billion-scale search on heterogeneous DRAM + Intel Optane PMem without compression, promoting high-degree nodes to DRAM; 46% higher recall at equal latency vs L&C / IMI+OPQ on BIGANN and DEEP1B; 2× and 5.8× faster than HNSW/NSG baselines built on HM. Static index; reviewers noted limited data-fetching evaluation. — [NeurIPS'20 camera-ready](https://www.microsoft.com/en-us/research/uploads/prod/2020/11/NeurIPS20_HM_ANN_camera_ready.pdf); [Zilliz summary](https://zilliz.com/learn/hm-ann-efficient-billion-point-nearest-neighbor-search-on-heterogeneous-memory)
- P-HNSW [PR: Applied Sciences 15(19):10554, Oct 2025, 20 pp.] "Crash-Consistent HNSW for Vector Databases on Persistent Memory": standard HNSW runs in DRAM, which is "costly and vulnerable to crashes"; P-HNSW achieves crash consistency on PM with two logs, NLog and NlistLog, with described normal-operation logging and post-crash recovery; abstract claims small logging overhead and better performance than SSD-based recovery. Full text and numbers not retrieved. — [catalog record](https://hdsdev.hebis.de/main/ubffm/EdsRecord/edb%252C188678937)
- Related background on the difficulty: Recipe (SOSP'19) converts concurrent DRAM indexes to PM indexes; crash-consistent PM structures need persist barriers/undo logging. — [MSR Recipe](https://www.microsoft.com/en-us/research/?p=787819)
- Industry patents on "Transactionally consistent HNSW index" and "Multi-snapshot HNSW index" exist (USPTO), indicating commercial interest in durable HNSW updates, but they are not research results. — [USPTO 12579131](https://image-ppubs.uspto.gov/dirsearch-public/print/downloadPdf/12579131); [USPTO 12524385](https://image-ppubs.uspto.gov/dirsearch-public/print/downloadPdf/12524385)

### Inferences
- CXL-ANNS's near-memory distance units and candidate-update pipeline are exactly the primitives an insert needs (search for neighbours, then rewrite adjacency), so extending the design to updates is architecturally plausible, but the published systems keep the graph read-only and the paper gives no roadmap for writes.
- With Optane discontinued, PM-based ANN work has not grown; P-HNSW is a single journal paper rather than the start of a line.

### Gaps
- No CXL-tiered mutable ANN index (hot updated data in DRAM, cold graph in CXL/SSD, with online inserts) was found; search terms "CXL dynamic ANN"/"CXL FreshDiskANN" returned nothing.
- CXL-ANNS TOS extended version was not read; it may add material.
- P-HNSW's mechanism details, hardware (Optane generation), and throughput/recovery numbers are unavailable from the sources reached.

## KQ5. PIM / UPMEM for index build or update

### Takeaway
No PIM/UPMEM paper on k-NN graph construction or ANN index updates was found for 2021–2026. The nearest works are a May 2026 PIM graph-ANN *search* co-design, a 2025 ICEIC paper accelerating distance computation for brute-force/HNSW search with DRAM-PIM, and PIM-tree/PIMLex, which show that updatable (ordered/learned) indexes can run on UPMEM but are not vector indexes.

### Cited Findings
- "Co-Designing Graph-based Approximate Nearest Neighbor Search at Billion Scale for Processing-in-Memory" [preprint, May 2026, cs.AR] (Chen, Li, Chen, Deng, Meng, Zhou): compacted index layout cutting PIM-resident footprint 14.5×; asynchronous pipelined scheduler saturating host–PIM interconnect; multiplication-free distance kernel with <0.08% recall loss; up to 20× over CPU and 17.1× over GPU baselines, 129× over prior PIM ANN accelerators in the high-recall regime, on three billion-scale benchmarks. Lists PIM obstacles: ~64 MB per DPU, costly cross-PU communication, host coordination, weak in-memory cores (UPMEM lacks hardware multipliers). Covers search only; nothing on build or dynamic updates. — [arXiv 2605.25522](https://arxiv.org/abs/2605.25522)
- "Vector Similarity Search Acceleration using DRAM-based PIM" [PR: ICEIC 2025, Ewha]: distance computation for brute-force and HNSW search, emulated on FPGA; no insertion/update handling found. — [Ewha record](https://pure.ewha.ac.kr/en/publications/vector-similarity-search-acceleration-using-dram-based-processing/)
- PIM-tree [PR 2023; arXiv 2211.10516]: ordered index on a commercial PIM prototype supporting batch-parallel point queries, updates and scans with near-constant data movement per update — demonstrates updatable indexes on UPMEM, but for 1-D keys. — [arXiv 2211.10516](https://arxiv.org/pdf/2211.10516v1)
- PIMLex [PR: FAST'25]: learned index on UPMEM, 36.5× throughput over a PIM learned-index baseline; one-dimensional. — [FAST'25](https://www.usenix.org/conference/fast25/presentation/cui)
- PiPNN [preprint, Feb 2026]: partition-based graph construction (recursive overlapping clusters + HashPrune) that builds indexes up to 11.6× faster than Vamana and 12.9× faster than HNSW; an algorithm that could map to PIM-style parallelism, but no PIM implementation. — [arXiv 2602.21247](https://arxiv.org/abs/2602.21247)

### Inferences
- UPMEM's 64 MB per DPU and lack of multipliers make neighbour-selection (distance-heavy, write-heavy) construction awkward; the 2026 PIM search paper needed a multiplication-free kernel and a 14.5× compacted layout just to fit search, which suggests construction/update on PIM would require an even more aggressive co-design.

### Gaps
- No "PIM-based graph construction", "DRAM-PIM k-NN graph build", or "UPMEM ANN build" paper exists in the sources found; this is a clear open area.

## KQ6. Systems co-design: many-core/NUMA concurrent insertion, lock-free graph updates, RDMA/disaggregated-memory update paths, log-structured SSD designs

### Takeaway
On many-core CPUs the dominant technique is ParlayANN's lock-free batch insertion (search on an immutable snapshot, semisort reverse edges by target vertex, prune per vertex, prefix-doubling batches), which builds billion-scale Vamana/HNSW/HCNNG in ~10 h on 128 vCPUs and is the template reused by the GPU streaming designs. RDMA/disaggregated designs (d-HNSW 2026, SHINE 2025) support inserts via reserved gaps, overflow regions and epoch-based shadow rebuilds with large throughput dips during rebuild. CPU dynamic indexes (CleANN, Wolverine, IP-DiskANN, DIGRA) improve repair/deletion but are not hardware-specific.

### Cited Findings
- ParlayANN [PR: PPoPP 2024; arXiv 2305.04359] (Dobson Manohar, Shen, Blelloch, Dhulipala, Gu, Simhadri, Sun): existing parallel graph builds rely on locks, limiting scaling and causing nondeterminism. Batch insertion with prefix doubling: batch end = min(2×start, start+θ, n), θ = 0.02n; each point greedy-searches an immutable snapshot; reverse edges merged with a parallel semisort keyed by existing vertex, so no locks; point i sees an index of ≈i/2 points; ParlayDiskANN (R=64, L=128) within 1% of sequential-build QPS on BIGANN-1M. Machines: AWS c6i (2× 3rd-gen Xeon Gold, 128 vCPUs, 1 TB RAM); x2idn for TEXT2IMAGE-1B (128 vCPUs, 2 TB). 100M build hours (BIGANN/MSSPACEV/TEXT2IMAGE): DiskANN .42/.35/.70; HNSW .35/.37/.94; HCNNG .45/.77/1.75; pyNNDescent .42/.73/1.23; FAISS .19/.13/.22. Billion scale: ParlayDiskANN/HNSW/HCNNG each ≈10 h; ParlayHNSW up to 2.3× faster than the other two. Scaling vs originals at 1M: DiskANN ~1.2×, HNSW ~1.4× (originals degrade beyond ~30–60 threads from lock contention), HCNNG up to 12×, pyNNDescent up to 28×. Dynamic post-build updates/deletions are not discussed; notes determinism matters for persistence, crash recovery and replication in vector DBs. — [arXiv HTML](https://arxiv.org/html/2305.04359v2); [PPoPP'24 page](https://ppopp24.sigplan.org/details/PPoPP-2024-papers/9/ParANN-Scalable-and-Deterministic-Parallel-Graph-Based-Approximate-Nearest-Neighbor-)
- CleANN [preprint, Jul 2025] "Efficient Full Dynamism in Graph-based ANN Search" (Zhang, Wei, Engels, Shun; MIT): concurrent insertions, deletions and searches; aims for query quality at least as good as a statically built index; argues existing quality-maintenance mechanisms are global and expensive. — [arXiv 2507.19802](https://arxiv.org/abs/2507.19802)
- Wolverine [PR: PVLDB 18(7):2268–, 2025, DOI 10.14778/3734839.3734860] (Liu, Zheng, Yue, Ruan, Zhou, Jensen): deletions destroy monotonic search paths causing recall decay; monotonic search-path repair accelerates deletion throughput up to 11× with more stable recall on 9 datasets; notes periodic rebuilding of large indexes "can take days or even months". — [PVLDB DOI](https://doi.org/10.14778/3734839.3734860)
- DIGRA [PR: SIGMOD 2025, PACMMOD 3(3) art. 148, DOI 10.1145/3725399]: dynamic range-filtered graph index with lazy weight-based updates; used as the CPU dynamic baseline by ETALE. — [author copy](https://www1.se.cuhk.edu.hk/~swang/V3mod148-DIGRA.pdf)
- d-HNSW [preprint, Mar 2026, arXiv 2603.13591; earlier 2505.11783] (Fang, Liu, Qian; UCSC): first RDMA-based vector search engine for disaggregated memory; compute nodes cache a meta-HNSW and route inserts to a sub-HNSW (fetched and cached if absent); changes tracked in an UpdateCommit and written with doorbell batching; vectors first fill reserved internal gaps in each cluster's arrays (in-place expansion), then a shared overflow region; when overflow fills, a shadow copy is built in a new epoch buffer and switched atomically while inserts are buffered in an LSH-bucket structure that queries still search. Hardware: 4× Dell R650 (2× 36-core Xeon Platinum, 256 GB, ConnectX-6 100 Gb) on CloudLab; 3 compute + 1 memory node; one-sided RDMA so memory-node CPU is off the query path. After 10K insertions (SIFT1M/GIST1M) query latency 1.8–2.1× lower than non-contiguous layouts; mixed workload SIFT1M batch 8000: batch latency 438K µs (100% search) → 1.46M µs (50% insert); during epoch transition throughput fell ≈190K → ≈70K QPS for a ~120 s rebuild window. No insert-only throughput reported. Earlier version: up to 117× lower query latency than naive d-HNSW at recall 0.87 on SIFT1M. — [arXiv HTML 2603.13591](https://arxiv.org/html/2603.13591v1); [arXiv 2505.11783](https://arxiv.org/abs/2505.11783v1)
- SHINE [preprint, Jul 2025] (Widmoser, Kocher, Augsten): global HNSW preserved across arbitrarily many memory nodes via RDMA with combined compute-node caches; same accuracy as single-machine HNSW; identifies index updates as a limitation of the baseline design; no update numbers in abstract. — [arXiv 2507.17647](https://arxiv.org/abs/2507.17647)
- Pyramid and distributed DiskANN update paths: no sources found describing RDMA-based update protocols for them.
- Log-structured SSD designs: see LSM-VEC and OdinANN's explicit rejection of a log-structured layout because of GC overhead (choosing 2× overprovisioned fixed slots instead) in KQ2. — [OdinANN PDF](https://storage.cs.tsinghua.edu.cn/papers/fast26-odinann.pdf)
- Local rewiring for HNSW under product-catalogue churn (Sengupta, CEUR workshop, independent researcher) exists but is algorithmic, not hardware-tied. — (file text only; no URL retrieved)

### Inferences
- The lock-free "snapshot search → semisort by target → per-vertex prune" pattern is now the common denominator across CPU (ParlayANN), GPU (Jasper, GrAND) and partially SSD (OdinANN's per-record isolation), which suggests the hardware-specific work is in memory/IO management rather than concurrency algorithms.
- Disaggregated-memory designs pay for inserts with periodic shadow rebuilds (~2.7× throughput drop for ~2 minutes in d-HNSW), re-creating at network scale the "merge spike" problem SPFresh/OdinANN attack on a single SSD.

### Gaps
- No NUMA-specific concurrent-insertion study for HNSW was found.
- ParlayANN gives no thread count per build and inconsistent machine descriptions (48/64/96/128 cores across sections).
- d-HNSW's insert algorithm is in an appendix not read; no per-insert latency.

## KQ7. Recall drift / consistency of hardware-accelerated updates, and the freshness-vs-throughput trade-off

### Takeaway
Every system that batches updates for hardware efficiency reports a freshness cost: GPU phase-alternation delays visibility until a batch completes (Jasper, unquantified), SVFusion shows recall collapsing from 0.96 to 0.18 if GPU copies are not synchronized, and SSD merge-based designs (DiskANN/FreshDiskANN) show 1.5–2.4× latency fluctuation and multi-day rebuilds. In-place designs (SPFresh, OdinANN, Yi, IP-DiskANN) trade peak batch throughput for stable latency and recall.

### Cited Findings
- SVFusion: larger update batches raise throughput but reduce recall beyond batch size 2^13 "because graph updates are delayed"; latency exceeds 1 s at 2^11; GPU copies lag the CPU until asynchronous propagation completes, with queries falling back to CPU in that window; with synchronization Recall@1 stays 0.96 at 10K QPS, without it recall falls to 0.18 while p99 drops from 33.2 ms to 7.4 ms; synchronization adds 15–30% p99 at low request rates. — [arXiv 2601.08528](https://arxiv.org/html/2601.08528v1)
- Jasper: inserts and queries alternate in phases; newly inserted vectors become searchable only after the batch completes; delay not quantified; recall varies <2 points across batch sizes except Gist at beam 128 (0.854→0.820 at the largest batch); consolidation raises average degree and lowers QPS. — [Jasper HTML](https://arxiv.org/html/2601.07048v5)
- SIVF: GPU IVF updates via CPU–GPU transfer push latency "from milliseconds to seconds"; tombstones do not reclaim space. — [arXiv 2601.11808](https://arxiv.org/abs/2601.11808)
- ETALE: tombstone-only systems' memory "grow[s] indefinitely"; claims bounded reclaim. — [arXiv 2607.02543](https://arxiv.org/abs/2607.02543)
- OdinANN: buffered-insert merge raises median search latency 1.54×, needs 125 GB for a 3% merge at 1B, and merge throughput caps at ~3000 QPS; direct insert gives 1.07× median-latency fluctuation vs DiskANN's 2.44×, at the cost of ~11.1 ms insert latency and 2× disk write amplification. — [OdinANN PDF](https://storage.cs.tsinghua.edu.cn/papers/fast26-odinann.pdf)
- SPFresh: DiskANN's P99.9 exceeds 20 ms during global rebuilds while SPFresh holds ≈4 ms; SPANN+ (no rebalancing) drifts from 4 ms to >10 ms and its recall degrades as partitions skew; DiskANN recall declines over the 100-day run. — [SPFresh HTML](https://arxiv.org/html/2410.14452v1)
- FreshDiskANN: recall drops over 50 delete/re-insert cycles without α-based pruning on deletion (Fig. 2); too many insert threads cause a TempIndex backlog before merge completes. — [arXiv 2105.09613](https://arxiv.org/abs/2105.09613)
- Yi: recall is less stable under spatially clustered (out-of-distribution) insertions; deletion-only recall slightly below full-scan baseline at 2% LRU delete-list size (4% closes the gap). — [Yi HTML](https://arxiv.org/html/2607.15576)
- Turbocharging (VLDB'25): static PQ/IVF indexes make incremental updates "infeasible or highly inefficient"; "recall performance often degrades rapidly as the index becomes outdated", requiring periodic rebuilds; FreshDiskANN's offline consolidation "incurs latency spikes and operational overhead". — [PVLDB PDF](https://www.vldb.org/pvldb/vol18/p4710-do.pdf)
- d-HNSW: ~2.7× QPS drop for ~120 s during epoch rebuild; 50% insert mix raises batch latency 3.3×. — [arXiv 2603.13591](https://arxiv.org/html/2603.13591v1)
- Wolverine: deletions destroy monotonic search paths, decreasing accuracy after updates. — [PVLDB DOI](https://doi.org/10.14778/3734839.3734860)

### Inferences
- The trade-off has two axes in the hardware literature: (a) batching for device efficiency (GPU kernels, SSD page writes) vs. visibility latency, and (b) deferred repair (tombstones, lazy consolidation) vs. recall and memory growth. In-place designs fix (b) and partially (a) but no GPU system yet runs concurrent inserts and queries on the same device without a CPU fallback.

### Gaps
- No paper quantifies "time-to-visibility" of an inserted vector on GPU; Jasper explicitly leaves it unquantified.
- No independent benchmark compares GPU streaming indexes (Jasper/ETALE/GrAND/SIVF) against each other or against cuVS `extend`.

## KQ8. Open problems and research opportunities explicitly listed, and what is NOT yet accelerated in hardware

### Takeaway
Papers explicitly list: SPDK-based acceleration of the update file system and multi-tenancy (Yi); delta pruning and faster delete handling (OdinANN); scaling GPU dynamic indexes beyond HBM via multi-GPU sharding/host-pinned memory, concurrent insert+query on GPU, cheaper consolidation (Jasper); distributed SPFresh; tier-aware index co-design, online repartitioning and SSD-write minimization (SIGMOD'26 tutorial). Not accelerated in hardware anywhere in the sources: in-storage graph insertion/edge repair, CXL/PIM-side index mutation, hardware-assisted rebalancing/compaction, and energy-measured update paths.

### Cited Findings
- Yi future work: "Use SPDK to accelerate the vector file system, and improve performance in multi-tenant settings." — [Yi HTML](https://arxiv.org/html/2607.15576)
- OdinANN: delta pruning and faster delete-side merge left for future work; location-to-ID table implementation inflates memory. — [OdinANN PDF](https://storage.cs.tsinghua.edu.cn/papers/fast26-odinann.pdf)
- Jasper: scaling beyond GPU memory "an open challenge" (multi-GPU sharding, host-pinned memory suggested); inserts and queries cannot run concurrently; consolidation is costly and densifies the graph; RaBitQ accuracy ceiling ≈0.95 recall on high-dimensional data. — [Jasper HTML](https://arxiv.org/html/2601.07048v5)
- SPFresh: single-node design "as a foundation for a future distributed version". — [SPFresh HTML](https://arxiv.org/html/2410.14452v1)
- SIGMOD'26 tutorial open directions: tier-aware index co-design; adaptive/predictive caching; efficient querying from object storage; elasticity with online repartitioning; cost optimization reducing SSD writes and object-storage bandwidth. — [arXiv 2601.01937](https://arxiv.org/html/2601.01937v1)
- SmartSSD HNSW future work: tens-of-TB databases and more devices (search only). — [ar5iv 2207.05241](https://ar5iv.labs.arxiv.org/html/2207.05241)
- PIM search paper's stated obstacles (per-unit memory, inter-unit communication, host coordination, weak cores) apply directly to any build/update attempt. — [arXiv 2605.25522](https://arxiv.org/abs/2605.25522)
- Helmsman/industry: single-node CPU-only construction "violating the freshness of services"; GPU pipelines bring billion-scale rebuilds to hours. — [arXiv 2606.13145](https://arxiv.org/abs/2606.13145)

### Inferences (what is not yet accelerated — the gap map)
- Neighbour selection / position seeking for inserts: accelerated on GPU (Jasper, GrAND, SVFusion) and via SIMD/compact codes on CPU (Flash); not in-storage, not CXL, not PIM.
- Graph edge rewiring / in-neighbour repair for deletes: CPU only (IP-DiskANN, Wolverine, CleANN) and GPU (GrAND's on-demand reverse graph, ETALE's CoW word); no SSD-internal or near-memory implementation.
- I/O for disk-resident graph updates: SPDK (SPFresh), io_uring + overprovisioned fixed slots (OdinANN), decoupled edge/vector files (NAVIS, DGAI, Yi); no computational-storage offload.
- Partition rebalancing (split/merge/reassign): host CPU only (SPFresh LIRE); no hardware.
- Compaction / consolidation: host CPU (LSM-VEC compaction, FreshDiskANN merge, SVFusion async consolidation) and GPU (Jasper compact phase); none near-data.
- Crash consistency of updates: one PM paper (P-HNSW); no NVMe-atomic-write or CXL-persistence design found.
- Energy: only search-side energy numbers exist (NDSearch, SmartSSD-HNSW); no paper reports energy per insert/delete.

### Gaps
- No paper found that (a) performs any part of vector-index mutation inside an SSD, CXL device, or PIM unit, or (b) measures energy of index updates. Search queries covering "in-storage vector index maintenance", "SmartSSD graph insertion", "CXL dynamic ANN", "UPMEM ANN build", and "FPGA HNSW construction" all returned only search-side or host-side work. This absence is the main finding of this note.
