# Hardware / Computer-Architecture Acceleration of ANN Vector Search (2020–2026)

Scope: hardware for ANN *search* (graph-based HNSW/DiskANN/Vamana and cluster-based IVF-PQ), organized by hardware class. A sibling note covers hardware for online *updates*; works here that also touch construction/updates are flagged "[also updates/construction]". "Peer-reviewed" vs "preprint" status is stated per entry. All speedup numbers are the authors' own measurements unless stated otherwise.

Research date: 2026-10-09. Tool budget was limited, so several papers are summarized from abstracts/arXiv HTML rather than full-text reads; those cases are marked.

---

## Key Question 1 — GPUs (CAGRA, GGNN, SONG, BANG, GPU-HNSW, Faiss/cuVS IVF-PQ, 2024–26 follow-ups)

### Takeaway
GPU graph search (SONG → GGNN → CAGRA) solved the *parallelism* problem of best-first traversal by batching candidate expansion, reaching 33–77× HNSW-CPU throughput at 90–95% recall on in-GPU-memory datasets; the dominant limit then becomes GPU **memory capacity** (billion-scale indexes do not fit) and **device memory bandwidth**, which the 2024–26 generation (BANG, PilotANN, FusionANNS, cuVS IVF-PQ) attacks by keeping only compressed (PQ/SVD) vectors on the GPU and placing the graph/full vectors in host DRAM or SSD.

### Cited Findings

**CAGRA (NVIDIA; arXiv 2308.15136, Aug 2023; v2 Jul 2024). Preprint on arXiv; also shipped in NVIDIA cuVS / RAFT and Faiss.**
- Title: "CAGRA: Highly Parallel Graph Construction and Approximate Nearest Neighbor Search for GPUs" — Hiroyuki Ootomo, Akira Naruse, Corey Nolet, Ray Wang, Tamas Feher, Yong Wang (NVIDIA). — [arXiv abs](https://arxiv.org/abs/2308.15136v1); [HTML v2](https://arxiv.org/html/2308.15136v2)
- Reported: at 90–95% recall, large-batch throughput 33–77× faster than HNSW (CPU) and 3.8–8.8× faster than SOTA GPU graph implementations (GGNN, GANNS); single-query 3.4–53× faster than HNSW at 95% recall; graph construction 2.2–27× faster than HNSW. — [arXiv](https://arxiv.org/abs/2308.15136v1)
- Evaluation setup: DGX A100 (A100 80 GB, AMD EPYC 7742 64-core); dataset+graph resident in GPU memory; datasets SIFT-1M (128-d), GIST-1M (960-d), GloVe-200, NYTimes, DEEP-1M/10M/100M (96-d); CAGRA graph degree 32–80; batch 10K for large-batch; baselines GGNN, GANNS, HNSW, NSSG (CPU, up to 64 OpenMP threads). Absolute QPS values appear only in figures, not the text. — [HTML v2](https://arxiv.org/html/2308.15136v2)
- Bottleneck statement: "the memory bandwidth of the device limits the throughput of CAGRA" when batch size and dimension are large; storing vectors as FP16 raises throughput without degrading recall. — [HTML v2](https://arxiv.org/html/2308.15136v2)
- Independent counterpoint (peer-reviewed, VLDB): a GPU IVF-RaBitQ paper reports 3.0× higher QPS than CAGRA at Recall≈0.95 with 14.7× faster index construction (an arXiv revision, 2602.23999, states 2.2× QPS and 7.7× construction). — [PVLDB vol 19 p3454 (Shi et al.)](https://www.vldb.org/pvldb/vol19/p3454-shi.pdf); [arXiv 2602.23999](https://arxiv.org/pdf/2602.23999)

**SONG (ICDE 2020, peer-reviewed).** "SONG: Approximate Nearest Neighbor Search on GPU" — Weijie Zhao, Shulong Tan, Ping Li (Baidu Research). Splits graph search into three stages so distance computation runs in parallel and removes dynamic GPU memory allocation; reports ~50–180× over single-thread HNSW; a later re-analysis puts it at ~3–11× over 16-thread HNSW. — [ICDE 2020 PDF](https://www.cs.rit.edu/~wjz/papers/conference/2020-icde-song.pdf); [Graph-based ANN revisit (arXiv 2204.00824)](https://arxiv.org/pdf/2204.00824)

**GGNN (IEEE Trans. Big Data 2023; arXiv 1912.01059, peer-reviewed journal).** "GGNN: Graph-based GPU Nearest Neighbor Search" — Fabian Groh, Lukas Ruppert, Patrick Wieschollek, Hendrik P. A. Lensch (Tübingen). GPU-friendly hierarchical kNN graph with GPU construction; claims surpassing CPU/GPU systems in build time, accuracy and search speed. The 2022 "revisit" study found GGNN ~2× faster than SONG at batch 10K and that SONG only ran reliably on SIFT1M. — [arXiv 1912.01059](https://arxiv.org/pdf/1912.01059); [revisit study](https://arxiv.org/pdf/2204.00824)

**BANG (IIT Hyderabad + Microsoft Research; arXiv 2401.11324, v1 Jan 2024, v4 Apr 2025). Preprint; no venue listed.**
- Title: "BANG: Billion-Scale Approximate Nearest Neighbour Search using a Single GPU." Target bottleneck: GPU memory capacity (earlier GPU methods needed dataset+graph in GPU memory or sharded over PCIe). — [arXiv v4](https://arxiv.org/html/2401.11324v4)
- Design: Vamana (DiskANN) graph (~260 GB for 1B) and full vectors in host DRAM; GPU holds PQ-compressed vectors (m=74 subspaces, ~74 GB per 1B dataset), PQ distance tables, per-query worklists, and a per-query Bloom filter (~400 kB, 2 FNV-1a hashes) for visited-set tracking; kernels for filtering, distance, merge-sort, parallel merge, prefetch; CPU returns neighbour lists; async memcpy/streams overlap PCIe transfers with compute; final exact-distance re-rank. — [arXiv v4](https://arxiv.org/html/2401.11324v4)
- Setup: 1× A100 80 GB (~2039 GB/s), PCIe Gen4 (32 GB/s), 2× Xeon Gold 6326, 660 GiB DDR4 (1133 GiB for Text-to-Image-1B); datasets SIFT-1B (128-d uint8), Deep-1B (96-d fp32), MSSPACEV-1B (100-d int8), Text-to-Image-1B (200-d); batch 10K; metric 10-recall@10. — [arXiv v4](https://arxiv.org/html/2401.11324v4)
- Reported: 50×–400× higher throughput than competing methods (GGNN sharded, FAISS-SQ) at recall 0.9 on three billion-scale datasets (55× SIFT-1B, 50× Deep-1B, 400× MSSPACEV-1B). From Table III total times, BANG ≈117K QPS on SIFT-1B (85.3 ms for 10K queries) and ≈99K QPS on Deep-1B — these QPS values are derived from the reported batch times, not stated directly. CAGRA was compared only at 100M scale because 1B exceeds GPU memory. — [arXiv v4](https://arxiv.org/html/2401.11324v4); [v1 reported 40×–200× over ten datasets](https://arxiv.org/html/2401.11324v1)

**PilotANN (arXiv 2503.21206, Mar 2025; an aggregator lists KDD 2026 — unverified).** "PilotANN: Memory-Bounded GPU Acceleration for Vector Search." Hybrid CPU–GPU graph search: GPU subgraph traversal over SVD-reduced vectors, then CPU refinement with full vectors; fast entry-point selection via coarse clustering. Reports 3.9–5.4× throughput speedup on 100M-scale datasets and handling datasets up to 12× larger than GPU memory; notes CAGRA "encountered GPU memory boundaries" on their datasets. Code: github.com/ytgui/PilotANN. — [arXiv](https://arxiv.org/abs/2503.21206)

**FusionANNS (USENIX FAST '25, peer-reviewed; arXiv 2409.16576).** "Towards High-throughput and Low-latency Billion-scale Vector Search via CPU/GPU Collaborative Filtering and Re-ranking" — Bing Tian, Haikun Liu et al. (HUST + Huawei). Placement: full-precision vectors on SSD, PQ codes in GPU memory, host DRAM holds only posting-list IDs + navigation graph; multi-tiered indexing avoids CPU↔GPU swapping; heuristic re-ranking skips I/Os; redundancy-aware I/O dedup. Motivation: raw vectors are smaller than the 4 KB NVMe read unit → read amplification in re-ranking. Reported: 9.4–13.1× QPS and 5.7–8.8× cost-efficiency over SPANN (SSD baseline); 2–4.9× QPS and 2.3–6.8× cost-efficiency over RUMMY (GPU in-memory system). — [FAST '25 page](https://usenix.org/conference/fast25/presentation/tian-bing); [arXiv](https://arxiv.org/html/2409.16576v1)

**JUNO (ASPLOS 2024, peer-reviewed; arXiv 2312.01712).** "JUNO: Optimizing High-Dimensional Approximate Nearest Neighbour Search with Sparsity-Aware Algorithm and Ray-Tracing Core Mapping" — SJTU + U. Rochester. Maps PQ-style search onto NVIDIA RT cores (BVH traversal) with tensor-core pipelining; 2.2×–8.5× throughput over baseline on four 1M–100M datasets; algorithm alone gives ≤2.6× without RT cores; on A100 (no RT cores) JUNO degrades at high recall; RTX 4090 gives 1.5× more improvement than A40. — [arXiv](https://arxiv.org/pdf/2312.01712)

**Faiss GPU / NVIDIA cuVS IVF-PQ (vendor documentation, not peer-reviewed).**
- Since Faiss v1.10.0, cuVS implementations of IVF-PQ, IVF-Flat, Flat and CAGRA can be enabled (faiss-gpu-cuvs). NVIDIA-reported vs classic Faiss GPU on Deep100M (96-d) at 95% recall: IVF-PQ/IVF-Flat build up to 4.7× faster, IVF-PQ search latency up to 8× lower, large-batch throughput up to 3× higher. — [NVIDIA blog: Faiss + cuVS](https://developer.nvidia.com/blog/enhancing-gpu-accelerated-vector-search-in-faiss-with-nvidia-cuvs)
- Billion-scale memory: DEEP-1B fp32 is 360 GiB; a typical IVF-PQ config compresses the index to 54 GiB (or 24 GiB with ~1.5× slower search) so it fits one GPU; refine_ratio=2 re-ranking recovers 0.99 recall at ~25% QPS cost. — [cuVS IVF-PQ deep dive part 1](https://developer.nvidia.com/blog/accelerating-vector-search-rapids-cuvs-ivf-pq-deep-dive-part-1/); [part 2](https://developer.nvidia.com/blog/accelerating-vector-search-rapids-cuvs-ivf-pq-performance-tuning-part-2)
- NVIDIA's RAFT/cuVS blog shows CAGRA vs HNSW on DEEP-100M at batch 10, 95% recall only as bar charts; no absolute numbers in text. — [NVIDIA RAFT blog](https://developer.nvidia.com/blog/accelerating-vector-search-using-gpu-powered-indexes-with-rapids-raft/)

**GPU-HNSW variants.** ON-NSW (2025, PMC-indexed journal article): flattened HNSW for Jetson Orin Nano using unified memory; up to 1.44× throughput over original HNSW on Jetson. — [PMC](https://www.ncbi.nlm.nih.gov/pmc/articles/PMC12568237/). cuhnsw is used as the GPU HNSW baseline in NDSearch. — [NDSearch ar5iv](https://ar5iv.labs.arxiv.org/html/2312.03141)

### Inferences
- Across the GPU line, the reported "×" over HNSW shrink from ~100× (single-thread baselines, SONG) to ~3–11× (multithreaded baselines) — baseline thread counts must be checked when comparing papers.
- The billion-scale GPU designs (BANG, FusionANNS, PilotANN, cuVS IVF-PQ) converge on the same placement rule: compressed codes on GPU, graph/full vectors on host/SSD, re-rank at the end; the PCIe link (32 GB/s) rather than GPU compute is the limit they overlap against.

### Gaps
- Absolute QPS for CAGRA and cuVS are in figures only; no text numbers found.
- RUMMY (Zhang et al. 2024, GPU IVF system used as a FusionANNS baseline) — primary paper not located in this search.
- No peer-reviewed venue confirmed for CAGRA or BANG (both remain arXiv preprints as of the versions checked).

## Key Question 2 — FPGAs (FANNS, Falcon, Chameleon/ChamVS, SmartSSD HNSW, "Vexless", "DF-GAS")

### Takeaway
ETH Zürich's line (FANNS → Chameleon/ChamVS → Falcon) shows FPGAs winning on *latency and energy* (Falcon: up to 4.3× lower latency than CPU and 19.5× than GPU, 8.0×/26.9× better energy) by pipelining the graph-search operators and tracking visited nodes with on-chip Bloom filters, while GPUs still win large-batch throughput because of ~12× higher memory bandwidth; Vexless and DF-GAS are not FPGA ANN works (see Gaps).

### Cited Findings

**FANNS (SC '23, peer-reviewed; DOI 10.1145/3581784.3607045; arXiv 2306.11182).** "Co-design Hardware and Algorithm for Vector Search" — Wenqi Jiang et al. (ETH Zürich, BUPT, Apple). Given a recall target and FPGA resource budget, auto co-designs IVF-PQ algorithm parameters + accelerator and generates it; includes a hardware TCP/IP stack for scale-out. Reported: up to 23.0× and 37.2× speedup over FPGA and CPU baselines; in an 8-accelerator configuration, 5.5× and 7.6× speedups over GPUs in median and 95th-percentile latency. — [SC23 proceedings page](https://sc23.supercomputing.org/proceedings/tech_paper/tech_paper_pages/pap219.html); [arXiv](https://arxiv.org/abs/2306.11182v1)

**Falcon + DST (PVLDB vol. 18, 2025, peer-reviewed; arXiv 2406.12385, Jun 2024).** "Fast Graph Vector Search via Hardware Acceleration and Delayed-Synchronization Traversal" — Wenqi Jiang, Hang Hu, Torsten Hoefler, Gustavo Alonso. — [VLDB PDF](https://www.vldb.org/pvldb/vol18/p3797-jiang.pdf); [arXiv HTML v2](https://arxiv.org/html/2406.12385v2); code: https://github.com/fpgasystems/Falcon-accelerate-graph-vector-search
- Design: spatial dataflow accelerator; FIFO-connected PEs; systolic priority queues for candidates/results; Bloom filters for visited set (3 Murmur2 hashes, 256 Kbit bitmap, ~1 false positive per 600K for 1K visited nodes); vector-fetch units with up to 64 outstanding reads; L2/dot/cosine compute units; across-query parallelism (one pipeline per query) and intra-query parallelism (multiple Bloom-fetch-compute units = number of memory channels); on-board TCP/IP for network serving; unified graph format (HNSW base layer only, NSG). DST relaxes best-first order to evaluate multiple candidate groups per iteration (parameters mg, mc). — [arXiv HTML](https://arxiv.org/html/2406.12385v2)
- Setup: AMD Alveo U250, 64 GB DDR4 (4 channels, ~77 GB/s), 200 MHz, DDR4 not HBM (HBM noted for future ASIC); CPU: 48-core Xeon Platinum 8259CL, 384 GB (~256 GB/s); GPU: V100 16 GB HBM2 (900 GB/s); datasets: first 10M of SIFT (128-d), Deep (96-d), SPACEV (100-d); HNSW and NSG, max degree 64, queue 64, ≥90% recall@10; GGNN on GPU; IVF 4096 lists via Faiss on CPU/GPU; 100 Gbps NICs. — [arXiv HTML](https://arxiv.org/html/2406.12385v2)
- Results: online latency up to 4.3× lower than CPU and 19.5× lower than GPU with graphs (up to 102.1×/6.5× vs CPU/GPU IVF); energy efficiency up to 8.0× (CPU) and 26.9× (GPU); power at batch ≤16: CPU 136.9–209.2 W, GPU 183.4–324.2 W, Falcon 55.2–62.3 W; at batch 10K GPUs lead in throughput owing to ~12× memory bandwidth, comparable when normalized by bandwidth; DST gives 1.7–2.9× lower latency than BFS-style traversal and raises R@10 by 0.14–4.93%; end-to-end: 1.03–1.60× retrieval speedup for recommenders, up to 1.60× TTFT for RAG. — [arXiv HTML](https://arxiv.org/html/2406.12385v2)

**Chameleon / ChamVS (PVLDB 18(1): 42–52, 2024, peer-reviewed; arXiv 2310.09949).** "Chameleon: a Heterogeneous and Disaggregated Accelerator System for Retrieval-Augmented Language Models" — Wenqi Jiang et al. (ETH Zürich). ChamVS: IVF index scanned on GPU, PQ codes stored on FPGA memory nodes (Alveo U250, 64 GB DDR4, 140 MHz) with PQ decoding units, systolic priority queues and an approximate hierarchical priority queue for top-K; LLM inference on GPUs (RTX 3090); CPU coordinator. ChamVS: up to 23.72× latency reduction vs optimized CPU and 5.8–26.2× better energy efficiency; end-to-end RALM up to 2.16× lower latency and 3.18× higher throughput vs CPU-GPU hybrid. — [arXiv HTML v4](https://arxiv.org/html/2310.09949v4); [PVLDB PDF](https://vldb.org/pvldb/vol18/p42-jiang.pdf); [ACM DL](https://dl.acm.org/doi/10.14778/3696435.3696439)

**SmartSSD HNSW (CSDANNS) (IEEE Transactions on Computers; extension of FCCM 2020; arXiv 2207.05241, peer-reviewed).** "Accelerating Large-Scale Graph-based Nearest Neighbor Search on a Computational Storage Platform" — Ji-Hoon Kim, Yeo-Reum Park, Jaeyoung Do, Soo-Young Ji, Joo-Young Kim. HNSW modified for hardware; HLS and RTL accelerators on Samsung SmartSSD; scaled to 4 SmartSSDs with graph parallelism. SIFT1B: 75.59 QPS at 258.66 W; 12.83×/17.91× faster and 10.43×/24.33× more energy-efficient than CPU/GPU servers. — [arXiv abs](https://arxiv.org/abs/2207.05241)

**Other FPGA+HBM graph-processing context (not ANN-specific):** ScalaBFS (BFS on Alveo U280 HBM2, near-linear scaling with HBM pseudo-channels), GraphScale, ACTS — relevant as HBM-channel-parallelism design patterns. — [ScalaBFS arXiv](https://arxiv.org/pdf/2105.11754)

### Inferences
- The FPGA works consistently frame the win as latency/energy at small batch, not peak throughput; FANNS's "7.6× over GPU" is a *tail-latency* figure across 8 FPGAs, and Falcon explicitly concedes batch-10K throughput to GPUs.
- Falcon's Bloom-filter visited set and Chameleon's hierarchical priority queue are the reusable micro-architectural ideas that later NDP/PIM designs (BANG's per-query Bloom filter, Cosmos's local candidate lists) borrow.

### Gaps
- "Vexless" (SIGMOD 2024) is a serverless vector DB on Azure Functions, not an FPGA work — [SIGMOD24 Vexless](https://www.cs.purdue.edu/homes/csjgwang/pubs/SIGMOD24_Vexless.pdf). No source for "DF-GAS" as an FPGA ANN accelerator was found; the only GAS hit is the "Swift" FPGA graph-accelerator framework (not ANN).
- A dedicated "ANNS on FPGA with HBM" paper was not located; Falcon uses DDR4 and FANNS's HBM usage was not confirmed from the abstract.

## Key Question 3 — PIM / NDP (UPMEM, HBM-PIM/AiM, DIMM-NDP; NDSearch, ANNA, ANSMET, DRIM-ANN, UpANNS, PIMANN)

### Takeaway
PIM work splits into (a) real-hardware UPMEM systems for IVF-PQ (DRIM-ANN, UpANNS, PIMANN) that reach roughly GPU-parity throughput at ~2× better energy and 2.4–10× over CPU, limited by weak DPU compute and the shared DDR bus; and (b) simulated DIMM/rank-level NDP (ANSMET, ISCA '25: 5.26× avg over CPU for HNSW; the 2026 billion-scale PIM graph co-design: up to 20×/17.1× over CPU/GPU) that offloads distance computation while keeping traversal on the host. ANNA (HPCA '22) is the canonical standalone ASIC for PQ-based search (2.3–61.6× throughput, 4.3–82.1× lower latency vs CPU/GPU).

### Cited Findings

**ANNA (HPCA 2022, peer-reviewed; pp. 169–183; DOI 10.1109/HPCA53966.2022.00021).** "ANNA: Specialized Architecture for Approximate Nearest Neighbor Search" — Yejin Lee, Hyunji Choi, Sunhong Min, Hyunseung Lee, Sangwon Beak, Dawoon Jeong, Jae W. Lee, Tae Jun Ham (Seoul National University). Compatible with ScaNN and Faiss (PQ with partitioning); specialized dataflow pipeline and data reuse; "multiple orders of magnitude higher energy efficiency, 2.3–61.6× higher throughput, and 4.3–82.1× lower latency" vs server CPUs/GPUs on million- and billion-scale datasets. Talk outline mentions two-level PQ encoding/search and memory-traffic optimization. — [IEEE CSDL](https://www.computer.org/csdl/proceedings-article/hpca/2022/202700a169/1Ds0hbEivny); [HPCA 2022 program](https://hpca-conf.org/2022/program/). A 2026 comparison table characterizes ANNA as an ASIC "operating on compressed vectors with parallel lookup pipelines". — [ACRONYM arXiv](https://arxiv.org/html/2606.03151v1)

**ANSMET (ISCA '25, peer-reviewed; pp. 1093–1107; DOI 10.1145/3695053.3731013).** "ANSMET: Approximate Nearest Neighbor Search with Near-Memory Processing and Hybrid Early Termination" — Yiwei Li, Yuxin Jin, Boyu Tian, Huanchen Zhang, Mingyu Gao (Tsinghua). — [PDF](https://people.iiis.tsinghua.edu.cn/~gaomy/pubs/ansmet.isca25.pdf)
- Motivation (Fig. 1, Faiss on 14-core Xeon 5120): distance computation dominates IVF and HNSW time; "50% to over 90%" of fetched vectors turn out not close enough, so their fetch/compute is wasted. — [PDF](https://people.iiis.tsinghua.edu.cn/~gaomy/pubs/ansmet.isca25.pdf)
- Design: heterogeneous CPU+NDP; index traversal and result sorting on host CPU; distance comparison in DIMM-buffer-chip NDP units (one per rank, 32 total, 1.2 GHz, 16-wide 32-bit MACs, 300 mW, 0.06 mm²); hybrid early termination (partial-dimension + partial-bit lower bounds) with offline common-prefix elimination; hybrid vertical/horizontal partitioning across ranks (1 kB sub-vectors); hot-vector replication (replicating top-4 HNSW layers = 0.14% of data cuts load imbalance from 1.49× to 1.05×); adaptive polling. — [PDF](https://people.iiis.tsinghua.edu.cn/~gaomy/pubs/ansmet.isca25.pdf)
- Setup: cycle-accurate Ramulator 2.0 simulation; DDR5-4800, 4 channels × 2 DIMMs × 4 ranks; datasets SIFT (1M, uint8, 128-d), DEEP (1B, fp32, 96-d), GIST (1M, 960-d); HNSW efConstruction 500, max degree 16; IVF also evaluated. — [PDF](https://people.iiis.tsinghua.edu.cn/~gaomy/pubs/ansmet.isca25.pdf)
- Results: NDP gives 5.26× average (up to 6.40×) over the CPU baseline by raising available bandwidth 8×; early termination adds 1.31× on CPU and 1.52× on NDP. Energy figures exist but were not extracted. — [PDF](https://people.iiis.tsinghua.edu.cn/~gaomy/pubs/ansmet.isca25.pdf)

**NDSearch (ISCA 2024, peer-reviewed; IEEE 10609615; arXiv 2312.03141).** See Key Question 4 (in-storage) — it is simultaneously the flagship NAND-level NDP design. — [IEEE Xplore](https://ieeexplore.ieee.org/document/10609615)

**DRIM-ANN (SC '25, peer-reviewed; arXiv 2410.15621).** "DRIM-ANN: An Approximate Nearest Neighbor Search Engine based on Commercial DRAM-PIMs" — ICT, Chinese Academy of Sciences. Target: UPMEM has high bandwidth/capacity but weak per-bank processors (no FP, no multiply) → replace squaring with lookup tables; load balancing and I/O optimizations for IVF-PQ (OPQ/DPQ). Setup: up to 2,543 DPUs @350 MHz, 159 GB PIM memory; CPU baseline Xeon Gold 5218 (32 threads, Faiss-CPU); GPU A100 80 GB (Faiss-GPU); SIFT100M, DEEP100M (uint8), recall@10 ≥ 0.8; nlist 2^14–2^16, nprobe 96. Results: 1.63–2.25× (SIFT100M) and 1.61–2.46× (DEEP100M) over Faiss-CPU on real UPMEM; Faiss-GPU is ~12.3× faster than Faiss-CPU so real UPMEM reaches ~16% of GPU; on *simulated* HBM-PIM and SK hynix AiM, 11.3–12.3× and 30.1–33.9× over CPU (AiM 2.09–2.67× over GPU); energy 1.10–1.58× better than CPU. The abstract's "2.67× over GPU" is the simulated AiM case. — [arXiv HTML v2](https://arxiv.org/html/2410.15621v2)

**UpANNS / MemANNS (SC '25, peer-reviewed; arXiv 2410.23805).** "UpANNS: Enhancing Billion-Scale ANNS Efficiency with Real-World PIM Architecture" — Sitian Chen, Amelie Chi Zhou, Yucheng Shi, Yusen Li, Xin Yao. Architecture-aware data placement, dynamic resource management, co-occurrence-optimized encoding, early-pruning top-k. Setup: 7 UPMEM modules, 896 DPUs, 56 GB, 612.5 GB/s, ~162 W; IVFPQ (IVF4096 default; nprobe 64–256; batch 1,000); DEEP1B/SIFT1B/SPACEV1B; CPU 2× Xeon Silver 4110 128 GB (Faiss-CPU); GPU A100 PCIe 80 GB (Faiss-GPU). Results: 1.6–4.3× QPS over Faiss-CPU; comparable to Faiss-GPU in most cases; ~2–2.3× QPS/W vs GPU; up to 9.3× QPS per dollar vs GPU; projected 2.6× GPU QPS at 2,560 DPUs. Recall not reported. — [arXiv abs](https://arxiv.org/abs/2410.23805); [HTML v2](https://arxiv.org/html/2410.23805v2)

**PIMANN (USENIX ATC '25, peer-reviewed; pp. 1223–1241).** "Turbocharge ANNS on Real Processing-in-Memory by Enabling Fine-Grained Per-PIM-Core Scheduling" — Puqing Wu et al. (Renmin U.) + Kuaishou. Observes ANNS has ~1:1 compute-to-memory ratio; UPMEM shares the DDR bus so CPU and PIM cannot access memory simultaneously → batch scheduling leaves inter-batch idle time and intra-batch imbalance. Repurposes an undocumented per-core control interface for per-PIM-core DDR arbitration; persistent PIM kernel + per-PU query dispatch by real-time load. Reported 2.4–10.4× throughput over existing CPU/GPU ANNS systems. Code: github.com/cds-ruc/PIM-ANNS. — [ATC '25 page](https://www.usenix.org/conference/atc25/presentation/wu-puqing)

**Graph-based ANNS on PIM at billion scale (arXiv 2605.25522, May 2026). Preprint.** "Co-Designing Graph-based Approximate Nearest Neighbor Search at Billion Scale for Processing-in-Memory" — Sitian Chen, Yusen Li, Yao Chen, Minwen Deng, Jintao Meng, Amelie Chi Zhou. Argues prior PIM designs used cluster indexes with a lower recall ceiling; contributes a compacted index layout (14.5× smaller PIM-resident footprint), asynchronous pipelined scheduler saturating host↔PIM interconnect, multiplication-free distance kernel (<0.08% recall loss). Reports up to 20× (CPU), 17.1× (GPU) and 129× (prior PIM, high-recall regime) throughput on three billion-scale benchmarks; targets UPMEM, Samsung HBM-PIM, SK hynix AiM. — [arXiv abs](https://arxiv.org/abs/2605.25522)

**HBM-PIM distance kernels (JSTS 2025 / ICEIC 2025; Ewha).** "Hardware-software Co-design for Vector Similarity Search on HBM-PIM" / "Optimized Distance Calculation Support for HBM PIM": ISA extension for Manhattan/Euclidean/cosine distance; simulations on random matrices show up to 44% cycle reduction. Exact distance kernels, not an ANN index. — [Ewha record](https://pure.ewha.ac.kr/en/publications/optimized-distance-calculation-support-for-hbm-pimprocessing-in-m/)

**ACRONYM (arXiv 2606.03151, Jun 2026). Preprint. [also updates]** "ACRONYM: Accelerated Approximate Nearest Neighbor Search in Memory for Dynamic Vector Databases" — Nayan, Zhang, Ponzina, Rosing, Naeemi. CAM-based in-memory Hamming-distance exhaustive search with distribution-independent encoding (systolic XOR-accumulate encoder), explicitly to avoid index rebuilds and allow updates during search. Million-scale: >90% recall, 8×10⁶ QPS, 32 MB footprint, 2.56 µJ/query, ~400× over HNSW-CPU and ~80× over FAISS-IVF-GPU. — [arXiv abs](https://arxiv.org/abs/2606.03151)

**SpANNS (arXiv 2601.03229, Jan 2026). Preprint.** CXL Type-2 near-memory platform for *sparse*-vector ANNS: controller for query parsing/cluster filtering, compute-enabled DIMMs for index traversal and distance; 15.2–21.6× over CPU baselines. — [arXiv abs](https://arxiv.org/abs/2601.03229)

**Preprints noted but not read:** ANNS-AMP (adaptive mixed precision, arXiv 2606.07156), RVANNS (RISC-V mixed-precision indexing + locality-aware traversal, arXiv 2608.09077). — [ANNS-AMP](https://arxiv.org/pdf/2606.07156); [RVANNS](https://arxiv.org/pdf/2608.09077). ICE (MICRO 2022) is cited as 3D-NAND in-memory computing for vector similarity search (citation only). — [cited in NAVIS](https://arxiv.org/pdf/2605.11523)

### Inferences
- Real UPMEM results (DRIM-ANN ≈16% of A100 throughput; UpANNS ≈ parity at ~2× energy efficiency) are far below simulated HBM-PIM/AiM projections (2–3× GPU); the gap is per-DPU compute and the shared DDR bus, exactly what PIMANN's scheduling attacks.
- All simulated NDP designs keep traversal/sorting on the host and offload only distance comparison, because graph traversal is control-heavy and irregular; the 2026 PIM graph co-design is the first to claim billion-scale *graph* search on PIM.

### Gaps
- No work specifically mapping ANN onto Samsung AxDIMM was found.
- "DF-ANNS" and "TBD" (as named in the brief) could not be identified; no source found.
- ANNA's simulator methodology and per-dataset numbers are behind IEEE paywall; only the abstract was accessible.

## Key Question 4 — In-storage / computational storage (SmartSSD, NDSearch, SmartANNS, VStore, REIS, DiskANN offload)

### Takeaway
In-storage designs attack the SSD I/O bottleneck of DiskANN-style search by moving traversal/distance into the device: SmartSSD-FPGA systems (CSDANNS 75.59 QPS on SIFT1B with 4 SmartSSDs; SmartANNS up to 10.7× over CSDANNS, near-linear scaling) exploit on-board FPGA logic, whereas NDSearch (ISCA '24) goes down to NAND-LUN-level "search-page" commands and reports up to 31.7×/14.6×/7.4×/2.9× throughput over CPU/GPU/SmartSSD-only/DeepStore at ~26 W; REIS (ISCA '25) uses only existing SSD components for RAG retrieval (13× perf, 55× energy vs server).

### Cited Findings

**NDSearch / NDSEARCH (ISCA 2024, peer-reviewed; IEEE 10609615; arXiv 2312.03141 "In-Storage Acceleration of Graph-Traversal-Based Approximate Nearest Neighbor Search").** Authors from Duke (Yitu Wang, Yiran Chen, Hai Li et al.), UCLA, Samsung Semiconductor (Zongwang Li, Linghao Song among authors). — [IEEE Xplore](https://ieeexplore.ieee.org/document/10609615); [NSF PAR full text](https://par.nsf.gov/servlets/purl/10534943); [ar5iv](https://ar5iv.labs.arxiv.org/html/2312.03141)
- Bottleneck: graph indexes reach hundreds of GB > single-node DRAM; spilling to SSD hits limited SSD I/O bandwidth; prior ISC designs (DeepStore) cannot use internal SSD bandwidth because graph traversal is irregular/sparse. — [Duke Scholars](https://scholars.duke.edu/publication/1642930)
- Design: SearSSD — modified SSD + FPGA (bitonic sort) over private PCIe 3.0 x4; "Search-in-NAND" engines (4 per channel, 2 LUN-level accelerators each) replacing read command with a search-page command; two-level scheduling (static degree-ascending BFS vertex reordering under multi-plane constraints; dynamic batch-wise query-to-LUN allocation + speculative prefetch of 2nd-order neighbours); LUNCSR layout that bypasses FTL translation; plane-level hard-decision LDPC. — [ar5iv](https://ar5iv.labs.arxiv.org/html/2312.03141)
- Setup: trace-driven cycle-level simulator on SSD-Sim modelled on Samsung 983 DCT; 512 GB NAND, 32 channels × 4 chips × 4 planes, 16 KB pages; logic at 32 nm/800 MHz; algorithms HNSW (hnswlib CPU, cuhnsw GPU) and DiskANN; datasets glove-100, fashion-mnist, sift-1b, deep-1b, spacev-1b at recall@10 of 95/95/94/93/90%; baselines 2× Xeon Gold 6254 + 24 GB DRAM, Titan RTX 24 GB, DeepStore (channel/chip variants), SmartSSD-only; batch 2048. — [ar5iv](https://ar5iv.labs.arxiv.org/html/2312.03141)
- Results: throughput up to 31.7× CPU, 14.6× GPU, 7.4× SmartSSD-only (DiskANN on sift-1b), 2.9× DeepStore (2.81× HNSW, 2.94× DiskANN); energy efficiency 178.68× CPU, 120.87× GPU, 30.06× SmartSSD-only, 3.48× DS-cp; power 26.32 W (18.82 W SearSSD + 7.5 W FPGA); dynamic allocation cuts page accesses up to 73% (2.67×), speculative search +1.27×, static reordering −38% pages (1.17×); full scheduling 4.1× over bare design on spacev-1b. — [ar5iv](https://ar5iv.labs.arxiv.org/html/2312.03141)

**SmartANNS (USENIX ATC '24, peer-reviewed; pp. 1135–1150).** "Scalable Billion-point Approximate Nearest Neighbor Search Using SmartSSDs" — Bing Tian, Haikun Liu, Zhuohui Duan, Xiaofei Liao, Hai Jin, Yu Zhang (HUST). Host CPUs + SmartSSDs cooperative architecture with hierarchical indices to cut data access/computation on SmartSSDs; dynamic task scheduling over optimized data layout for load balance and reuse; learning-based shard pruning. Implemented on Samsung SmartSSDs; up to 10.7× QPS over CSDANNS; near-linear scaling with more SmartSSDs. Datasets/SmartSSD count not in abstract. — [ATC '24 page](https://usenix.org/conference/atc24/presentation/tian); [PDF](https://usenix.org/system/files/atc24-tian.pdf)

**CSDANNS (IEEE TC; arXiv 2207.05241).** See Key Question 2: 4 SmartSSDs, SIFT1B, 75.59 QPS at 258.66 W, 12.83×/17.91× faster and 10.43×/24.33× more energy-efficient than CPU/GPU servers. — [arXiv abs](https://arxiv.org/abs/2207.05241)

**VStore (DAC 2022, peer-reviewed; DOI 10.1145/3489517.3530560; published 23 Aug 2022).** In-storage computing design for graph-based vector search that targets accuracy, latency, memory use and data movement together; "significant search efficiency improvement and energy reduction while attaining accuracy over CPU, GPU, and ZipNN platforms". Numbers and author list were not retrievable (ACM DL paywall; redirect chain). — [ACM DOI](https://doi.org/10.1145/3489517.3530560); cited as in-storage graph accelerator in [ACRONYM (2026)](https://arxiv.org/html/2606.03151v1)

**REIS (ISCA-52, 2025, peer-reviewed; extended arXiv 2506.16444 v2 Nov 2025).** "REIS: A High-Performance and Energy-Efficient Retrieval System with In-Storage Processing" — Kangqi Chen, …, Jisung Park, Mohammad Sadrosadati, Onur Mutlu (ETH Zürich SAFARI). Problem: RAG retrieval (ANNS + fetching the selected documents) causes heavy host↔storage movement; prior ISP used ISP-unfriendly algorithms, ignored document fetch, and required hardware changes. Design: DB layout linking embeddings to documents; ISP-oriented placement across flash planes + lightweight FTL; ANNS engine using only existing in-SSD compute (binary quantization per secondary source). Results: average 13× retrieval performance and 55× energy efficiency vs a server-grade system. — [arXiv abs](https://arxiv.org/abs/2506.16444); [ETH collection](https://www.research-collection.ethz.ch/items/5d2b5083-f0bc-4115-8a8b-78cc9667f618)

**ES4D / GraphAccel (SNU seminar, 2024–25).** "Accelerating Vector Similarity Search with Near-Storage Processing": ES4D = exact search executed directly on SSDs; GraphAccel = near-storage accelerator for graph-based approximate search. Seminar abstract only; no numbers. — [SNU CSE seminar](https://cse.snu.ac.kr/en/community/seminar/1071)

**Host-side SSD-offload baselines (software, for comparison):**
- DiskANN (NeurIPS 2019): billion-point search on one workstation with 64 GB RAM + SSD; graph + full vectors on disk, PQ codes in memory. — [NeurIPS19 PDF](https://www.cs.utexas.edu/~rak/papers/neurips19-diskann.pdf)
- AiSAQ (Kioxia, arXiv 2404.06004): moves PQ codes to SSD too, 10 MB DRAM for billion-scale queries "without critical latency degradation". — [arXiv](https://arxiv.org/pdf/2404.06004)
- PageANN (arXiv 2509.25487, 2025): page-node graph aligning graph nodes to SSD pages; 1.85–10.83× throughput and 51.7–91.9% lower latency vs prior disk-based methods. — [arXiv](https://arxiv.org/pdf/2509.25487v2)
- GateANN (arXiv 2603.21466, 2026): SSD-based filtered search decoupling traversal from vector retrieval; up to 10× fewer SSD reads, 7.6× throughput. — [listing](https://awesomepapers.io/similarity-search/papers/2603.21466)
- NAVIS (arXiv 2605.11523, May 2026, preprint) **[also updates]**: on-SSD graph search with concurrent updates; identifies "position seeking" (full traversal per insert) as the update bottleneck; layout-supported selective vector read, dynamic entrance-graph update, entrance-graph-aware edge cache; up to 2.74× insert throughput, 1.37× concurrent search throughput, 25.26% lower search latency. — [arXiv abs](https://arxiv.org/abs/2605.11523)

### Inferences
- The 7.4× gap NDSearch reports over a "SmartSSD-only" design quantifies the cost of stopping at the on-board FPGA (which still pulls pages over the SSD controller) versus pushing search into NAND LUNs.
- CSDANNS's absolute 75.59 QPS on SIFT1B (4 SmartSSDs) shows SmartSSD-class throughput is orders of magnitude below GPU-resident designs (BANG ~10⁵ QPS at batch 10K); the value proposition is capacity/cost and energy, not QPS.

### Gaps
- "InSS" and "DiskANN with CSD" as named systems: no sources found; no 2025 paper running DiskANN traversal inside a commercial computational SSD was located.
- VStore's quantitative results and author list were not accessible.

## Key Question 5 — CXL / memory disaggregation (CXL-ANNS, Cosmos, second-tier memory, CXL-ANNX, IKS)

### Takeaway
CXL work treats the pooled memory as "far memory" and compensates with placement: CXL-ANNS (ATC '23) caches hot graph neighbours in local DRAM, prefetches, and offloads distance computation to the CXL controller (111.1× QPS vs SOTA, within 68%/3.8× of an unlimited-DRAM oracle); Cosmos (2025) runs the entire traversal on general-purpose cores inside the CXL device with rank-level distance units (6.72× over host-compute baseline, 2.35× over CXL-ANNS); Cheng et al. (2024) show that second-tier memory (RDMA/CXL/NVM) removes the SSD-induced 5–8× index-size amplification while giving 1.5–5.9× throughput.

### Cited Findings

**CXL-ANNS (USENIX ATC '23, peer-reviewed).** "CXL-ANNS: Software-Hardware Collaborative Memory Disaggregation and Computation for Billion-Scale Approximate Nearest Neighbor Search" — Junhyeok Jang, Hanjin Choi, Hanyeoreum Bae, Seungjun Lee, Miryeong Kwon, Myoungsoo Jung (KAIST CAMEL / Panmnesia). Disaggregates DRAM via CXL into a pool holding all datasets; CXL acts as far memory → caches neighbours expected to be visited most often (node-level relationship) in local DRAM, prefetches likely-next nodes, lets CXL interconnect components search collaboratively in parallel, relaxes execution dependency of neighbour-search tasks. Results: 111.1× higher QPS with 93.3% lower latency vs tested SOTA ANNS platforms; vs an oracle with unlimited DRAM, 68.0% (latency) and 3.8× (throughput). Press notes a real hardware prototype. — [ATC '23 page](https://www.usenix.org/conference/atc23/presentation/jang); [PDF](https://www.usenix.net/system/files/atc23-jang.pdf); [KAIST DSpace](https://dspace.kaist.ac.kr/handle/10203/311402); [Blocks & Files](https://blocksandfiles.com/2023/06/20/panmnesia-speeds-up-vector-search-with-cxl)

**Cosmos (IEEE Computer Architecture Letters, accepted 2025, peer-reviewed; arXiv 2505.16096).** "Cosmos: A CXL-Based Full In-Memory System for Approximate Nearest Neighbor Search" — Seoul National University + Samsung Electronics. — [arXiv abs](https://www.arxiv.org/abs/2505.16096); [HTML](https://arxiv.org/html/2505.16096v1)
- Design: hybrid graph+cluster index (clustering added to in-memory DiskANN so traversal is restricted to relevant clusters); programmable general-purpose cores in each CXL memory controller run the full traversal and candidate-list management with no host involvement during search (CXL-ANNS offloaded only distance computation); rank-level PUs compute partial L2/IP distances on 64 B sub-vector segments with dimensions column-partitioned across DRAM ranks; adjacency-aware cluster placement spreads neighbouring clusters across devices by centroid distance and cluster size; only local top-k crosses PCIe. — [HTML](https://arxiv.org/html/2505.16096v1)
- Setup: custom simulator + Ramulator; 1 TB CXL memory over 4 devices × 256 GB, each 4× DDR5-4800 channels × 2 ranks; SIFT1B and DEEP1B, 10,000-query traces; baselines Base (all data in CXL, host compute), DRAM-only oracle, reproduced CXL-ANNS (without its graph caching), round-robin placement. Recall not reported in the content read. — [HTML](https://arxiv.org/html/2505.16096v1)
- Results: up to 6.72× QPS vs Base on SIFT1B, 5.35× on DEEP1B; up to 2.35× vs CXL-ANNS; lower load-imbalance than round-robin at num_probes 4/8/16. — [HTML](https://arxiv.org/html/2505.16096v1)

**Second-tier memory characterization (arXiv 2405.03267, May 2024; preprint, SJTU + Shanghai AI Lab + Alibaba).** "Characterizing the Dilemma of Performance and Index Size in Billion-Scale Vector Search and Breaking It with Second-Tier Memory" — Rongxin Cheng et al. — [arXiv abs](https://arxiv.org/abs/2405.03267); [HTML v2](https://arxiv.org/html/2405.03267v2)
- Characterization: SSD graph index (DiskANN) pays 5.8× storage amplification for 5.7× throughput; SSD cluster index (SPFresh) pays 7.7× for 1.7×; root cause is the mismatch between SSD block granularity and fine-grained random index reads; graph amplification mostly from edge storage plus padding to block boundaries. Growing graph index from 1.7× to 5.9× raised throughput from 1.9K to 15.2K req/s. — [HTML v2](https://arxiv.org/html/2405.03267v2)
- Hardware: RDMA DRAM via BlueField-3 200 Gbps (≤25 GB/s, 2.8 µs); CXL 2.0 memory expander over PCIe 5.0 x8 (≤32 GB/s, 0.3 µs); 8× Optane 200 (≤60 GB/s, 0.4 µs); SSD baseline Intel D7-P5520 (5.3 GB/s, ~75 µs). Datasets SPACEV1B (100-d int8, 94 GB), BIGANN1B (128-d uint8, 120 GB), DEEP1B (96-d fp32, 358 GB); CXL experiments used 100M subsets. — [HTML v2](https://arxiv.org/html/2405.03267v2)
- Design + results: graph index on second-tier memory with cross-query pipelining (coroutines for RDMA; reordered loads/prefetch for CXL/NVM) and CSR layout → amplification 1.7–4.1× (vs 4.3–4.9× SSD) and 2.3–4.1× SSD throughput (conclusion: 1.5–5.6× with 15–62% less amplification); cluster index with decoupled vector/address layout and ILP/greedy grouping → index 16–22% of SSD index size and 1.4–7.1× throughput (conclusion: 1.4–5.9× with 92–98% less amplification). Graph beats cluster by 2.1×/2.2×/1.2× (RDMA/CXL/NVM) on BIGANN/DEEP; cluster wins 1.5×/1.2×/1.7× on SPACEV. — [HTML v2](https://arxiv.org/html/2405.03267v2)

**CXL-ANNX (Michigan Tech dissertation, not peer-reviewed).** Distributed near-memory accelerator running sub-queries across multiple CXL-attached DRAM modules; techniques: termination of unnecessary sub-queries, speculative search, memory-aware cluster placement; claims 13.1× throughput over DiskANN on billion-scale datasets. — [MTU ETD](https://digitalcommons.mtu.edu/etdr/1961)

**IKS — Intelligent Knowledge Store (arXiv 2412.15246, Dec 2024; preprint, venue unconfirmed).** "Accelerating Retrieval-Augmented Generation" — Derrick Quinn, …, Hamed Zamani, Mohammad Alian. CXL Type-2 device with near-memory accelerators and cache-coherent host interface for *exact* kNN over a 512 GB vector DB; argues exact retrieval (smaller, more accurate doc list) can cut end-to-end time vs ANN; v1: 13.4–27.9× faster search vs Sapphire Rapids CPUs → 1.7–26.3× lower end-to-end RAG inference time; a later version states 18–52× vs Sapphire Rapids on-chip accelerators → 2.0–49× end-to-end (figures differ by version); DRAM also usable as a memory expander to avoid stranded DRAM; argues CXL avoids DIMM-NDP limits on per-rank capacity, host compute sharing and thermals. — [arXiv abs](https://arxiv.org/abs/2412.15246)

### Inferences
- Placement across tiers converges on: hot graph layers/entry neighbourhoods in local DRAM, bulk graph + vectors in CXL pool, and compute pushed to the CXL device for distance (CXL-ANNS) or whole traversal (Cosmos); Cheng et al. additionally show that moving *off SSD* alone shrinks the index 15–98% because fine-grained access removes block padding.
- Cosmos's 2.35× over CXL-ANNS was measured with CXL-ANNS's graph caching disabled, so it likely overstates the gap against the full CXL-ANNS system.

### Gaps
- No peer-reviewed 2025–26 paper specifically evaluating DiskANN/Vamana split across local DRAM + CXL-attached DRAM was found beyond the Cheng et al. preprint (which used 100M subsets for CXL).
- "DRAM-tiered DiskANN" and "CXL-based billion-scale ANN" as distinct titles were not found; they may refer to CXL-ANNS/Cosmos.

## Key Question 6 — Custom ASICs and end-to-end RAG accelerators (ANNA, Chameleon, RAGO, Hermes, PipeRAG, TeleRAG, HeteRAG, 2026)

### Takeaway
Beyond ANNA (HPCA '22 ASIC) and ANSMET/REIS (ISCA '24–'25), the RAG-level work splits into accelerator systems (Chameleon FPGA+GPU; IKS CXL; REIS in-storage; Hermes ISCA '25 distributed datastores: up to 9.33× latency, 2.10× energy) and scheduling/pipelining frameworks (RAGO: 2× QPS/chip, 55% TTFT; PipeRAG: 2.6×; TeleRAG MLSys '26: 1.98× latency). The consistent bottleneck finding is that retrieval becomes dominant when the datastore is large (trillion-token / 512 GB), retrieval is frequent (per-token in RETRO-style decoders), or the generator is small; Chameleon reports the optimal accelerator-resource split ranging 53.7%–99.0% across RALM configurations. HeteRAG is a software retrieval-chunking method, not hardware.

### Cited Findings
- **Chameleon** (PVLDB 18(1), 2024): characterizes 4 RALM configs (Dec-S 101M, Dec-L 1259M, EncDec-S 158M, EncDec-L 1738M), retrieval every token for decoder-only and every 8/64/512 tokens for enc-dec, over 1B-vector DBs (Deep, SIFT, SYN-512, SYN-1024); in the CPU-GPU baseline, PQ-code scan on CPU limits vector search; bottleneck shifts across configs so the optimal vector-search accelerator ratio ranges 53.7%–99.0%; with ChamVS retrieval latency becomes "almost negligible" vs GPU inference; retrieval-step speedups Dec-S 1.94–4.11×, EncDec-S 1.71–3.02×, Dec-L 1.76–3.41×, EncDec-L 1.29–2.13×; end-to-end 2.16× latency, 3.18× throughput. — [arXiv HTML v4](https://arxiv.org/html/2310.09949v4)
- **RAGO** (arXiv 2503.14649, Mar 2025; Wenqi Jiang, Suvinay Subramanian, Cat Graves, Gustavo Alonso, Amir Yazdanbakhsh, Vidushi Dadu — ETH + Google): RAGSchema abstraction + workload analysis showing large performance variability across RAG algorithms; RAGO yields up to 2× QPS per chip and 55% TTFT reduction vs RAG built on LLM-system extensions. Venue not stated on arXiv (ISCA 2025 not confirmed). A talk abstract describes RAGO as "the first systematic performance study of RAG" and Chameleon as "the first heterogeneous accelerator system for RAG". — [arXiv abs](https://arxiv.org/abs/2503.14649); [BU talk](https://www.bu.edu/cds-faculty/stay-connected/calendar/?eid=304317)
- **Hermes** (ISCA 2025, peer-reviewed; pp. 958–973; DOI 10.1145/3695053.3731076): Michael Shen, Muhammad Umar, Kiwan Maeng, G. Edward Suh, Udit Gupta. As datastores grow to trillions of tokens, retrieval raises latency and lowers throughput/energy efficiency; partitions and distributes datastores across nodes and uses hierarchical search to route queries to subsets; up to 9.33× end-to-end latency and 2.10× energy reduction at trillion-token scale without retrieval-quality loss. — [PSU Pure](https://pure.psu.edu/en/publications/hermes-algorithm-system-co-design-for-efficient-retrieval-augment/)
- **RAG systems trade-off characterization** (arXiv 2412.11854, Dec 2024, same authors as Hermes; preprint): taxonomy of RAG components; inefficiencies can cause "TTFT latencies that are twice as long" and unoptimized datastores consuming "terabytes of storage". - **PipeRAG** (arXiv 2403.05676, 2024; ETH): pipeline parallelism between retrieval and generation, flexible retrieval intervals, performance model; up to 2.6× end-to-end generation latency speedup; motivates with retrievals from large DBs constituting "a substantial portion of the overall generation time" for iterative retrieval. — [arXiv](https://arxiv.org/abs/2403.05676?context=cs); [ETH collection](https://www.research-collection.ethz.ch/handle/20.500.11850/663487)
- **TeleRAG** (MLSys 2026, peer-reviewed; arXiv 2502.20969): lookahead retrieval prefetches IVF clusters CPU→GPU during generation for a 61 GB Faiss index with Llama-3-8B; MLSys version: up to 1.98× average end-to-end latency reduction (single query) and 1.83× throughput (batched); arXiv v1 said 1.72×, a later version 1.53×/1.83×. — [MLSys 2026](https://proceedings.mlsys.org/paper_files/paper/2026/hash/7fd522b89ac21009b7bbe7560a9a5add-Abstract-Conference.html); [arXiv](https://arxiv.org/abs/2502.20969)
- **HeteRAG** (arXiv 2504.10529, Apr 2025, preprint): heterogeneous *representation* framework (short chunks for generation, multi-granular chunks for retrieval, adaptive prompt tuning); no hardware, no speedup numbers. — [arXiv abs](https://arxiv.org/abs/2504.10529)
- **HedraRAG** (arXiv 2507.09138, 2025): coordinating LLM generation and DB retrieval in heterogeneous RAG serving (not read; listed for completeness). — [arXiv](https://arxiv.org/pdf/2507.09138)
- **RAGDoll** (arXiv 2504.15302, 2025): single-GPU offloading RAG; for an 8B model per-stage averages were retrieval ~293–320 s vs generation ~57–66 s in their batch setting, with waiting time dominating. — [arXiv](https://arxiv.org/pdf/2504.15302)
- **ANNA** ASIC details: see Key Question 3.

### Inferences
- "Retrieval share" is never reported as a single number across papers; it is configuration-dependent (Chameleon's 53.7–99.0% optimal-accelerator-ratio range is the most explicit quantification). Hardware papers (IKS, REIS, Hermes) all pick the regime where retrieval dominates (exact search, trillion-token datastores, in-storage document fetch).

## Key Question 7 — Characterization studies of vector search on hardware

### Takeaway
Characterization work agrees that ANN search is memory-bound (≈1:1 compute-to-memory ratio; 50–90% of fetched vectors are wasted; CPU results track cache bandwidth/latency and microarchitecture more than SIMD width), that SSD-resident indexes pay 5–8× storage amplification for throughput because of block-granularity mismatch, and that GPUs only win when the index is device-resident — with PCIe transfer of a "data-owning" index taking >95% of wall time in a relational-engine study.

### Cited Findings
- Cheng et al. (arXiv 2405.03267): DiskANN 5.8× storage amplification for 5.7× throughput; SPFresh 7.7× for 1.7×; second-tier memory (RDMA/CXL/NVM) removes it. — [arXiv abs](https://arxiv.org/abs/2405.03267)
- ANSMET (ISCA '25): Faiss IVF/HNSW on 14-core Xeon — distance computation dominates and 50% to >90% of visited vectors are not close enough to matter. — [PDF](https://people.iiis.tsinghua.edu.cn/~gaomy/pubs/ansmet.isca25.pdf)
- PIMANN (ATC '25): ANNS has a roughly 1:1 compute-to-memory-access ratio. — [ATC '25](https://www.usenix.org/conference/atc25/presentation/wu-puqing)
- CAGRA: device memory bandwidth limits GPU throughput at large batch/dimension; FP16 storage helps. — [arXiv HTML](https://arxiv.org/html/2308.15136v2)
- Falcon: GPU wins batch-10K throughput due to ~12× memory bandwidth; bandwidth-normalized throughput comparable to FPGA. — [arXiv HTML](https://arxiv.org/html/2406.12385v2)
- "To GPU or Not to GPU: Vector Search in Relational Engines" (arXiv 2605.15957, May 2026; Mageirakos, André, Kabić, Wu, Chronis, Alonso — ETH; preprint): extends TPC-H with vectors; relational operators gain far more from GPU than vector search; when vector search must move data and indexes to the GPU it is not the best choice even with NVLink; IVF1024 and CAGRA over PCIe are "orders of magnitude slower than CPU" and index transfer takes >95% of wall time on most queries; proposes a smaller index/embedding organization that makes GPU win on fast interconnects. — [arXiv abs](https://arxiv.org/abs/2605.15957)
- "Bang for the Buck: Vector Search on Cloud CPUs" (DaMoN '25, peer-reviewed workshop; arXiv 2505.07621; Leonardo Kuffo, Peter Boncz): IVF on fp32 — AMD Zen4 ≈3× QPS of Intel Sapphire Rapids; ranking reverses for HNSW; AWS Graviton3 best queries-per-dollar across most index/quantization settings, beating Graviton4. — [arXiv abs](https://arxiv.org/abs/2505.07621)
- Microarchitecture study (arXiv 2512.02278, Dec 2025; title not captured): CPU cache bandwidth/latency matter because vector search "is memory-bound in many scenarios"; cross-microarchitecture performance depends on data-access patterns of the algorithm, not only SIMD. — [arXiv PDF](https://arxiv.org/pdf/2512.02278v1)
- Graph-based ANN revisit (arXiv 2204.00824, 2022): HNSW multithreaded CPU vs GGNN/SONG/Faiss-IVFFlat on GPU; SONG only ran on SIFT1M; GGNN ~2× SONG at batch 10K. — [arXiv](https://arxiv.org/pdf/2204.00824)

### Inferences
- The field has three distinct "memory walls": GPU HBM bandwidth (in-memory graph search), host DRAM bandwidth/latency (CPU graph search → NDP/PIM target), and SSD block granularity (billion-scale → in-storage/CXL target); each hardware class in this note maps to one wall.

### Gaps
- No single peer-reviewed cross-hardware (CPU vs GPU vs FPGA vs PIM) characterization of ANN search at matched recall was found; the comparisons above are each paper's own baselines.
- "VDB on CPU vs GPU profiling" as a named study was not identified beyond arXiv 2605.15957.
